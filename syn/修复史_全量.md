
## ICACHE-1：为什么旧写法（同拍组合旁路）上板必炸（原编号：无 B 编号，属“上板改造”段）

**位置**：文件头块注释中 `为什么原来必须改（上板必炸）` 一节（原第 24~29 行）。

**原文**：

> ```systemverilog
>  * 为什么原来必须改（上板必炸）：
>  *   旧写法是“同拍组合旁路”：
>  *       assign cpu_rdata = hit ? data[index] : mem_rdata;
>  *   它假设 mem_rdata 与本拍 cpu_addr 同拍有效（零延迟组合 ROM）。
>  *   FPGA 的 Block RAM 是**同步读**：地址打一拍、数据下一拍才出，
>  *   所以真实存储器不可能同拍返回数据。
> ```

**补充说明**：这段是 A 类（它决定了整份文件的两拍时序）。**第二轮压缩后**，正本只在
`★ 不变量：同沿、同源` 那条的末尾留了一句引用（`踩坑史（旧“同拍组合旁路”为什么上板
必炸）：见 §ICACHE-1`），所以这里必须保留完整原文 —— 它是“为什么不能改回组合旁路”的
唯一依据。**注意**：正本里不能再出现 `assign cpu_rdata = hit ? data[index] : mem_rdata;`
这种“看起来像真代码”的行 —— 现在的实现是
`assign cpu_rdata = hit ? data[align_index_r] : `NOP;`，两者不可混淆。

## ICACHE-2：时间对齐（原文件最关键的部分，所有寄存器都为它服务）

**位置**：文件头块注释中 `时间对齐` / `两个实测踩过的坑` 两节（原第 31~47 行）。

**原文**：

> ```systemverilog
>  * 时间对齐（本文件最关键的部分，所有寄存器都为这一条服务）：
>  *   一次取指横跨两拍，且“喂 BRAM 的地址”与“做判定的 index/tag”必须描述
>  *   **同一条请求**，判定还必须与 mem_rdata 落在同一拍：
>  *
>  *     拍 T   ：IFU 呈现 cpu_addr(T) = A
>  *     ── posedge T→T+1 ──
>  *              ① cpu_addr_r  <= A           // 喂 BRAM，下一拍才出数据
>  *              ② cpu_index_r <= A 的 index   // 必须同沿、同源，与①配对
>  *                 cpu_tag_r   <= A 的 tag
>  *     拍 T+1 ：align_index_r/align_tag_r（T→T+1 沿由②再寄存一拍）
>  *              与 mem_rdata(=A 的数据) 同拍 → hit/cpu_rdata/miss 全部对齐到 A
>  *
>  *   两个实测踩过的坑：
>  *   - ② 必须与 cpu_addr_r **同沿同源**，否则两者的请求会差一拍，
>  *     每条新指令都被误判成 miss（前端变成 3 拍走一条）。
>  *   - 判定不能挂在“本拍 cpu_addr”上：本拍 cpu_addr 已是**下一条**请求，
>  *     它的数据还在 BRAM 里。
> ```

**补充说明**：完整的 ASCII 时序图（拍 T / posedge / 拍 T+1 那三行）在正本里保留了
“两拍横跨”的骨架，但把三个编号 ①② 的寄存器采样关系改写成散文，
因为 RTL 里 `/* 请求侧寄存器 */` `/* 判定侧寄存器 */` 两段已经把 ①② 兑现了。
两个“实测踩过的坑”是 **A 类**（下一个人很可能会把 index/tag 换成当拍 cpu_addr，
让 3 拍走一条），正本各保留一行并标 `★ 不变量`。

## EXU-1：异常标志的清除必须独立于流水线握手（原编号：v9 修复 C4）

**补充说明**：

事故链条：异常标志原来和别的控制寄存器挤在同一个 always_ff 里，清除分支的条件是
`valid_last & ready_next & EXU_inst_clr`。trap 那一拍之后本级 valid_next 被清 0 →
下游 LSU 的 valid_reg=0 → LSU_ready=0 → ready_next=0，清除分支**永远不成立**；
而记录分支又要求 `valid_last & ~mdu_stall & ~bp_pend`（此时 valid_last 已是 0）。
结果异常标志卡死在 1：exc_pending 每拍成立、trap_take/trap_redirect 每拍都发，
PC 被反复重定向回 mtvec，陷阱处理程序的第一条都跑不完。
现实现：单列一个 always_ff，`if (reset | trap_take)` 清，不等任何握手。

## EXU-11：H1 —— 上游 hold 期间不得重复接收同一条指令（`up_stall` 接收门控）

> **本节不是注释压缩的结果**，是官方差分验证（`cdp-tests`）修掉的一个 **P0 正确性缺陷**。
> 出处：[`../docs/待修复清单_cdp-tests第三轮.md`](../docs/待修复清单_cdp-tests第三轮.md) 第 1 节（H1）。

**现象**：官方差分第一条 `addi` 就 desync —— 参考模型已到 `debug_wb_pc=0x8`/`reg=14`，本 CPU 还停在
`0x4`/`reg=1`，之后全表失配；`jal` 用例里 `0x3c` 的 `addi x1,x1,1` 被执行两次（2→3），`0x40` 因此算出 4、应为 3。

**根因**：`IFU_stall`（= load-use | MDU 忙 | `icache_hold` | `dcache_hold`）期间 IDU 会**保持**它送出的
`valid_last` 与指令编码不变（IDU 自己的 `ready_last` 已经带了 `~IFU_stall`，所以它知道"没被收走"）；
但 EXU 内部的接收判据用的是 `ready_last = ready_next & ~mdu_stall` —— **不含 IFU_stall**。
于是同一条指令在 hold 期间被连续接收两拍、交给 LSU 两次。这是旧设计一直存在的握手漏洞：
没有 Cache 时前端不会真的 hold，所以被掩盖。

**改了什么**：EXU 新增 `input logic up_stall`，把它并进**四处**"接收并锁存"的条件
（`valid_next` 的置 1 分支、EX 级数据寄存器、控制寄存器、异常标志寄存器）；`myCPU.sv` 例化处接
`.up_stall(IFU_stall)`。

**为什么 `valid_next` 在 `up_stall` 期间可以置 0（不是丢指令）**：能走到那条分支说明 `ready_next=1`，

>  * store 为什么用状态机而不是边沿检测：
>  *   cpu_en / cpu_addr 都由上游 LSU 的 pipe 级寄存器保持，是**电平**。

>  *   流水线冻结期间会连续多拍 mem_wen=1，一次 store 被写多次

> ```

**补充说明**：两个实测事实（① load 之后紧跟的 store 一笔都写不进去；② 被测试台的 write-once

## DCACHE-3：MMIO（uncacheable）不缓存

**位置**：文件头“MMIO（uncacheable）保护”一节（原第 53~58 行）+ `uncacheable / uncacheable_req`
两个组合判断。

原文 6 行 → 现在 1 行。

### 删掉的原文（逐字）

> ```systemverilog
>  * MMIO（uncacheable）保护：
>  *   写直达缓存如果只看 tag/index，会把外设寄存器也缓存起来。外设读常有副作用
>  *  （读清中断标志、FIFO 出队），一旦命中缓存，软件读到的就是上一次的快照，
>  *   行为不可预测。因此 addr & ~UNCACHE_MASK != 0 的地址一律：
>  *     - 命中判定恒为“不驻留” -> 读直通外设、不写缓存行；
>  *     - store 的命中合并条件也被排除 -> 不会用旧值去合并写 MMIO 行。
> ```

**补充说明**：`UNCACHE_MASK = 32'h0FFF_FFFF`（只有低于 `0x1000_0000` 的地址可缓存）
这条参数说明保留在参数旁边，未动。注意请求侧用**寄存地址**判（`uncacheable`，与比较侧同拍），
store 的命中合并/`store2_hit` 用**组合地址**判（`uncacheable_req`）—— 两者不能互换。

## DCACHE-6：H2 —— 读请求窗口必须向存储器声明"整字访问"

> 同 §EXU-11，本节是官方差分验证的修复记录，不是注释压缩。
> 出处：[`../docs/待修复清单_cdp-tests第三轮.md`](../docs/待修复清单_cdp-tests第三轮.md) 第 2 节（H2）。

**现象**：`lb x14,2(x1)`（字内偏移 2，内存字节 `0xf0`）读出 0，应为 `0xfffffff0`；
修完 H1 后剩下的失败集恰好是 `lb lbu lh lhu lw sb sh` 这 7 条。

**根因**：上板改造后本 CPU 的契约是"存储器返回**原始整字**、CPU 自己按 `addr[1:0]` 抽取"
（§DCACHE-1 / v9 修复 B1），而课程原始 SoC 的 `mySoC/dram_driver.sv` 会**按 `perip_mask` 先在
存储器侧抽一次** → 二次抽取。

**改了什么**：`assign mem_mask` 在读窗口（`mem_en | mem_req_r`）改成 `2'b10`（整字），
写口仍用真实 `store2_mask`。

**★ 不变量：整字 mask 必须保持到数据被采走那一拍（`mem_req_r=1`）** —— 课程 DRAM 是**组合读**
（`dram_driver` 每拍按当前 mask 重新抽取），只给 `mem_en` 那一拍会在数据回来前就掉回 `store2_mask`。

**对已上板的 bitstream 无影响**：板级 `board/sync_mem.sv` 的读口是 `if (ren) rdata <= mem_ram[word_addr];`
—— **完全不看 mask**（已逐行核对）。所以这一项只是为了兼容课程 SoC 与官方差分，
不改变已上板硬件的行为。

## WBU-2：`stall` 端口漏接 —— iverilog 下的 x 态陷阱

**位置**：`always_ff` 之前的锁存块注释（原第 49 行）+ 文件头两行（原第 4~5 行）。
本模块**原本没有**关于 `stall` 的任何注释，这一节是本次新增的知识，原文只有文件头那两行。

### 删掉的原文（逐字）

> ```systemverilog
> // 写回级是整条数据通路的最终收束点。
> // 无论结果源头是 ALU、访存、跳转返回地址还是 CSR 读值，都会在这里统一选择成 rd_value_next。
> ```
>
> ```systemverilog
>   // 先把来自 LSU 末拍的所有候选结果锁存住，确保最终提交时序稳定。
> ```

**补充说明（这条最容易返工，写全）**：

- 写回级是**纯延迟级**：`valid_next = valid_reg`，`ready` 恒 `1'b1`，它从不背压，
  按设计就不该被暂停 —— 所以 `myCPU.sv` 现在是 `.stall(1'b0)`。
- 但 `else if (!stall)` 里的 `stall` **一旦悬空**（历史上加端口时在 `myCPU.sv` 里漏接），
  iverilog 会把这条 `if` 的条件算成 **x**：条件“未知”时整个 `else` 分支不执行，
  于是**一条写回都出不来** —— 所有写回寄存器永远停在复位值。现象是 PC 还在走、寄存器全是 0。
- 为什么长期没被发现：**FPGA/Verilator 是 2 态仿真**，悬空端口被当成 0/1（而不是 x），
  `!stall` 恰好为真，行为完全正常；只有 iverilog（4 态）的回回归能把它抓出来。
- 判据：任何人再动 `WBU` 的 `stall`/`ready` 端口，或把 `myCPU.sv` 里那句 `.stall(1'b0)`
  改成别的信号，都必须重跑 iverilog 回归，不能只看上板/Verilator。

## CONTROL-5：同步异常的两拍脉冲（`trap_take` / `trap_take_q`）与去重（原编号：v9 新增 C4）
**位置**：模块内 `// v9 新增（C4）：同步异常…` 大块注释 + `trap_take_q_r` 的 always_ff
**删掉的原文**：
> // v9 新增（C4）：同步异常（非法指令 / 访存非对齐 / 指令地址非对齐）
> // -----------------------------------------------------------------------
> // 原来的核只认识 ecall 这一种同步异常，非法指令会被"当成加法"执行掉、
> // 非对齐访存会被静默对齐（LSU 里把 addr[17:16] 强制清零）—— 两者都违反
> // RISC-V 最少可测的语义，而且会让软件拿到错误结果却毫无提示。
> //
> // 这里做三件事：
> //   1) 定优先级（与 RISC-V 规范一致）：
> //        指令地址非对齐(0) > 非法指令(2) > 访存非对齐(4/6)
> //   2) 生成"确认接收一次异常"的单拍脉冲 trap_take，交给 CSR 登记
> //      mepc/mcause/mtval（登记发生在异常指令位于 EX 级的那一拍）。
> //   3) 下一拍用 trap_take_q 发一次**只发一次**的重定向到 mtvec。
> //      为什么要分两拍、而不是用组合电平直接重定向：
> //        - 组合电平在 mem_stall（缓存 hold）期间会持续拉高，而 IFU 的
> //          ready=0 会把重定向丢掉 → 异常丢失；
> //        - 若改成"电平持续发"，则每一拍都 flush，重定向目标那条指令永远
> //          进不了 EX → 整机锁死。这与分支预测器 bp_redirect_pending 踩过
> //          的坑完全相同，所以复用同一手法：先登记、再补发一次。
> //      只用一拍（EXU 那一拍）做重定向的话，hold 期间同样会丢；
> //      所以用"EXU 拍脉冲 + 下一拍补发"覆盖两种时序。

以及 `trap_cause` / `fault_*` 两段原文（这两段改后原样保留，此处只作留档）：

> // 优先级编码（独热）：bit3=指令地址非对齐, bit0=非法指令,
> //                    bit1=load 非对齐, bit2=store 非对齐
> // mtval 取值来源：非法指令给指令编码（IDU 的原始 inst），其余给出错地址。
> //   非法指令的编码由 IDU 透传过来（fault_inst），地址用 EXU 的目标/有效地址
> //   （EX_result：对 load/store 是有效地址，对跳转是目标地址）。

**补充说明**：`trap_take` 去重条件 `~trap_take_q_r` 的作用是"同一拍不重复登记"
（`trap_take_q` 已经把登记延续到下一拍）。当前状态（见 `syn/修复进度_C系列.md` §4.3）：
`TRAP_ENABLE=1` 时 `prog_loop` 仍复现 B4 症状，所以默认 0；`trap_redirect` 这一类
"单拍冲刷脉冲"与 v9 "stall 只冻结寄存器、不清 valid"的握手约定之间仍有已知交互缺陷。

## RESETSYNC-1：原文件头（为什么需要它 / 做法 / 复位极性 / 上板连线建议）
**位置**：原第 3~29 行（整个文件头）
**删掉的原文**：
> /* =============================================================================
>  * reset_sync.sv — 「异步置位、同步释放」的复位同步器
>  * -----------------------------------------------------------------------------
>  * 为什么需要它：
>  *   板卡按键复位是**异步**的（按下时刻与时钟无关）。如果把它直接当同步复位
>  *   喂给 CPU 里成百上千个 `always_ff @(posedge clock) if (reset)`，
>  *   复位的**置位时刻**就与时钟无关，不同寄存器可能在不同拍被清掉，
>  *   而且触发器的复位恢复时间（recovery/removal）会被违反，属于典型的
>  *   亚稳态风险。
>  *
>  * 做法（标准两级同步器）：
>  *   - 置位（assert）走**异步**通路：rst_n_async 一低，输出立刻为低，
>  *     保证按键一按下就进复位，不需要等时钟；
>  *   - 释放（deassert）走**同步**通路：按键松开后，先经两级触发器同步到
>  *     clk 域，再一起释放。这样所有寄存器的复位释放都发生在同一个时钟沿，
>  *     不会出现“部分先释放、部分后释放”。
>  *
>  * 复位极性：
>  *   输入 rst_n_async 是**低有效**（板卡按键一般接成按下拉低），
>  *   输出 rst_sync 是**高有效**，正好对上 v9 全工程
>  *   `always_ff @(posedge clock) if (reset) ...` 的同步高有效复位约定。
>  *
>  * 上板连线建议：
>  *   .clk        (sys_clk)        // 与 CPU 同一时钟
>  *   .rst_n_async(btn_rst_n)      // 按键，低有效
>  *   .rst_sync   (cpu_rst)        // 送 myCPU.cpu_rst
>  * =========================================================================== */
以及两个同步寄存器上方的行注释：
>     // 两级同步寄存器：异步置位、同步释放

**补充说明**：三条不变量（异步置位 / 同步释放 / 输出高有效 `rst_sync = ~sync_ff2`）
在新注释里都保留为 `★ 不变量`，一个字都没有弱化；本文件只是把上面这段
"为什么需要它"的机理解释压缩成了 3 行。
