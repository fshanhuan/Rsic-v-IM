# v9 源码注释迭代 · 统一风格指南（保守版）

> 本文件是本次注释迭代的**唯一权威风格定义**。所有参与改写的 agent 必须遵守。
> 目标：**精简 + 补充**，同时**一个字的知识都不能丢**。

---

## 0. 铁律（违反即返工）

1. **只允许改注释。** 任何真代码 token（标识符、运算符、数字、字符串内容、端口连接、
   `if/else` 结构、`begin/end`）都不能动。空格与换行尽量少动。
   - 有机械校验：`python tools/check_all.py` 会剥离全部注释后逐字符比较。
     它报 `CODE-CHANGED` 的文件**必须回滚重做**。
2. **不许用 PowerShell 的 `Get-Content` / `Set-Content` 读写这些文件。**
   PS 5.1 默认按 ANSI(936) 读，中文注释会变乱码，换行还可能被吃掉，
   结果真代码被粘进注释里（本项目已经踩过一次）。用 Python（显式 UTF-8）
   或 agent 自己的文件工具。
3. **不许删知识，只许搬。** 删掉的每一段"故障战史/实测现象/推演"都必须
   原样写进 `_comment_iter/extract/<文件名>.md`（见 §3）。
4. **A 类注释（接口契约 + 设计不变量）一个字都不许弱化。** 这是仓库最值钱的东西。
5. 注释语言保持**中文**；术语、信号名、代码片段保持原样。

## 1. 注释分三类，处理方式完全不同

| 类 | 内容 | 处理 |
|---|---|---|
| **A 接口契约 / 设计不变量** | "同步 BRAM 是请求/响应两拍交替"、"PC 只在返回结果属于当前 PC 时才推进"、"重定向不看 inst_valid 也不看 ready" | **保留**，可压缩措辞，但**语义强度不许降低**。用 `★ 不变量：` 标出 |
| **B 故障战史** | "v9 修复（B4）：原来…实测 loop_min 的 x1 涨到 2491…因为…所以改成…" | **压缩**成 2~5 行（见 §2），原文搬进 extract |
| **C 缺失 / 不好读** | LSU/WBU/ALU/Reg_Stack 等注释稀薄处；位选掩码、优先级、前递选择 | **补充**（见 §4） |

判断标准：**"下一个人如果不知道这条，会不会把代码改坏？"**
会 → 是 A 类，必须留。只是"当初怎么发现的" → B 类，可压。

## 2. B 类压缩后的固定格式

```systemverilog
// ★ 不变量：<一句话说清"改回去就会坏"的那条约束>
//   原因：<机制，1~3 行。要能让人自己推出结论，而不是只给一句口号>
//   踩坑史 + 实测现象：见 syn/修复史_全量.md §<模块>-<编号>
```

要求：
- `★ 不变量：` 必须是**可执行的判断**（"X 不能看 Y"、"Z 必须与 W 同拍"），
  不是"这里要注意"这种废话。
- `原因` 里保留**机制**，删掉**过程**（波形数字、试了几版、当时怎么想的）。
- 结尾必须给 extract 文档的锚点，否则以后没人找得到细节。
- 原来若已有 `v9 修复（Bx）` 这类编号，**编号要保留**（它是对外索引）。

示例（rtl/IFU.sv 的 B4/B7/B9，26 行 → 5 行）：

```systemverilog
// ★ 不变量：真实重定向既不看 inst_valid，也不看 ready —— 别加回任何一个。
//   原因：重定向的语义是"放弃当前取指、把 PC 拨到确定目标"（dnpc_flag 同时就是
//   IDU 的 flush），而 inst_valid/ready 描述的都是"当前这条取指能不能被接收" ——
//   用它们门控重定向是因果颠倒。且 ecall/mret/fence.i 的 dnpc_flag **只有一拍宽**，
//   被吃掉不会重发（Control 里只有分支误预测建了挂起重发）。
//   踩坑史（B4/B7/B9 三次，含上板 ILA 逐拍证据）：见 syn/修复史_全量.md §IFU-1
```

## 3. 抽取文件（extract）的要求

每个源文件产出一个 `_comment_iter/extract/<文件名>.md`，**只写被删掉/被压缩掉的内容**：

```markdown
# <文件名>

## <模块>-<序号>：<主题>（原编号：v9 修复 B4/B7）
**位置**：<大致行号或所在 always 块>
**删掉的原文**：
> <原注释原文，逐字保留，中文照抄>
**补充说明**：（可选）<如果原文没写清背景，补一句>
```

- 一个主题一节。**宁可多记，不可漏记**。
- 若某文件完全没有 B 类内容，就写一行 `（本文件无需抽取）`。
- 编号规则：`<模块名大写>-<序号>`，例如 `IFU-1`、`CONTROL-3`、`DCACHE-2`。

## 4. C 类补充的要求（重点：LSU / WBU / ALU / Reg_Stack / Reg / add / sext）

补充时**只加注释，不加代码**。要补的是"读代码看不出来、但必须知道"的东西：

- 每个 `always_ff` / `always_comb` 开头一行：**这是什么级、维护什么状态**。
- 反直觉的位选 / 掩码 / 拼接：为什么是这几位的顺序（例如 `imm_B` 的位序）。
- 优先级：`if/else if` 链的**先后顺序**为什么是这个顺序，换序会怎样。
- 握手：`valid/ready/stall` 三者在**哪一拍**对齐，谁跟谁同拍。
- 魔数：`32'h00000013`（NOP）、`2'b10` 等常量的含义。
- 反例标注：某处看起来像 bug 但**不是**（例如"这里不加 begin/end 是有意的"）。

**不要**补"顾名思义"型废话（`// 时钟信号`、`// 复位`）。

## 5. 文件头模板（统一收敛到 ≤ 25 行）

```systemverilog
/* =============================================================================
 * <文件名> — <一句话职责>
 * -----------------------------------------------------------------------------
 * <这个模块在流水线里的位置、上下游是谁>
 *
 * ★ 接口契约（改之前必读）：
 *   - <契约 1>
 *   - <契约 2>
 *
 * ★ 不许改回去的地方（每条一行，细节见 syn/修复史_全量.md）：
 *   - <不变量 1>  → §<锚点>
 *   - <不变量 2>  → §<锚点>
 *
 * 参考：docs/模块阅读文档.md、syn/修复史_全量.md
 * ============================================================================= */
```

原来文件头里那些"为什么又有一个顶层""和上一版方案的取舍"这类**方案沿革**，
压成文件头里的一两行或直接移入 extract（历史价值有，但不必占 RTL 篇幅）。

## 6. 验收（每个 agent 交付前自检）

1. `python tools/check_all.py` → 你负责的文件必须是 `CODE-IDENTICAL`。
2. `python tools/check_all.py --stats` → 注释行数应下降（总目标约 −35%）；
   但 **A 类不变量条数不能少**。
3. `_comment_iter/extract/<文件名>.md` 已产出，且覆盖了你删掉的全部 B 类内容。
4. 全文再读一遍：**"如果我只读注释不看代码，能不能正确理解这个模块？"**
   以及 **"如果有人把某条不变量改掉，注释能不能拦住他？"**

## 7. 注释预算（每个文件的硬上限）

**这一节是第一轮返工后补的，原因值得记住**：
第一轮 prompt 里只写了"补充是本组重点"，没给数量预算，
结果好几个文件**只补没删**（`rtl/Control.sv` 206→317、`rtl/Branch_Predictor.sv` 38→105、
`rtl/Reg.sv` 2→28）。"重点"没有预算约束时，会被理解成"越多越好"。

**判据不是"总数变少"，而是"注释密度与模块难度匹配"**：
反直觉的地方（握手、优先级、位选、为什么不许改回去）要详细；
看一眼就懂的连线/端口/宏定义要极少。
但**总账必须往下走** —— 因为本任务叫"精简还有补充"，不是"扩写"。

### 7.2 关于"−15%"而不是描述里写的"−35%"

我在方案选项里写"预计总注释量 −35%"，**这个估计偏乐观了**，原因：
`−35%` 只估了 B 类战史的压缩量，**没有把"补充"这一半算进去** ——
而 `LSU/WBU/ALU/Reg_Stack/RegisterFile/Reg/add/sext` 这些文件本来只有 1~16 行注释，
是明确要求补的，补完必然增加。

诚实的口径应该是**分开报告**：

- **B 类战史**：净减（这是"精简"的兑现）
- **C 类补充**：净增（这是"补充"的兑现）
- **总数**：小幅下降（因为要精简的文件本来注释就多）

所以验收时看的是：① 每个文件是否落在上表上限内；② `★ 不变量` 条数是否没减少；
③ 覆盖率检查是否 100%；④ 所有文件是否 `CODE-IDENTICAL`。

### 7.3 A 类优先级高于预算

**上限是软约束，A 类不变量是硬约束。**
如果某个文件压到上限就必须删掉一条 `★ 不变量`，那就**超预算**，不要删不变量。
（这类情况在回报里说明即可。）

### 7.4 预算修正记录（第一轮验收后）

写预算时我对"小文件的真实信息量"估计偏低，实测后修正：

| 文件 | 原预算 | 修正为 | 为什么 |
|---|---|---|---|
| `rtl/ALU.sv` | 18 | **40** | 它虽然只有 92 行正文，但藏着**两个真陷阱**：① `unique case` 带来的 `parallel_case` 是**正常产物不是告警**（去掉了会生成优先级链）；② `alu_equal` 宏名与语义相反（给的是"不相等"），要和 EXU 的 `inv_flag` 异或才是 beq/bne 的方向。加上有符号比较的溢出推导、`choose_add_sub` 必须逐分支赋值否则推锁存器 —— 这些压到 18 行必然要丢东西。**它是"小文件但反直觉"的典型，不该按行数配额砍。** |
| `sync_mem.sv` | 45 | 45（不变） | 读写时序契约是全设计的核心，压不动就超 |

**教训**：预算应该按"**反直觉点的数量**"估，而不是按"文件行数 × 比例"。本次的
`ALU / sync_mem / ICache / Data_hazard` 都属于"小而不简单"，`myCPU` 属于"大而简单"
（778 行连线表，按组写而不是按端口写）。

### 7.5 "输入不存在 / 产物没生成"必须显式失败，不许静默跳过

`acceptance_report.py` 原来在 `current_path()` 给出一个不存在的路径时**直接 `continue`**。
2026-10 清理掉工作目录根那份冗余 `board_top_gui.sv` 之后，这个 `continue` 让报表
**悄悄少了一行**、合计从 1312 掉到 1286 却不报任何错 —— 光看结论根本发现不了。

现在改成：缺行时打印 `!! 报表缺行（文件不存在）`，并新增验收维度
**报表完整（无缺行）**。

**同一类教训还有一次**（更危险）：`regress_canonical.py` 的编译失败检测只认 `": error"`，
而 iverilog 找不到 `` `include `` 时只打 `Include file ... not found` —— 于是它判定
"编译 OK"，接着跑**上一次留下的旧 `.vvp`**，报出一个漂亮的假 **7/7**。

**通用规则**：
1. 检查脚本遇到"输入不存在"要**报错**，不要 `continue` / `except: pass` 吞掉；
2. 跑验证前**先删掉上一次的产物**（`.vvp` / `obj_dir`），否则失败会被旧产物掩盖；
3. **产物是否存在**本身就是一个判据 —— 编译"成功"却没有输出文件，就是失败。

### 7.6 预算修正记录（第二轮：H1/H2/H3 真实缺陷修复之后）

§7.1 的预算是按"**注释迭代**"（只重排 / 精简 / 补充**已有**知识）定的。而 H1/H2/H3 是
**真实缺陷修复**，它们带来的"★ 不许改回去"说明是**新知识**，不是注释膨胀：

| 文件 | 原预算 | 修正为 | 实际 | 为什么 |
|---|---|---|---|---|
| `rtl/EXU.sv` | 90 | **105** | 101 | H1：`up_stall` 端口要写清"**为什么不能**用 `ready_last` / `valid_last` 顶替"—— 这是新踩出来的坑（§EXU-11） |
| `rtl/DCache.sv` | 80 | **90** | 83 | H2：读窗口为什么必须把整字 mask 保持到数据被采走那拍（课程 DRAM 是组合读）—— 接口契约级信息（§DCACHE-6） |
| `rtl/MDU_pipelined.sv` | 40 | **55** | 50 | H3：文件头必须写明"工程里有两个逐字相同的副本，改一个必须同时改另一个"（§MDU-4） |
| `rtl/myCPU.sv` | 130 | **140** | 132 | H1 的 `.up_stall(IFU_stall)` 接线说明 |

**该不该涨**：按 §7.3 的原则 —— 上限是**软**约束，"不许改回去"的知识是**硬**约束。
这 4 处若硬压回原预算，丢掉的正是"下次有人再踩同一个坑"的防护。

**总账**：改动前 **1581** 行 → 现在 **1286** 行（**−18.7%**），仍然明显精简；
4 个文件上涨合计 **+34 行**，全部是这三项修复的文档。

## 8. 绝对禁止

- ❌ 改真代码 / 改字符串 / 改端口 / 改实例
- ❌ 删除 A 类不变量（哪怕它很长）
- ❌ 只删不搬（B 类内容必须进 extract）
- ❌ 用 `Get-Content`/`Set-Content` 处理这些文件
- ❌ 顺手"格式化"代码（重排缩进、拆行、对齐）—— 那会让机械校验变得不可读
- ❌ 改 `syn/` 下已有文档（本次只产出 `syn/修复史_全量.md` 的素材）
