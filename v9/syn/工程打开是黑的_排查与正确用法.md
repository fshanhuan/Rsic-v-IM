# GUI 里 Design Runs 是灰的 / 打开工程是黑的 —— 成因与正确用法

> 适用：Vivado 2025.2，工程 `E:\FPGA\v9_vivado_ila\v9_ila\v9_ila.xpr`
> 相关文件：`build_project_ila.tcl`（一条命令重建）、`project_src\board_top_gui.sv`（顶层）

---

## 1. 现象

双击 `.xpr` 打开工程后：

| 界面元素 | 现象 |
|---|---|
| Flow Navigator → **Design Runs** | 空白，或只有一个灰掉的 `synth_1`，右键 Run 是灰的 |
| Flow Navigator → **Synthesis / Implementation** | 大部分条目灰掉点不动 |
| Sources 里的 netlist 源 | 没有 `synth_1` / `impl_1` 节点可双击 |
| 想看时序报告 | Reports 窗口里没有已实现设计的报告 |
| 双击已实现检查点 | 有时能打开（检查点本身是好的），但它是"外来文件"，不属于任何 run |

**关键判据**：到磁盘上看工程目录。

```powershell
Get-ChildItem 'E:\FPGA\v9_vivado_ila\v9_ila' -Force | Select-Object Name
```

如果**没有 `v9_ila.runs`、没有 `v9_ila.srcs`**，那这个工程就只是"一个壳"，
Design Runs 必然是灰的 —— 跟 Vivado 装坏了、工程损坏都无关。

---

## 2. 成因：非工程模式（non-project mode）留下的后遗症

前两版脚本都用过这条错误路线：

```tcl
create_project -force v9_ila_gui $PROJ -part $PART   ;# ← 建了工程
open_checkpoint post_synth.dcp
create_debug_core u_ila_0 ila
implement_debug_core
opt_design
place_design
route_design                    ;# ← 却在工程外面用手工命令把设计实现完了
write_bitstream v9_ila.bit
add_files post_route_ila.dcp    ;# ← 最后把成品"挂"进工程当装饰
```

这套流程**结果是对的**（bit 出来了、时序过了、DRC 干净），但它有一个致命副作用：

* `synth_design / opt_design / place_design / route_design` 是**非工程模式命令**，
  它们在**内存**里操作设计，**完全不碰工程的 run 目录**；
* 于是 `create_project` 建出来的工程里，`synth_1` 从来没有真的 run 过，
  `impl_1` 根本不存在；`add_files` 加上去的 `.dcp` 只是一个普通源文件，
  **不是** run 的产物；
* GUI 的 Design Runs 面板是按 `*.runs` 目录和 run 状态来填的，
  没有 run → 面板全灰；Implementation 相关的菜单项也因为"当前没有打开
  已实现设计"而灰掉。

> 一句话：**工程模式和 prj 模式命令不能混着用**。
> 只要用了 `create_project`，后面就必须用 `launch_runs` / `wait_on_run`；
> 只要用了 `synth_design` / `route_design`，就不该指望 GUI 里能看到流程树。
>
> 详细的判据和修复记录见 `工程打开是黑的_排查与正确用法.md`。

## 3. 正确做法（本工程采用）

### 3.1 把 ILA 做成标准 IP 例化，而不是内存插桩

前一版 ILA 靠 `(* mark_debug = "true" *)` + `create_debug_core` 在内存里插入。
这条路只能在非工程模式下走（`create_debug_core` 需要先 `open_checkpoint`），
所以它天然和"GUI 可见的 run"冲突。

本版改成 Vivado 最标准的写法：

```tcl
create_ip -name ila -vendor xilinx.com -library ip -version 6.2 -module_name u_ila_0
set_property -dict [list \
    CONFIG.C_NUM_OF_PROBES       13 \
    CONFIG.C_DATA_DEPTH          2048 \
    CONFIG.C_INPUT_PIPE_STAGES   1 \
    CONFIG.C_EN_STRG_QUAL        1 \
    CONFIG.C_ADV_TRIGGER         false \
    CONFIG.ALL_PROBE_SAME_MU_CNT 2 \
] [get_ips u_ila_0]
# 再逐个设 C_PROBE0_WIDTH ~ C_PROBE12_WIDTH
generate_target all [get_ips u_ila_0]
```

然后在 RTL 里像普通模块一样例化（`project_src\board_top_gui.sv`）：

```systemverilog
u_ila_0 u_ila_0 (
    .clk     (sys_clk_50m),   // 采样时钟 = CPU 时钟
    .probe0  (dbg_have_inst), // 1
    .probe1  (dbg_pc),        // 32
    ...
    .probe12 (dbg_trap_take)  // 1
);
```

这样带来四个好处：

1. **综合/实现/bitstream 全由 `synth_1`、`impl_1` 两个真实 run 完成**，
   GUI 里 Design Runs 有内容、每一步都能双击查看、能右键 Re-run；
2. ILA 出现在 Sources 窗口的 IP 源里，**双击能改深度/位宽**并重新生成；
3. 上板时 Hardware Manager 能**自动匹配** `board_top_gui.ltx` 探针文件，
   不用手工指定；
4. **不再需要"骗综合别删我"的绕法**。之前 13 组调试网络只剩 3 组，是因为
   它们没有负载被优化掉了；现在 ILA 的 probe 端口就是这些信号的**真实负载**，
   综合自然不会删（`board_top.sv` 里的 `(* keep *)` 保留，属于双保险）。

### 3.2 流程全部用工程模式命令

```tcl
create_project -force v9_ila $PROJ -part xc7z020clg484-1
add_files ...                              ;# RTL
add_files -fileset constrs_1 ...           ;# XDC
create_ip ... / generate_target all ...     ;# ILA IP
update_compile_order -fileset sources_1

reset_run synth_1
launch_runs synth_1 -jobs 8
wait_on_run synth_1

launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1
```

同一个 Tcl 脚本里**不允许**再出现 `synth_design` / `place_design` / `route_design`。

### 3.3 一条命令重建

```powershell
& 'D:\vivado\2025.2\Vivado\bin\vivado.bat' -mode batch -notrace `
    -source 'E:/FPGA/v9_vivado_ila/build_project_ila.tcl' `
    -log 'E:/FPGA/v9_vivado_ila/build_project_ila.log' `
    -journal 'E:/FPGA/v9_vivado_ila/build_project_ila.jou'
```

脚本开头的 `set DO_IMPL 0` 可以只跑到综合（约 5 分钟），调试脚本时很有用。

## 5. 上板（Hardware Manager）

1. 板子接 JTAG，`Open Hardware Manager` → `Open Target` → `Auto Connect`；
2. `Program Device` → 选
   `E:\FPGA\v9_vivado_ila\v9_ila\v9_ila.runs\impl_1\board_top_gui.bit`；
3. 探针文件会自动带上（同目录 `board_top_gui.ltx`）；若没带上，
   手工在 `Program Device` 对话框的 `Debug probes file` 里选它；
4. 出现 `hw_ila_1` → `Run Trigger`，把 `probe1`（PC）设为触发条件即可抓波形。

> 注意：`mtval` 那一路 probe（probe11）抓不到有效值，
> 因为 v9 的 `CSR.mtval` 在 RTL 层面从未被写。
> 这是 **RTL 待修项**，不是 ILA 或工程的问题，详见 `上板改造说明.md`。

## 6. 常见坑速查

| 坑 | 现象 | 处理 |
|---|---|---|
| 工程模式 / 非工程模式混用 | Design Runs 全灰 | 只用 `launch_runs`+`wait_on_run`，别用 `synth_design` |
| `target_language` 写 `SystemVerilog` 或 `Mixed` | `ERROR: [Common 17-162] Invalid option value`，脚本静默中断 | 合法值只有 `VHDL` / `Verilog`；`.sv` 靠逐文件 `file_type` 指定 |
| 忘了给 `.sv` 设 `file_type` | 接口/结构体解析错，综合报一堆莫名语法错 | 加文件后逐个 `set_property file_type SystemVerilog` |
| `set_property` 失败没捕获 | 脚本从此静默中断，只留一行 ERROR | 探测性脚本里一律 `catch {...} msg`，把 msg 打出来 |
| ILA 默认 `ALL_PROBE_SAME_MU_CNT=1` | `ERROR: [IP_Flow 19-3458] ... out of the range (2,16)` | 显式设成 `2` |
| `create_ip` 后没 `generate_target` | 综合找不到 `u_ila_0` | 必须 `generate_target all` |
| ILA 采样时钟接了板载 100MHz | 波形看着有、但和 CPU 时钟不同源，触发不准 | 采样时钟用 `sys_clk_50m`（`board_top_ila` 新引出的输出口） |
| 改完 RTL 直接 Re-run Synthesis | 还是老结果 | RTL 变了 Vivado 一般会自动重跑；不放心就 `reset_run synth_1` |
| 打开工程后弹出 `.dcp` 无关文件 | 混淆 | 本版不再往工程里挂外来检查点，全部由 run 产生 |
