## 轮次 3：hold 保护带约束（第一次上板，翻车 → 修好）

**目标**：WHS 0.020 ns 太紧（周期的 0.1%），给 CPU 域补用户保护带。

**翻车（我引入的）**：第一版 `v9_board_ila.xdc` 用
`set ila_xdc_clks [get_clocks -include_generated_clocks sys_clk]` + `foreach` + `puts`
展开派生时钟。综合日志：

```
CRITICAL WARNING: [Designutils 20-1307] Command 'foreach' is not supported ... [:80]
CRITICAL WARNING: [Designutils 20-1307] Command 'foreach' is not supported ... [:87]
CRITICAL WARNING: [Designutils 20-1307] Command 'puts'    is not supported ... [:90]
INFO: [runtcl-6] Synthesis results are not added to the cache due to CRITICAL_WARNING
```

- **循环体整段被跳过** ⇒ `clk_sys_unbuf` 的 `-hold 0.200` 根本没加上（WHS 仍是 0.020）；
- 综合结果不进缓存。
- 根因：**XDC ≠ 通用 Tcl**。XDC 只支持受限命令子集：**不支持** `foreach`/`while`/`if`/`proc`/
  `puts`/`source`/`exec`/`lappend`；`set` 是支持的。

**修法（最终形态，零控制流）**：

```tcl
set ila_unc_clks [get_clocks -quiet -include_generated_clocks {sys_clk clk_sys_unbuf}]
set_clock_uncertainty -setup 0.100 $ila_unc_clks
set_clock_uncertainty -hold  0.200 $ila_unc_clks
```

两个 pattern 一起给 ⇒ 命中集一定至少含 `sys_clk`，不会传空列表（空列表可能直接 ERROR）；
派生时钟改名也不会漏。代价：`puts` 不能用了 ⇒ **验证改成看 WHS 数字**（0.020 → ≈0.20 才算生效）。

**工具修补**：`_diag/chk_xdc.py` 原来只验"Tcl 语法"，是**必要但不充分**的判据。已增加：
- `XDC-LEGAL`：命令首词黑名单 + 行尾 `{` 开块检测 + 白名单拼写告警；
- `ENCODING`：UTF-8 / 无 BOM / 纯 LF / 无 U+FFFD；
- 反向自测：把出问题的那段喂进去，必须报出 4 条（否则"PASS"无意义）。

**② 的更正**：noila 的 `syn/v9.xdc` 那 9 条 `set_false_path -to [get_ports debug_*]` **不能照抄**：
ILA 顶层只有 3 个端口；只补 `set_false_path -to [get_ports debug_dead]`。

**结果（同一天重跑，11:06→11:39，构建成功）**

- XDC 合法：`0 Critical Warnings`（坏构建是 3）；`Designutils 20-1307` 0 次。
- 保护带生效的直接证据：hold 要求的 clock uncertainty 出现 `0.200ns ... + UU`
  （UU = User Uncertainty）；原来那条最差 hold 路径数据延时 **0.342 → 0.445 ns**，
  slack **0.020 → 0.156 ns**（且是在要求严格了 0.165 ns 之后）。

## 轮次 4：v12（A）串口程序引导（UART bootloader）

**动机**：程序原来靠 `IROM_INIT` 在**综合时**固化进 BRAM，改一行程序要重跑 **33 分钟**构建。
这是当时最大的成本项（比任何微架构优化都贵）。

**方案**：UART RX-only 引导（不是 JTAG-to-AXI）。选型的决定性理由是**可仿真** + **零仲裁**
（引导期间 CPU 在复位、IROM 口由 loader 独占）+ UART 本来就是 RTOS console 的必备外设。
完整设计见 `docs/BOOT_UART.md`。

**仿真抓出的两个 bug（都会在"上板后毫无反应"这一层被误判）**

1. IDLE 超时后又回到 IDLE ⇒ 没有 magic 时状态机空转、`busy` 永不落 ⇒ CPU 永久停在复位。
2. IROM 的 `reset` 接成了 `cpu_rst_eff`（含 `boot_busy`），而 `sync_mem` 的写逻辑在
   `if (reset) … else` 的 else 里 ⇒ **引导期间所有写都被丢掉**。表现极具欺骗性：
   `ok=1`（校验和确实算对了）但 IROM 一个字没写进去，CPU 跑全 0 = 非法指令。

**引脚（★ 已订正，上面初版写的 AB6/COM13 是错的）**：
最终用的是板上的 **J8 = PL_RS232** 那个口 —— J8-1 `PL_RS232_RX` = **A16**（FPGA 收）→ `uart_rx`，
J8-2 `PL_RS232_TX` = **A17**（FPGA 发，v12（B）起用）。内部上拉。
串口是 **COM9**（J8 上的 Silicon Labs CP210x），115200 8N1。
`COM13` 是另一个独立的 FTDI 模块，**与板子无关** —— 第一次上板失败就是灌到了 COM13。
接线：J8 插上 USB 线即可，收发都在同一个口；GND 共地。
（原文里"SW0 必须拨到 OFF"这条只适用于 AB6 方案，现在用 J8，不再相关。）

## 轮次 5：v12（B）Zicntr + UART 发送 + 状态字探针（Tier 1）

**动机**：轮次 4 把"改程序"的成本从 33 分钟降到 1 分钟，但**"快了多少"仍然测不出来** ——
`mtime`（0x7C0）是 100 分频的**墙钟**（板上 50MHz → 500kHz），不是拍计数器；
Zicntr 的 `mcycle`/`instret` v9~v11 一直没实现。同时没有 console，
程序唯一的输出手段是往 DRAM 写数再用 ILA 抓。
所以这一轮的目标是**把板子从"能跑"变成"能测"**：先可度量，再谈优化。
完整设计见 `docs/ZICNTR_UART.md`。

**一次性交付四项**

| # | 内容 | 关键判据 |
|---|---|---|
| 1 | Zicntr：`mcycle`/`minstret`（64 位 RW）+ `cycle`/`time`/`instret` 只读影子 | `minstret` 在 8 条 addi 前后**恰好差 9** |
| 2 | UART TX（115200 8N1，MMIO `0x1000_0000`/`+4`） | `sw` 一个字节 → 宿主机 `read_uart.ps1` 收到 |
| 3 | 状态字探针（probe5）+ `mcycle` 探针（probe6） | 16 个探针宽度**一个都没改**，不重建 ILA IP |
| 4 | `trap_seen` 粘滞位 | 抓"第一次陷入"不再靠赌抓包停在那一拍 |

**关键设计决定（都有实证支撑）**

- `minstret` 的计数使能是 **`retire_wb = ready_next & ~lsu_freeze & valid_reg_pipe`**，
  **不是** `WBU_valid`。后者在 DCache 缺失 / MDU 忙期间会连续多拍为 1，
  把一次访存缺失数成 3~4 条指令 —— 这正是历史上"仿真与上板拍数口径对不上"的同类坑。
- 4 个新写位（`csr_wen[14:11]` = mcycle/minstret/mcycleh/minstreth），
  ★★ **别名必须映射到同一个 onehot 位**（`cycle`↔`mcycle` 等）。
  第一版只给本体位，结果 `csrw mcycle,0` 紧跟 `csrr x,cycle` 会**绕过前递**，
  读到的是清零**前**的值（实测 41 而不是 0）。
- UART 放在 `0x1000_0000`：DCache 的 `UNCACHE_MASK` 默认 `0x0FFF_FFFF`，
  地址 ≥ 0x1000_0000 自动走 MMIO（不分配缓存行）。DCache 一行都没改。
- ★★ `dram` 的 `wen` 必须被 `~mmio_uart_sel` 门掉，否则 `sw 0x1000_0000`
  会同时写掉 DRAM 第 0 个字 —— 症状是"打印一个字符，某个变量莫名其妙变了"。

**仿真验证（先仿真再上板，19→27 项全过）**

| 测试台 | 结果 |
|---|---|
| `tb_sys +kind=zicntr`（新） | **PASS**，15 条判据 |
| `tb_uart_tx`（新，回环 tx→rx） | **PASS**，11 条判据；帧长 4341 拍（期望 4340） |
| `tb_board_top_uart`（新，板级端到端） | **PASS**，6 条；收到 'H' 'i'，DRAM[0] 未被覆盖 |
| `tb_boot`（进回归） | **PASS** |
| 全量回归 | **`ALL PASS (27 runs)`** |

★ 7 个程序拍数**一个都没变**（35/42/46/54/77/110/97）—— "加了两个计数器、没动数据通路"的直接证据。

**仿真抓出的 bug（3 个，全部是自造的）**

1. `csr_onehot` 别名没给位 → 计数器清零后读回旧值（见上）。
2. `tb_uart_tx` 在 posedge 驱动激励，与被测模块的 `always_ff` 竞争 → `send` 被吞、
   `busy` 永不起来、测试台死等超时。教训：**激励一律在 negedge 驱动**，`while` 必须带 guard。
3. `regress.ps1` 的 `Run-Vvp` 判定正则只认 `[SYS-SELFCHECK]`/`[EXC-SELFCHECK]`，
   新测试台会落到 `PASS(exit)` —— vvp 正常退出就是 0，**FAIL 会被报成 PASS**。
   已放宽成 `\[[A-Za-z0-9_-]*SELFCHECK\]`，并显式匹配 `tb_boot` 的历史格式。

**新增工具**：`_diag/read_uart.ps1`（宿主机串口终端，`-List`/`-Hex`/`-Seconds`）、
`_diag/an_ila_boot.py` 升级（解状态字 + 用 probe6 算拍数与 IPC + 列名兼容）。

**综合/实现结果**：`RESULT build OK`，**WNS 1.300 ns / WHS 0.006 ns / TNS 0 / THS 0**，
0 Errors / 0 Critical Warnings；LUT 35 620（66.95%）、FF 22 717（21.35%）、
BRAM 38.5（27.5%）、DSP 4。Fmax ≈ 53.5 MHz。
产物 `board_top_gui_boot.bit` 4 045 694 B + `.ltx` 70 007 B。
**上板验证已通过**（16:49）：串口收到 740 组 `Hi`（每轮 8.11 ms，仿真 8.2 ms）；
ILA 抓到 `mcycle` **2047/2047 个差分全为 1**（真板上每拍 +1）；
状态字只有 `0x280` 一个取值（`IDU_ready`+`boot_ok`，**停顿位全 0**），
1024 次写回 / 2048 拍 ⇒ **板上 IPC = 1.00，零停顿**。

## 轮次 6：v12（C）console 收发 + GPIO（+ 两个必须说清楚的否定结论）

**动机**：轮次 5 让板子"能打印"，但只能打不能收 —— console 不算完整；
同时 LED 一直只是心跳灯，软件碰不到。本轮补齐这两件，并顺手验证定时器中断。

**交付**

| # | 内容 | 关键点 |
|---|---|---|
| 1 | 串口**接收**：第二个 `uart_rx` + 8 深 FIFO + `RXDATA/RXSTAT` | 弹出**延迟一拍**（DCache 是"请求拍 + 下一拍采样"两拍契约） |
| 2 | GPIO：`LED` 寄存器 @ `0x1000_0010` → LED1~LED7 | 满时**丢弃并置溢出位**，不覆盖已有数据 |
| 3 | `sim/gen_console_demo.py` → `console_demo.hex` | 横幅 / 回显 / 定时器中断心跳，自带两遍汇编 |

**验证**：`tb_console`（新）6 条判据全过；全量回归 **`ALL PASS (28 runs)`**；
7 个基准程序拍数仍然一个没变（只动了板级）。

**两个否定结论（比代码更重要）**

1. **"load-use 0 拍前递"在本微架构下不成立**。
   DCache 的 `cpu_en/cpu_addr` 取自 **M2**（`LSU.sv:199` 用的是
   `Ex_result_addr_reg_pipe`），数据最早在 M2 出现，而消费者最晚在 M1 就得拿到
   —— 差一拍，物理上没有。要少停 1 拍只能把 DCache 请求前移到 M1，
   那是**重定时工程**（`mem_req_r/resp_valid_r/hold` 全套时序契约），不是加一条前递线。
   顺带查明：`LSU_Rdata`（M1 级数据）与 M1 地址**错位**，
   它接到 `Control.MEM_Rdata` 却**没有读者**（综合报告那条 `has no load` 就是它）。
2. **handler 里 not-taken 分支之后的指令不执行**（可疑，未修）。
   最小复现、已排除项与下一步排查方法见 `docs/CONSOLE_GPIO.md` §6。

**自造的坑（4 个）**

1. 把横幅字符串放在 **IROM** 然后用 `lw` 读 —— IROM 只能取指，`lw` 读到 DRAM 的 0，
   横幅一个字节都不打且不报错。
2. `puts` 本字内右移 4 次后忘了"取下一个字"，只打出 `BigB`。
3. TB 用 `uart_tx` 当激励时 `send` 脉冲**从未被采样**（`[SAMP]` 一行都没有），
   改成 10 行位翻转后立即可用 —— 排查成本远大于省下的代码。
4. `regress.ps1` 里混进了一句中文注释（BOM-less .ps1 在 PS 5.1 下按 GBK 解码），
   已恢复纯 ASCII 不变量。

## 轮次 7：v12-BUG-1 —— 更年轻的 `mret` 吞掉更老分支的误预测（已修）

**来源**：轮次 6 的 console 演示程序里，"每 4 个 tick 打一个点"一个点都没打出来。
当时只如实记录、没有深挖；本轮把它查清并修掉。

**分离手段**：新建 `sim/tb_mini.sv`（最小观察台：只有 CPU + IROM + DRAM 模型，
`+win=<拍>` 可逐拍打印 IFU/IDU/EXU 三级 PC 与全部重定向源）+ `sim/gen_brsel_progs.py`。

| 程序 | 模式 | 修复前 | 修复后 |
|---|---|---|---|
| `brsel_a` | 普通代码 `andi`→`bne`→条件 `addi` | 10 ✓ | 10 ✓ |
| `brsel_b` | 同上 + nop | 10 ✓ | 10 ✓ |
| `brsel_c` | 条件执行的是 `sw` | 10/9 ✓ | 10/9 ✓ |
| `brsel_h` | **同一模式放进定时器中断 handler** | **0** ✗ | **1** ✓ |

⇒ 不是"not-taken 分支"本身的问题，只在**中断上下文**里错。

**根因**（`rtl/Control.sv` 的 `bp_misp_det`）：

```systemverilog
// 修复前
assign bp_misp_det = EXU_ctrl_valid & ~(intr_take | system_redirect | trap_redirect) & ...
```

`system_redirect = mret_flag | ecall_flag | fence_i_flag | trap_redirect`，前三个都是
**IDU（译码级）**的译码标志 —— 属于**更年轻**的指令。放进屏蔽项的效果是：
**更年轻的 mret 把更老分支的误预测吞掉**，于是预测器取的错路径 `mret` 被当成正确路径
执行，中间那条 `addi` 永久跳过。**不报错、不跑飞**，只是"某段条件代码静默不执行"。
（原注释还写"这三个源各自会清掉 EX 级那条指令"，其实 `EXU_inst_clear` 里并没有它们。）

**修复**：屏蔽项只保留真正会抢同一拍 dnpc 的两个源
`~(intr_take | trap_redirect)`。dnpc 优先级链本来就是
`intr_take > trap_redirect > bp_mispredict > system_redirect` ——
"老分支先重定向、mret 之后重新取"是正确语义，优先级早就写对了，
只是屏蔽项把更老的判定提前掐死。

**验证**

- `brsel_h` x6：0 → **1**；
- `console_branchy`（带条件分支的心跳点）：0 个点 → **tick 2/4/6 各一个点**；
- 全量回归 **32/32**（新增 4 条 `brsel_*` 永久回归项）；
- 7 个基准程序拍数**一个都没变**（35/42/46/54/77/110/97）。

★ 不变量（新增）：`bp_misp_det` 的屏蔽项**只能包含"会造成同一拍 dnpc 冲突"的源**；
"更年轻指令产生的重定向"不是冲突，是**优先级问题**，而优先级已由 dnpc 三元链处理。
