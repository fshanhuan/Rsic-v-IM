## 1. 定位

一台**台式数据记录仪 / 简易示波器**：

| 指标 | 目标 |
| --- | --- |
| 模拟输入 | 2 通道，0–1 V（XADC 量程） |
| 采样率 | 连续 100 kSPS/ch；突发 500 kSPS/ch |
| 分辨率 | 12 bit（记录）/ 9 bit（显示） |
| 显示 | HDMI 800×600@60，实时波形 |
| 存储 | SD 卡 CSV |
| 导出 | WIFI232-A / ENET |

### 为什么是 RISC-V + ARM 双核

架构不是"想用双核"推出来的，是从三条物理约束推出来的：

| 约束 | 事实 | 推论 |
| --- | --- | --- |
| ① 采样不能等 | XADC 1 MSPS，DRP 握手延迟不可控 | 采样 FSM 必须是 RTL |
| ② 存储会卡 | SD 卡写一次可能阻塞 100 ms 量级 | 必须有一个**不被阻塞的核**守缓冲 |
| ③ 像素比 CPU 快 | 800×600@60 = 40 Mpx/s，接近 CPU 主频 50 MHz | 像素必须全程 RTL |

约束③直接排除"ARM 渲染"：480 K 像素/帧 × 60 fps = 28.8 MB/s，经 AXI4-Lite
单拍传输（每字约 6 周期）要吃掉 **86% 的 PL 总线带宽**。

## 4. S0：MMIO 索引 4 → 6 位

### 改动

| 文件 | 改动 |
| --- | --- |
| `rtl/soc_map.sv` | 16 个寄存器宏 `4'dN` → `6'dN`；注释记录索引演进史 |
| `board/soc_bus.sv` | `mmio_idx` 位宽 4→6，`addr[5:2]` → `addr[7:2]` |
| `board/board_top.sv` | `bus_mmio_idx` 位宽 4→6 |
| `ip_repo/src/*` | 同步上面三份副本（PS 侧 BD 用） |

### 为什么必须做

4 位索引下 **16 个寄存器（0x00–0x3C）已全部占满**，记录仪要加的
I2C / HDMI / XADC / 列缓冲一个都放不进去。这是所有后续阶段的**前置依赖**。

### 兼容性

- 0x00–0x3C 的 16 个寄存器：编号、语义、读写时序**完全不变**。
- 唯一可观测变化：0x40–0xFF 不再回卷到 0x00–0x3C。
- 副作用（好的那种）：停机 magic 写 `0x1000_00F0` 原本会误写 MTIME
  （idx = 0xF0>>2 & 0xF = 12），现在落到未映射区，隐患消失。
- 新空间：**0x40–0xFC（64 个寄存器）**；0x100 起会回卷。

## 5. S1a：ADV7511 I2C 冒烟测试

### 为什么先做这个

手册第 31 页只写了「ADV7511 做 HDMI 输出」，**没给 I2C 地址**（由 ADDR 脚接法决定，
0x72 / 0x7A 两种都常见），也没给总线拓扑。在写 2000 行 HDMI 时序代码之前，
先用半天回答一个问题：**这颗芯片到底在不在总线上？**

### 设计

三个新模块，全部不接 CPU 总线（S1a 阶段独立于 SoC 运行）：

| 文件 | 作用 |
| --- | --- |
| `board/i2c_master.sv` | 字节级 I2C 原语：`start_req` / `byte_req` / `stop_req` 三个脉冲，各自 `done` |
| `board/i2c_probe.sv` | 扫描 0x70–0x7F → 选最低应答地址 → 读 0x00/0xF5/0xF6 |
| `board/uart_report.sv` | 结果按固定格式周期打到串口 |
| `project_src/board_top_rec.sv` | 顶层：v18 平台 + 探针 + 上报 + IOBUF |

### 为什么不用 Xilinx AXI IIC IP

- IP 要走 AXI/BD，而本设计 PS 是**主**、PL 是**从**，加 AXI 主设备要开
  `S_AXI_HP` 口、改 BD —— 为了读 3 个寄存器不值；
- 自己写 150 行，**iverilog 能直接仿真**（IP 不能）——迭代周期从 30 分钟降到 1 秒。

### 判据

| 寄存器 | 期望值 | 说明 |
| --- | --- | --- |
| 0xF5 | `0x41` ('A') | ADI 固定 ID 字节 |
| 0xF6 | `0x44` ('D') | ADI 固定 ID 字节 |
| 0x00 | `0x13` | 芯片版本 |

**0xF5/0xF6 读到 'A''D' 是不可伪造的证据** —— 只看 0x00 有风险，
好几个 ADI 器件在 0x00 都返回 0x13 附近的值。

### 仿真证据（`sim/tb_i2c.sv`）

自带一个 I2C 从机模型（只应答 0x72，寄存器预置成 ADV7511 的真实值）：

```
=== 场景1：从机在 0x72 ===
  found = 0004   addr_lo = 72   id00 = 13   idf5 = 41   idf6 = 44   rd_ok = 111
[PASS] 扫描只应答 0x72 / any_found=1 / 选到 0x72 / 三个寄存器都读完
[SELFCHECK] status=PASS

=== 场景2：无应答（+noslave）===
[PASS] 无应答时 any_found=0 / 位图全 0 / 不读寄存器 / 仍能收尾
[SELFCHECK] status=PASS
```

仿真过程中抓到并修掉两个真 bug（都记在源码注释里）：

1. **`S_IDLE` 无条件释放 SCL/SDA** → START 一结束 SCL 就被抬回高、SDA 随后释放，
   线上出现一个假 STOP，从机直接回 IDLE。现象是"扫描一个地址都不应答"。
2. **从机在第 9 个上升沿就释放 SDA** → ACK 只维持了半个高电平，
   主机在末尾采样时读到的已经是释放态 → 永远 NACK。
3. （仿真台自身）`3'd8` 被截断成 `3'd0` → `bc < 3'd8` 恒假，从机从不采样数据位。

### 上板证据（第一版）

烧写成功，串口有数据。**结论：0x72 与 0x7A 都没有应答。**

```
[uart] 收到 651 字节 / 6 秒
"2 on=00ad=0i=00 0o=..." （每行 38 字节，周期 200 ms）
```

这份流是"每隔一个字符丢一个"的（见下节 bug），但丢失不影响**保留下来的字符的值**：
`found` 的低半字节和 `found[11:8]` 都落在保留下来的奇数位上，两者都是 `0`
→ 0x72（bit2）与 0x7A（bit10）都没有 ACK。

### 上板暴露的自身 bug（已修）

`uart_report` 把 `tx_send<=1` 和 `idx<=idx+1` 放在同一个 `!tx_busy` 条件下，
而 `uart_tx.busy` 是**下一拍**才起来的 —— 于是下一拍又发一次，被 `uart_tx`
在忙状态下静默丢弃，`idx` 却已加了两格。现象就是"每隔一个字符丢一个"。

修法：每次发送后强制冷却 8 拍（那时 `busy` 一定已经起来），结构上不可能连发。

### 第二版增加的诊断手段

| 手段 | 目的 |
| --- | --- |
| 两根线都改**开漏** | 合规 I2C 电气；让"互换 SCL/SDA"变安全 |
| 拨码 **SW0 = 互换 SCL/SDA** | 排查手册引脚标反 / 板上有丝印反 |
| 线路健康度 `h=xx` | 区分"没上拉/接错"与"总线正常但没人应答" |
| 报告加 `D=x` | 确认拨码实际拨法，避免"以为拨了其实没拨" |

`h` 的编码（高 2 位 SCL，低 2 位 SDA）：

| 值 | 含义 |
| --- | --- |
| 0 | 从没见它高过 → 没上拉 / 没供电 / 接错脚 / 被别的器件按住 |
| 1 | 见过高也见过低 → 总线是活的 |
| 2 | 一直是高 → 从机从没驱动过它（= 没有 ACK） |

判读：`h=22` → 两根线都正常上拉、只是没人应答；`h=02` / `h=20` → 某根线根本没上拉。

报告格式（38 字节，200 ms 周期）：

```
I2C f=0004 a=72 i=134144 o=7 h=22 D=0
```

## 5b. S1b：800×600@60 时序发生 + 彩条

### 为什么是 800×600@60

| 模式 | 像素时钟 | 能否从板上 100 MHz 整数分频 |
| --- | --- | --- |
| 640×480@60 | 25.175 MHz | ✗ 要小数分频 |
| **800×600@60** | **40.000 MHz** | ✓ **MMCM：VCO 100×10=1000，CLKOUT0=1000/25** |
| 1024×768@60 | 65 MHz | ✓ 但帧缓冲/列缓冲要重新算 |
| 1080p60 | 148.5 MHz | ✗ VCO 超范围 |

这是本板唯一"不将就"的分辨率：40.000 MHz 是精确值，不是近似。

### 时序参数（VESA 标准）

| | 有效 | 前沿 | 同步 | 后沿 | 合计 |
| --- | --- | --- | --- | --- | --- |
| H | 800 | 40 | 128 | 88 | **1056** |
| V | 600 | 1 | 4 | 23 | **628** |

帧率 = 40×10⁶ / (1056×628) = **60.32 Hz**（VESA 标称 60）。同步极性负（低有效）。

### 为什么先放彩条

彩条不是"好看"，是**能一眼定位错误**：

| 现象 | 说明 |
| --- | --- |
| 颜色顺序错 | 字节序错 / Cb Cr 反了 |
| 竖条位置偏 | H 时序参数错 |
| 整屏偏色 | 色彩空间或 CSC 配置错 |
| 只有黑白 | 色度通道没接 / 4:2:2 配置错 |

| | 内容 |

| DAC | DAC0832，VREF = **−3.98 V**（−5V × 4.7k/5.9k）进 LM324 反相运放 → 输出 **0~+3.98 V**（码 0x00=0 V，不反相） |
| DAC 引脚 | CS# H17 · WR1# D17 · WR2# F16 · XFER# D16 · BYTE2 E16 · D7..D0 = E15 D15 G15 G16 F18 E18 G17 F17 |
| XADC 通道 | AD11 = A18/A19（J5-9/10，DADDR 0x1B）· AD6 = V13/W13（J5-13/14，DADDR 0x16） |
| XADC 量程 | **0–1 V，超过有损坏风险** |

### 两个设计决定

**1. 不写 XADC 配置寄存器。**
序列器配置（0x48/0x4A/0x4B）写错的后果是"整颗 ADC 不转换、读回永远 0"，
而这一点上板前无法验证。默认配置下 XADC 连续扫描全部通道，
读某通道的 DRP 得到它最近一次转换结果；代价是每通道新数据率
= 1 MSPS / 序列长度 ≈ 59 kSPS —— 对记录仪完全够用。
要更高再单独配序列器，那时有硬件可以量了。

**2. 采样间隔由 RTL 定，CPU 只管按块取。**
`xadc_sampler.sv` 的轮询节拍是硬件固定的，FIFO 在 PL 里。
这是"记录仪时基不抖"的来源：CPU 什么时候来取，都不影响采样间隔。

### 仿真证据（`sim/tb_xadc_sampler.sv`，带 DRP 从机模型）

```
前 6 次 DRP 地址: 16 1b 16 1b 16 1b          PASS（通道严格交替）
FIFO 满 / level=16 / 样本计数                  PASS ×3
读 4 次后 level: 16 -> 12                      PASS
溢出标志置起 / 清后为 0                        PASS ×2
drdy 静音后 den 脉冲数 = 33（看门狗没卡死）     PASS
[SELFCHECK] status=PASS
```

11 项全过。过程中修掉三个自己的错：

1. **两个 always 块抢同一个 `wp`** —— 状态机写指针 + FIFO 块写指针，多驱动。
   改成状态机只产生"该写了"这个组合条件，指针全归 FIFO 块。
2. **溢出永远置不起来** —— `do_wr = st==S_CAP && !full` 之后再判 `do_wr && full`
   恒为假。改成单独的 `wr_ovf = st==S_CAP && full`。
3. **看门狗的判据错了** —— 用"daddr 变化"当活着的证据，但 daddr 只在
   **成功取到样本**时才换通道，而测看门狗时 drdy 是静音的，永远不成功。
   正确的活证据是"den 还在周期性发出"。

## 5d. S3：列摘要 + 扫描渲染（RTL + 仿真部分）

### 规模账（为什么不做帧缓冲）

| 方案 | 存储 | CPU 每帧要写 |
| --- | --- | --- |
| 帧缓冲 800×600×8bpp | 480 KB（超过本片 BRAM） | 480 KB（AXI-Lite 要吃掉 86% 总线） |
| **列摘要 800×{min,max}** | **2 KB** | **2 KB**（每列一个 20 位字） |

扫描时逐像素比较 `y ∈ [min[x], max[x]]` 即可，分辨率无关、带宽为零。

### 设计要点

- **双缓冲（乒乓）**：扫描读 bank A 时 CPU 写 bank B，`frame_tick` 处交换，避免撕裂。
  写口 50 MHz、读口 40 MHz，只有 bank 选择位需要两级同步。
- **渲染优先级**：波形 > 网格 > 背景。
- **色度恒定 128**：波形单色，正好用满 4:2:2 的半个色度带宽。

### 仿真证据（`sim/tb_scope_display.sv`）

```
写 bank 与读 bank 相反                          PASS
波形行 y=100 亮（235）                          PASS
相邻行是背景（16）                              PASS
x=400 是网格线（70）                            PASS
y=250 是网格线（70）                            PASS
波形压过网格（235）                             PASS
[SELFCHECK] status=PASS
```

### 踩的三个坑（都是"差一拍"）

1. **网格用计数器省除法** —— 计数器是寄存的，天然比 px 晚一拍，而列缓冲同步读也晚一拍，
   两者相消后"该用 gx 还是 gx_d"恰好反了，横向网格整整偏一格；纵向那个计数器还写成了
   "每像素加 1"而不是"每行加 1"。**改用直接取模**，40 MHz 下几十个 LUT，一眼就是对的。
2. **`de_o` 只延迟 1 级，`vdata_o` 的数据通路是 2 级** —— 送出去就是"数据和同步差一个像素"。
3. 测试点选在 y=200（正好是网格行）当"背景"，误报了两次 —— 测试点本身要避开网格线。

第 2 条是最典型的：**同步信号与数据必须同深**。这一点在真板上表现为整幅图横向错 1 像素，
很容易被当成"显示器过扫描"而忽略过去。

### 7.5 由此揪出的两个真 bug（仿真永远抓不到）

**bug 1：`SCAN_BASE` 是 7 位地址，不是 8 位**

`i2c_probe` 发地址用的是 `m_tx <= {scan_addr, 1'b0}`。第一版给 HDMI 传
`SCAN_BASE = 7'h70`，本意是"扫 8 位地址 0x70~0x7F"，实际发出的是 `0xE0`，
等于在扫 **7 位 0x70~0x7F**（SMBus 保留 / 10 位地址区）—— 那片区域永远不会有
器件应答。ADV7511 的 7 位地址是 `0x39`（8 位写地址 0x72），落在 `0x38~0x3F`。

修正：HDMI 与音频都用 `SCAN_BASE = 7'h38`。
（ADV7511 = 0x39，ADAU1761 = 0x38~0x3B，恰好都在这一档。）

**bug 2：用按位或拼地址，基址非 16 对齐时会重复扫描**

```verilog
wire [6:0] scan_addr = SCAN_BASE | {3'd0, scan_idx};   // 错
wire [6:0] scan_addr = SCAN_BASE + {3'd0, scan_idx};   // 对
```

`0x38 | 1` 和 `0x38 | 9` 都等于 `0x39`，于是"每个地址扫两遍、位图出现幽灵应答"。
仿真里实测到 `found = 0x0202`（bit1 + bit9）才暴露。
加法则严格保证 bit n ↔ `SCAN_BASE+n`，与 `lowest_addr()` 的语义一致。

修完后仿真仍然：

```
[SELFCHECK] status=PASS   (4/4，+noslave 无器件时正常收尾)
```

### 8.2 两个必须先说的硬件事实

**（1）AD6(V13/W13) 这个通道在本板上用不了**

第一次接进顶层时 place 直接报错：

```
ERROR: [DRC BIVC-1] Conflicting Vcc voltages in bank 35.
  adc_n6 (LVCMOS18, requiring VCCO=1.800)
  adc_n11 (LVCMOS33, requiring VCCO=3.300)
ERROR: [PLCK-87] IO/clock placer failed to collectively place all IOs and clock instances
```

bank 35 在板上是 3.3 V（HDMI 那一堆脚都在这个 bank），而 AD6 这对脚 Vivado
只接受 LVCMOS18 —— 两者不可能同时满足。**结论：自环只能用 AD11(A18/A19)**，
一个通道对 S2 已经够用。改完后 place/route/bitgen 全部 0 Errors。

**（2）DAC 复位值必须是 0xFF，不是 0x00**

DAC 的 VREF 是 **−3.98 V**（手册 §17），经 LM324 反相运放后**两次反相抵消**：
码值 0x00 → **0 V**，码值 0xFF → **+3.98 V**（不反相；早期文档写「反相」是漏了负号）。
而 XADC 的 AD11 只允许 **0~1 V**。如果复位值是 0，上电瞬间输出脚上就有 4 V，
自环线一接上去就可能打坏 XADC。
现在 `dac0832` 和 `rec_mmio` 的复位值都是 **0xFF（≈0 V）**，任何接线顺序都安全。

### 8.6 XADC 决定性自检：转换是好的（2026-11-16 23:25 实测）

AD11 读回 `0x0000` 有两种解释（输入真是 0 V / XADC 根本没转换）。为了不靠"猜"，
加了一个 **JTAG 可写的通道选择位**（VIO `probe_out1` = `int_ch`）：
置 1 时把采样通道换成**片内温度传感器**（DRP 0x00），它不依赖任何外部接线。

| `int_ch` | 采样通道 | `adc_last` 实测 | 结论 |
| --- | --- | --- | --- |
| 0 | AD11 (0x1B) | `0x0000` | 输入确实是 0 V（外面没接线） |
| 1 | 片内温度 (0x00) | **`0xA028`** | **XADC 在正常转换** |

`0xA028` 的解读很关键：XADC 的 DRP 数据是**左对齐**的，12 位结果在 `DO[15:4]`。

```
0xA028 >> 4 = 0xA02 = 2562
2562 × 503.975 / 4096 − 273.15 = 42.0 °C     ← 刚跑完综合的芯片温度，合理
```

★ 这条踩坑要记住：若按"低位"解释会得到 `0x028 = 40` → **−268 °C**，明显荒谬。
所有读 ADC 的软件（`sw/app/adctest.c` 的 `adc12()`）都已经按 `>>4` 处理。
S3 的列摘要如果直接用 FIFO 原始值，也要记得左对齐这件事。

**因此 S2 的结论是：数字链路 + XADC 转换全部实测通过，唯一还缺的是
DAC→AD11 的那根分压线**（以及跑一次 `adctest` 打印扫频表）。

### 8.7 顺带修掉的时序隐患

S2 接进来后 WNS 从 +0.815 掉到 **+0.014**。查 critical path 发现**不是** S2 的逻辑，
而是 CPU 内部 `LSU → DCache tag 分布式 RAM → hit → Control`（布线占 15.5/19.7 ns）。
属于"逻辑没变、位置被挤"的类型。给 `impl_1` 加了

```
STEPS.ROUTE_DESIGN.ARGS.DIRECTIVE = AggressiveExplore
```

| | WNS | WHS | LUT |
| --- | --- | --- | --- |
| 加 S2、默认布线 | +0.014 | +0.015 | 40 717 |
| 换 AggressiveExplore | **+0.540** | +0.014 | 40 759 |
| 再加 int_ch 自检位 | +0.160 | +0.008 | 40 770 |

后两次的差异是布局随机性（+0.540 → +0.160），但都远离 0，不再是一碰就破的临界状态。

## 10. S4：硬件触发单元（已仿真验证）

### 10.1 为什么触发必须做在硬件里

XADC 是 200 kHz 连续采样。软件轮询 MMIO 读样本的间隔是"微秒级不确定"，
一旦错过就补不回来。真实示波器/记录仪的触发必须在**采样节拍上**判定，
软件只负责事后读结果。所以 `board/trigger_unit.sv` 每个样本都判一次，一拍不漏。

### 10.2 语义（与台式示波器一致）

| mode | 含义 | 判据 |
| --- | --- | --- |
| 0 | 上升沿 | `prev < TH && now >= TH` |
| 1 | 下降沿 | `prev >= TH && now < TH` |
| 2 | 任意边沿 | 上两者之一 |
| 3 | 电平 | `now >= TH` 持续有效 |

两个防抖机制：

- `fired` **粘滞**：触发一次置位，直到软件写 `clear` —— 软件可以慢慢处理；
- **holdoff**：一次触发后至少再等 `HOLDOFF` 个样本才允许下一次，
  等价于示波器的 holdoff 旋钮，防止在噪声上连续触发把缓冲冲掉。

### 10.3 仿真结果（`sim/tb_trigger_unit.sv`，**10/10 PASS**）

| 用例 | 结果 |
| --- | --- |
| T1 上升沿（2000→9000） | 1 次，`fired=1` |
| T2 下降沿（A000→3000） | 1 次 |
| T3 任意边沿（两跳变相邻） | 1 次（第二次被 holdoff 吃掉，符合预期） |
| T5 电平 24 个样本 + HOLDOFF=8 | 3 次（第 1/9/17 个样本） |
| T6 clear 后 | `fired=0`、计数归零 |
| T7 禁用时 | 0 次 |
| T8 `last_sample` / `above` | 0x9000 / 1 |

### 10.4 仿真抓出的一个真 bug：holdoff 按"拍"递减

第一版把 `hold_cnt` 的递减写在 `sample_valid` 外面，于是**每个时钟**都减一次。
样本之间隔着好几拍（TB 里是 2~3 拍），holdoff 就被"偷跑"成 1/3：

```
24 个样本、HOLDOFF=8：期望 3 次 → 实测 6 次
```

改成"只在 `sample_valid` 那一拍递减"后为 3 次，与手算的 1/9/17 一致。
**教训**：凡是"以样本/事件为单位"的计数，绝不能在时钟域里按拍递减。

## 11. S3 软件：列摘要主循环（`sw/app/recorder.c`）

### 11.1 分工

| 谁 | 做什么 |
| --- | --- |
| XADC（硬件） | 200 kHz 连续采样，样本进 1024 深 FIFO |
| **CPU（本程序）** | 每帧 800 列，每列取若干样本算 min/max，`0x80 COL_PUSH` 一次写一列 |
| scope_display（硬件） | 双 bank ping-pong，CPU 写一块、扫描读另一块 |

把软件参与次数从"每帧 3333 个样本"降到"每帧 800 次列写"，抖动由硬件 FIFO 吸收。

### 11.2 写代码时算出来的两个真问题

**问题 1：固定"每列 4 个样本"必然让 FIFO 溢出**

```
显示一帧 = 663168 pixclk / 40 MHz   = 16.579 ms  (60.32 Hz)
800 列 x 4 样本 = 3200 个 @200 kHz   = 16.000 ms  (62.5 Hz)
差 3.6% → 每帧净增约 116 个样本 → 1024 深的 FIFO 大约 9 帧就满，
之后开始丢数据（`overflow` 置位），波形每 150 ms 断一次。
```

解决：**按可用量分配**。每帧先读 `ADC_LVL`，把现有样本全部取走并按列平均分
（余数给前几列）。生产多少消费多少，软件自动跟住采样率，不会累积。
上限 `800*8` 防止长期积压后一次抢太多把一帧拖长。

**问题 2：bank 在自己翻转，写一帧的过程中必被翻走**

`scope_display` 现在是**自己**按 `frame_tick` 翻 bank 的。CPU 写满 800 列要
约 16 ms ≈ 一个显示帧，所以写的过程中几乎必然发生一次翻转 —— 转到的那几列
会写进正在被扫描的 bank，屏幕上表现为一条竖直的撕裂。
程序里先加了 `tears` 计数把这件事**量出来**（每 60 帧打印一次）。

正确的修法（下一轮做）：把 bank 翻转改成**由 CPU 提交触发**——
写 `DISP_CTL`（新寄存器）一位 = "这一帧写完了，可以换"，
`scope_display` 在下一次帧同步时再翻。这样两边节奏就锁上了。

## 12. S3 撕裂修复：bank 翻转改成"CPU 提交触发"

### 12.1 问题（第 11 节算出来的）

`scope_display` 原来每帧自己翻 bank。CPU 写满 800 列要约 16 ms ≈ 一个显示帧
（16.58 ms），所以写的过程中几乎必然被翻走一次 —— 那几列写进了正在扫描的 bank，
屏幕上一条竖直撕裂。

### 12.2 改法

新增寄存器 `0xA8 / idx42 DISP_CTL`（WO，写 1 = 提交一帧），`scope_display` 的
`bank_r` 不再自己翻：

```
commit（cpu_clk 单拍） → commit_tgl（电平翻转）
   → 两级同步到 pix_clk → commit_pend
   → 只在 frame_tick && commit_pend 时才翻 bank_r
```

要点：

- 用"电平翻转 + 两次同步 + 边沿还原"过域，而不是直接把单拍脉冲送过去
  （单拍脉冲在 40 MHz 域只有 25 ns，二级同步很容易整个漏掉）；
- `bank_r` 只在一个 `always_ff` 里驱动（第一版把复位写在另一个块里，
  综合会直接报 multiple drivers）；
- 语义上多了一个好性质：**CPU 不提交，画面就冻结在写好的那一块**——
  这正是记录仪"暂停/冻结"需要的效果。

### 12.3 验证

`sim/tb_scope_display.sv` 改成在写完 800 列后打一拍 `commit`，然后重新跑：

```
[PASS] 写 bank 与读 bank 相反   = 1
[PASS] 波形行 y=100 亮         = 235
[PASS] 相邻行是背景             = 16
[PASS] x=400 是网格线           = 70
[PASS] y=250 是网格线           = 70
[PASS] 波形压过网格             = 235
[SELFCHECK] status=PASS          (6/6)
```

软件侧（`sw/app/recorder.c`）每帧 800 列写完后写一次 `0xA8 = 1`，
并把"写列过程中 bank 变了"记为 `tears` 计数，每 60 帧打印一次，便于上板核对。
`recorder.app` 重新编译：2220 B（code 1856 B @0x6000）。

## 13. S1a 下半段：ADV7511 自动配置（`board/adv7511_init.sv`）

### 13.1 为什么做成硬件

ADV7511 必须**在 HPD 变高（显示器接上）之后**才能配置。而"什么时候插显示器"
不可预知 —— 配置若靠软件，用户每插拔一次就得重灌一次程序。
放进硬件后：状态机在 NACK 时自己每 200 ms 重试，**插上就亮**，不用重灌。

### 13.2 结构

```
IDLE → START → ADDR(0x72 写) → REG → VAL → STOP → NEXT → …
地址字节 NACK → 认为器件未上电 → 等 RETRY（10 M 拍 = 200 ms）→ 整表重来
整表写完 → done=1，不再重试
```

配置表 14 项（`{reg,val}`）：

| # | reg | val | 含义 |
| --- | --- | --- | --- |
| 0 | 0x98 | 0x03 | ADI 要求必写 |
| 1 | 0x9A | 0xE0 | ADI 要求必写 |
| 2 | 0x9C | 0x30 | ADI 要求必写 |
| 3 | 0x9D | 0x61 | ADI 要求必写 |
| 4 | 0xA2 | 0xA4 | ADI 要求必写 |
| 5 | 0xA3 | 0xA4 | ADI 要求必写 |
| 6 | 0xAF | 0x04 | ADI 要求必写 |
| 7 | 0x15 | 0x01 | **输入**：YCbCr 4:2:2、16 位、分离同步 |
| 8 | 0x16 | 0x30 | **输出**：RGB 4:4:4 |
| 9 | 0x17 | 0x00 | 宽高比 4:3 |
| 10 | 0x18 | 0x46 | CSC：YCbCr→RGB |
| 11 | 0x3B | 0x00 | — |
| 12 | 0x4C | 0x00 | — |
| 13 | 0x41 | 0x10 | **退出掉电（必须最后）** |

★ 第 7~12 项是视频格式配置，值是按 ADI 参考代码给的，**必须上板用显示器确认**：
若屏幕亮了但颜色不对/没图，先改这几项（软件侧 `i2ctool` 也能单改）。

### 13.3 仿真验证（`sim/tb_adv7511_init.sv`）

从机模型：7 位 0x39 应答、把每次 (reg,val) 记进数组。

| 用例 | 结果 |
| --- | --- |
| 正常：14 项写入顺序与表完全一致、`done=1`、`no_dev=0` | **PASS** |
| `+noslave`：器件不在 → `no_dev=1`、`done=0`、`ack_err>0` | **PASS** |

### 13.4 仿真抓出的 FSM bug：START 没等完成就发地址

第一版 `S_START` 在发出 `m_start` 的同一拍就 `st <= S_ADDR`，于是 `S_ADDR` 抓到的
`m_done` 其实是 **START 那一拍**，而 `m_ack` 还是复位值 0 → 每次都判成"地址 NACK"：

```
现象：ack_err=1、nwr=0、SCL 只动一下（一次下降沿）就再也不动了
```

改成"发出 `m_start` 后等 `m_done` 再进 `S_ADDR`"后，14 项一次写通。
**教训**：一个"请求/完成"握手，请求发出后必须**等到完成**才能推进状态，
否则会把自己发出的请求的完成信号当成下一步的结果。
### 13.5 上板实测：重试机制在真硬件上按 200 ms 节拍运行（2026-11-17 03:06）

烧写后从 VIO 读（56 个输入探针）：

| 探针 | 采样1 | 采样2（+0.5 s） | 含义 |
| --- | --- | --- | --- |
| `init_no_dev` | 1 | 1 | 没有器件应答（没插显示器，符合预期） |
| `init_done` | 0 | 0 | 未完成配置 |
| `init_ack_err` | **303** | **306** | **0.5 s 内 +3 次** —— 正好是 200 ms 重试一次 |
| `m_frame_clk` | 663168 | 663168 | HDMI 时序无回归 |

`ack_err` 每 200 ms 加 1（0.5 s / 0.2 s ≈ 2~3 次），**与设计值完全一致**。
这说明整条"地址→NACK→等 RETRY→整表重来"的链路在真芯片上是对的。

**因此：显示器插上的那一瞬间，ADV7511 一旦应答，配置表就会自动写完，
屏幕应当直接出图 —— 不需要重新综合、不需要灌程序、不需要断电。**

## 14. 时序余量：从 +0.045 拉回 +0.479（2026-11-17 03:50）

### 14.1 问题

同一份 RTL 连续几版的 WNS 是 **+0.836 / +0.566 / +0.320 / +0.045**，摆幅近 0.8 ns。
查 critical path 每次都指向同一条：

```
u_cpu/LSU_Inst0/Ex_result_addr_reg_pipe_reg[*]_replica
  → DCache tag 分布式 RAM (RAMD64E) → hit → Control.MEM_m1_ok → EXU.iaddr_misalign
数据路径 19.7 ns，其中布线 15.5 ns（79%）、逻辑只有 4.2 ns（22 级 22 个 logic level）
```

也就是说：**逻辑没变，位置在飘**。而且这条寄存器上本来就有
`(* max_fanout = 8 *)`（`rtl/LSU.sv:134`），说明之前已经有人调过扇出。

### 20.2 失败原因：一个真实的跨时钟域（CDC）错误

集成后的构树报：

```
CRITICAL WARNING: [Timing 38-282] The design failed to meet the timing requirements.
Slack (VIOLATED) : -0.896ns
  Source:      u_disp/text_mem_reg_0_63_0_2/RAMA/CLK     (clk_sys_unbuf, 20 ns)
  Destination: u_disp/vdata_o_reg[12]/R                  (clk_pix_unbuf, 25 ns)
  Requirement: 5.000ns   Data Path Delay: 4.985ns
```

**这是我自己写错的地方**：文本 RAM 的写口在 `cpu_clk`（50 MHz），而我把它的读口
做成了**组合读**、直接进 pix 域的 `vdata_o` 寄存器。Vivado 把这块 64×5 阵列实现成
带同步输出的分布式 RAM（时钟用写时钟），于是这条路径变成 **cpu_clk → pix_clk 的
跨时钟路径**，只有 5 ns 预算，差 0.896 ns。

★ 教训：**任何跨时钟域的数据，都不能指望"组合读 + 目标域直接寄存"能过时序**。
慢变数据也要么用 2 级同步器 + `set_max_delay -datapath_only` 明确约束，
要么老老实实用异步 FIFO 把数据搬到目标时钟域。

### 20.3 已采取的动作

1. 叠加层从 `scope_display` 撤出（端口、RAM、输出选择全部回退），
   已用 `xvlog` 确认恢复成单行 `vdata_o <= de_d ? {y_out, 8'd128} : 16'h0000;`；
2. 用新写的 `_diag/program_bit.tcl`（可直接指定 bit/ltx）回退到

3. 回退后上板复测：`m_frame_clk=663168`、`m_frame_lines=628`、两个 MMCM 锁定、
   温度测量仍在工作（min 0xA0C8 / max 0xA1E4 / mean 0xA15A ≈ 44.5 °C）。

### 20.4 正确的下一步（留给后续）

把文本缓冲**搬进 pix 域**，而不是把 cpu 域的 RAM 直接读出来：

```
软件写 0xCC  →  cpu_clk 侧的 11 位（{addr[5:0], data[4:0]}）
              →  异步 FIFO（深度 4，指针用格雷码）
              →  pix_clk 侧写入 text_mem（此时 RAM 完全在 pix 域，无 CDC）
```

这样 RAM 的读口和写口都在 pix_clk，路径变 25 ns 预算，问题从根上消失。
现在的 `0xCC TEXT_PUT` 寄存器已经定义好（`rtl/soc_map.sv`），`font5x7.sv` 也验证过了，
接上这段 FIFO 就能用。

## 21. S6 文本层（二）：用异步 FIFO 修掉 CDC，集成成功

### 21.1 修法

第 20 节失败的原因是"cpu 域的 RAM 被 pix 域组合读"。这一次让 **RAM 完全待在 pix 域**：

```
软件写 0xCC（{addr[5:0], data[4:0]}, cpu_clk 域）
   → async_fifo（深度 8，格雷码指针 + 两级同步）
   → pix_clk 域写 text_mem[64x5]
   → 组合读 → 字模 → 叠加到 vdata
```

FIFO 读侧每拍都在吞（40 MHz，25 ns），写侧最快也只有软件写 MMIO 的速率
（约 100 ns 一次），所以**永远不会满**；满了也只是少一个字符。

### 21.2 验证

**① 异步 FIFO 单元测试**（`sim/tb_async_fifo.sv`）：50 MHz 写 / 40 MHz 读，
灌 20 个已知数据，**22 项断言全 PASS**——顺序完全一致、不丢、不重、读完为空。

> 这个 TB 一开始是 FAIL 的，原因在 TB 自己：把 `rpop` 写成了寄存器（`rpop <= 1`），
> pop 比记录晚一拍，同一份数据被记了两次（256,256,257,257…），看起来像"FIFO 重复出数"。
> 改成组合 pop（`assign rpop = !rempty`），才能和 `rdata` 同拍。

**② 叠加层像素级验证**（集成前）：写字模索引 1（'0'）到面板左上角，
按屏幕坐标采回整块 ASCII 图正是带斜杠的 0，第 2 行空格整行面板底色，
面板边界 x16..271 / y16..31 精确落位 —— **7/7 像素断言 PASS**。

**③ 集成后时序**：

| 版本 | 最差路径 | WNS | 结果 |
| --- | --- | --- | --- |
| 第 20 节（组合读） | `text_mem`(cpu) → `vdata_o`(pix) | **−0.896** | ❌ 失败 |

## 22. S6 文本层收尾：面板上电清零 + 软件绘制 + 时序收敛

### 22.1 面板上电清零

`text_mem` 在 FPGA 里是未定义初值，上电会显示随机字模。加复位清零：

```systemverilog

```

### 22.2 软件绘制（`sw/app/recorder.c`）

每 8 帧刷一次面板（够用，且省 MMIO 带宽）：

```
行 0:  VPP  0.mmm      ← (max-min) 换算成 mV
行 1:  MEAN 0.mmm      ← 均值换算成 mV
```

换算：`mV = code12 * 1000 / 4096`（code12 = 原始值 >>4，用 64 位乘避免溢出）。
`recorder.app` 重新编译：**2616 B**（code 2252 B @0x6000）。

### 22.3 时序收敛：directive 选择的实测对比

这一轮为了同一个设计试了三种布线策略，结果差别巨大，值得记下来：

| route directive | 结果 | 耗时 |
| --- | --- | --- |
| `AggressiveExplore` | 卡在 Phase 5.1 跑了 **3h45m** 仍未收敛（还剩 8 个冲突） | ❌ 不可用 |
| `Default` | 完成，但 **WNS −0.173**（失败在 FIFO RAM 的假 CDC 路径） | ~25 min |
| `Explore` | 完成，**WNS +0.554 / WHS +0.009 / LUT 42 389** | ~45 min |

另外加了 `set_clock_groups -asynchronous`（clk_sys / clk_pix）。这不是掩盖问题：
两处跨时钟通路在 RTL 里都已经同步过（异步 FIFO 格雷码指针 + 两级同步器；
commit 用"翻转电平 + 两级同步 + 边沿还原"），XDC 里逐条写明了理由和注意事项。

**结论**：大改之后先用 `Default` 快速验证功能，再用 `Explore` 收时序；
`AggressiveExplore` 在这种利用率（约 42k LUT + 调试核）下代价不成比例。

## 23. 上电即跑：把记录仪主循环固化进比特流（绕开 J8）

### 23.1 问题：J8 串口一直没枚举出来

记录仪的全部功能（列摘要、测量面板）都是 `sw/app/recorder.c` 在 RV32 上跑出来的，
而这个程序原来只能**经串口**灌进去：`monitor` shell 收 `L` 帧写 DRAM、`sa` 存文件系统、
`run recorder` 跳 0x6000。实测卡在这里：

| 项 | 实测 |
| --- | --- |
| PS 串口（COM13，FTDI `1234-TUL`） | 正常，是 **Zynq PS** 的 UART1，和 RV32 无关 |
| PL 串口（J8，CP2103 `VID_10C4`） | **从未枚举**：`GetPortNames()` 只有 COM13 + 6 个蓝牙口；`Win32_PnPEntity` 里没有任何 10C4 设备 |
| 换 USB 线 / 换 J8 另一个口 | 无改善 |

也就是说：**软件栈完好、硬件通道不通**。这不是写代码能修的。

### 23.2 做法：镜像进 BRAM 初值

`board_top` 原来只能固化 IROM（`IROM_INIT`，`$readmemh` 进 BRAM 初值），DRAM 初值写死是
空字符串。加一个对称的参数就够了：

```systemverilog
parameter DRAM_INIT = "",    // "" = v18 行为逐位不变
```

两个 DRAM 实现（`g_dram_single` 的 `sync_mem`、`g_dram_axil` 的 `dram_shared`）都接
`.INIT_FILE (DRAM_INIT)`。`board_top_rec` 里把默认值改成：

```systemverilog
parameter IROM_INIT = "boot_rec.hex",         // 代码，0x0 起
parameter DRAM_INIT = "boot_rec_dram.hex",    // .rodata，0x1_0000 起
```

为什么这样就够了：`IROM_BOOT=1` 的引导器有 **500 ms** 的串口窗口（`IDLE_TMO_MS=500`），
窗口超时后 `busy` 撤掉、CPU 从 0 开始执行 IROM 里的固化镜像。所以
**没有串口也能跑**；串口要是通了，反而可以随时把别的镜像灌进来覆盖固化镜像
（引导优先），灵活性一点没丢。

镜像怎么来（两步，都可脚本化）：

```bash
# 1) 把 recorder.c 当"独立程序"编在 0x0（不是 0x6000 的 shell 应用）
bash sw/build_simple.sh sw/app/recorder.c recboot
# 2) 合成全量初值文件（IROM 16384 字 / DRAM 32768 字）
python tools/mk_boot_image.py
```

`recboot` 的尺寸：`.text 2568 B`、`.rodata 84 字`、`bss 0` —— 占 IROM 的 1.6%、
DRAM 的 0.25%，固化成本可以忽略。

### 23.3 为什么 DRAM 要写**全量** 32768 行

`$readmemh` 没碰到的元素在仿真里是 X、在综合里是"未指定"。板上 BRAM 上电是 0，但那是
**器件特性**，不是设计保证。全量文件把"其余全是 0"写进比特流，仿真和硬件就完全一致，
出问题时不用再猜某一块到底是 0 还是 X。代价是 295 KB 文本 + 约 128 KB 比特流。

### 23.4 三道自检（每一道都对应一个真实踩过的坑）

| 自检 | 位置 | 守什么 |
| --- | --- | --- |
| 文件级 10 项 | `sim/tb_boot_image.sv`（已进回归） | 行数 / 逐字回读 / 入口字 / DRAM 基址 / 非零字数 / 不许压 ramdisk |
| 网表级 | `build_project_rec.tcl` §4b | 实现后直接读 BRAM 的 `INIT_00`：IROM 第 0 字必须是 `0x00011197`、DRAM 第 0x4000 字必须是 `0x6D617266`。**没进网表就报 FAIL** |

为什么要在实现后查 BRAM 属性：`$readmemh` 找不到文件时 Vivado 只给一条**警告**，
BRAM 初值全是 0，上板表现是"CPU 停在 0x0"，和"程序写错"完全分不清。

`_diag/read_vio.tcl` 拿到了完整证据。

### 24.2 但是采样停了：`adc_cnt` 卡在 1024

同一份数据里有两处不对：

| 探针 | 读数 | 期望 | 说明 |
| --- | --- | --- | --- |
| `adc_cnt` | **1024**（两次相同） | 持续增长 | 1024 正好等于 FIFO 深度 |
| `meas_cnt` | **978**（两次相同） | 每秒增长约 195 | 窗口计数冻结 |
| `adc_level` | 0 | 0~1023 波动 | FIFO 一直是空的 |

### 24.3 根因：写"弹出"把采样使能清掉了

`ADC_CTL`（idx38）的位定义是 `bit0 en / bit1 clr_ovf / bit2 pop`，RTL 原来是这样写的：

```systemverilog
6'd38: begin
    adc_en_r      <= wdata[0];   // ← 每一次写都会改 en
    adc_clr_ovf_r <= wdata[1];
    adc_rd_en_r   <= wdata[2];
end
```

而软件为了"弹出 1 个样本"写的是 `4`（只有 bit2）→ **bit0 = 0 → en 被清零**。
于是：第一个样本弹完，采样器就永久停了。软件毫无察觉，继续读一个空 FIFO，
800 列全用 `ADC_LAST`（=0）顶替，屏幕上只会是一条贴底的平线。

`adc_cnt` 停在 **1024** 正好是这个 bug 的指纹：引导窗口 500 ms 里 FIFO 被灌满
（`sample_cnt` 只在**成功写入**时加一，满了就不再增加），之后再也没有新样本进来。

### 24.4 修法（两层都改，任一层单独也能活）

1. **RTL**（根治）：`pop` 不许改 `en`，只有"不含 bit2 的写"才改。

```systemverilog
if (!wdata[2]) adc_en_r <= wdata[0];
adc_clr_ovf_r <= wdata[1];
adc_rd_en_r   <= wdata[2];      // 单拍选通，下一拍自清
```

2. **软件**（防御）：弹出写 `5`（en+pop），清溢出写 `3`（en+clr_ovf）——
   这样即使跑到老位流上也不会把 `en` 清掉。

### 24.5 顺手修掉的第二个问题：主循环没等帧

原来主循环里**没有任何等待**，只受 MMIO 延迟限制，实测约 **2500 次/秒**，
而显示只有 60 Hz：

| 现象 | 原因 |
| --- | --- |
| 98% 的 `DISP_CTL` 提交被下一次覆盖 | 提交频率是刷新率的 40 倍 |
| 每一轮只取到约 80 个真实样本 | `avail` 只有约 80，`per = avail/800 = 0`，只有前 `rem` 列有真样本 |
| 其余 720 列全是 `ADC_LAST` | 上面那条的直接后果 |

修法：提交之后**等 bank 真的翻过去**（`R_DISP_ST` 的 bit0 变化）再进下一轮，
主循环自然锁到 60 Hz。这样每帧拿到 1024 个样本：800 列各 1 个、前 224 列各 2 个，
**列列都是真实采样值**。

带宽账（如实记录）：200 kHz × 16.58 ms ≈ **3316 个样本/帧**，而 FIFO 只有 1024 深，
所以每帧约 **2/3 的样本会被硬件丢弃**（`ovf` 每帧置位）。这是 FIFO 深度决定的，
不是软件丢的。要一个都不丢只有两条路：加深 FIFO，或把采样率降到约 60 kHz。

### 24.6 一个自己挖的坑：网表级自检误报 FAIL

第一次构建后，`build_project_rec.tcl` 的自检打印：

一个字的 4 个字节被摊到 4 个 BRAM 上，`INIT_00` 里当然找不到完整的 `0x00011197`，

## 25. 排空率异常：仿真台把范围缩小到"DCache 之后"（2026-11-17 18:50）

### 25.1 为什么要写仿真台

板上 60 个只读探针、每次采样 150 ms，看到的是"FIFO 一直是满、每帧只弹出 0~1 个样本"
这种**结果**，但排空逻辑发生在微秒级，靠 JTAG 采样永远看不到过程。所以按 §24.7 的计划
写了 `sim/tb_recorder.sv`：

| 组成 | 说明 |
| --- | --- |
| `board_top(IROM_BOOT=0, EXT_MMIO=1)` | 真 CPU/总线/中断，IROM/DRAM 用**烧进比特流的同一份镜像** |
| `rec_mmio` | 真 MMIO 译码（`ADC_CTL` 的 pop 就在这里） |
| `xadc_sampler` + **假 DRP** | 真 200 kHz 轮询与 FIFO 逻辑；不用 XADC 原语（iverilog 跑不了），用一个"den 后一拍给 drdy"的假源 |
| 显示桩 | `disp_commit` 后下一次帧边沿翻 bank；帧周期参数化（默认 2 ms，只为缩短仿真） |

### 25.2 定位过程（每步都有证据）

| 步骤 | 观察 | 排除掉的可能 |
| --- | --- | --- |
| ① 列循环有没有跑满 | `COL_PUSH` **800 次/帧**，一列不少 | 不是"循环没跑"或"提交没生效" |
| ② 弹出有没有发出去 | `pop` 只有 0.5 次/帧 | 内层 `for k` 循环几乎不进 |

```
[WIN 3] hold=0  LSU.rdata=0x00000000  LSU.rdata_reg2=0x00000000  perip_rdata=0x00000000  pc=0x2d0
```

- **正确的 1024（0x400）确实进过 `rdata_reg2`**，但只停了一拍；

所以一直"看起来对"；记录仪连续读**不同**寄存器就必然踩到。

```c
static unsigned int rd_mmio(volatile unsigned int *p)
{
    (void)*p;      /* 空读：只为把地址送进总线 */
    return *p;     /* 实读：此时总线给的就是这个地址的数据 */
}
```

本文件用到的读口（33/35/36/37/41/47..50）全部**只读、无副作用**，多读一次不改变任何
硬件状态，所以这个绕法是安全的。

## 26. 根治：DCache 不可缓存读"响应提前有效"（2026-11-17 20:00）

### 26.1 根因（逐拍证据在 §25.7）

`DCache` 判断"这笔 load 的数据到了"用的是：

```systemverilog
assign resp_for_now = (mem_data_vld & (cpu_index_r == index) & (cpu_tag_r == tag_in)
                       & (rd_addr_r == cpu_addr_r))
                    | (uncacheable & unc_busy & req_same & (rd_addr_r == cpu_addr_r));
```

第二项（不可缓存）里的 `cpu_addr_r / req_same / rd_addr_r` 描述的是**上一笔已寄存的请求**。
当 LSU 已经给出**下一笔**地址（`cpu_addr` 变了、`cpu_addr_r` 还是旧的）时，这一项**仍然成立**
—— 于是"上一笔的返回"被当成"当前这笔也好了"，`hold` 被提前撤掉，LSU 把当拍总线上的残留值
锁进 `rdata_reg2`。逐拍实测：

```
请求 0x1000_0094 的那一拍：hold=0
同一拍 LSU.rdata_reg2 里是上一笔 0x84 的 0/1（正确值 0x400 只在中间停了一拍就被覆盖）
```

`monitor` 那种"同地址轮询"每拍读同一个地址，错位也读到同一个寄存器的值，所以十几年没暴露。

### 26.2 修法（一行）

给不可缓存那一项再加 `cpu_addr == rd_addr_r`：**只有"当前地址 == 那次读的地址"才算这笔的返回**。

```systemverilog
| (uncacheable & unc_busy & req_same & (rd_addr_r == cpu_addr_r)
   & (cpu_addr == rd_addr_r));
```

安全性：粘滞等待期间 LSU 被 `hold` 冻住、`cpu_addr` 不动，必然等于 `rd_addr_r`，
所以不会出现注释里担心的"重发被禁 → 永远等不到响应"的自锁。

### 26.3 验证一：软件**单读**就能读对了

为了证明"是 RTL 修好了"而不是"软件连读两次蒙对了"，做了一份**单读版**镜像
（`_diag/build_single.sh`，`-DREC_SINGLE_READ` 让 `rd_mmio` 只读一次），

## 27. 自动量程（vertical auto-range）：让小幅信号也能看清（2026-11-17 21:00）

### 27.1 为什么需要

纵轴有 1024 行，而 AD11 量程 0~1 V（12 位 → 4096 码）。固定量程下：

| 输入幅度 | 占屏高度 | 实际问题 |
| --- | --- | --- |
| 1 V（满量程） | 100% | 正常 |
| 100 mV | 10% | 能看出形状，但很扁 |
| 片内温度噪声 ≈ 2.6 °C ≈ **21 个码** | **2%** | 基本就是一条直线，"看不出在测东西" |

而记录仪最常测的恰恰是小幅信号。所以必须有自动量程 —— 这不仅是"好看"，
**没有它就没法证明"这条线上真的有信号"**。

### 27.2 做法

用硬件测量窗（`meas_unit`，每 1024 个样本更新）给出的 `meas_min/meas_max`
当"当前信号范围"，**每 8 帧（≈7.5 Hz）**更新一次纵轴窗口：

```
窗口 = [min - pad, max + pad]，pad = (max-min)/8      ← 上下各留 12.5%
y    = (code - lo) * 1023 / span                       ← 线性映射到 0..1023
```

三个护栏：

1. `span` 下限 **8 个码** —— 信号恒定时 `span=0` 会除零；纯噪声也不会被放大成满屏雪花；
2. 窗口不超出量程（`span ≤ 4096`）；
3. **面板上的 VPP/MEAN 仍然是真实物理量（mV），自动量程只改显示坐标** ——
   不为好看去动测量值。

### 27.3 仿真量化验证（`sim/tb_recorder.sv`）

仿真台加了**真的 `meas_unit`**（以前把它接 0，所以自动量程拿不到 min/max），
假 DRP 改成"小幅方波"（12 位码 384↔416，摆幅 32 码 = 满量程的 3.1%）。

| | 12 位码范围 | 打到屏上的行范围 | 占屏 |
| --- | --- | --- | --- |
| 自动量程关闭（第 0 帧，默认 `lo=0/span=1024`） | 384..416 | **383..415** | **3%** |
| 自动量程生效（第 1 帧起） | 384..416 | **102..920** | **80%** |

放大 **25 倍**，且数字与设计公式完全对上：`pad = 32/8 = 4` → 窗口 380..420（span 40）→
`code 384 → (4×1023)/40 = 102`、`code 416 → (36×1023)/40 = 920` ✓。

另外用"摆幅只有 2 个码"的病态输入验证了 `span` 下限：结果稳定在 511..767
（256 行），既没除零也没满屏雪花 ✓。

### 27.4 一个自己踩的坑（记下来）

第一版把假信号做成"连续锯齿"（5 ms 扫完 4096 码）。自动量程按 8 帧更新窗口，
而锯齿在一个窗口周期内已经跑过整个量程 —— 于是所有样本都落在窗口外，全部画成 1023。
**诊断结论不是"自动量程坏了"，而是"测试信号对自动量程是病态的"**：真实示波器信号
不会每 5 ms 扫一遍满量程。换成小幅方波后一次就测通了。这条值得记：验证一个功能时，
**测试信号必须在功能的假设范围内**，否则会把"测试设计错误"误判成"实现错误"。

### 27.5 上板验证（位流 `S6_autorange`，WNS +0.255 / WHS +0.005 / LUT 41 602）

只换了固化的软件镜像，RTL 一字未改（所以时序与 `S6_mmiofix` 完全相同）。
VIO 连采 4 次（内部温度通道）：

| 探针 | 采样值 | 判定 |
| --- | --- | --- |
| `d_wb_pc` | 0x3A8 / **0x408** / **0x400** / **0x408** | ✅ 落在**新加的自动量程/映射代码**里（旧版是 0x3B8~0x3C8） |

## 28. 把记录仪契约台子放进全量回归（2026-11-17 23:10）

### 28.1 为什么

之前 `sim/tb_recorder.sv` 只打印观察值、没有判据 —— 放进回归也只会被兜底判成
`PASS(exit)`，等于没测。这轮给它 6 条硬判据，让它变成**回归门**：

| 判据 | 内容 | 钉住哪个历史 bug |
| --- | --- | --- |
| **D1** | 每帧 `COL_PUSH` 正好 **800** | 列循环没跑满 / 提交丢列 |
| **D2** | 第 0 帧 pop ≥ **1000**（一次排空积压） | 排空完全没发生 |
| **D3** | 之后每帧 pop ∈ [300,500]（≈400 = 该帧到达量） | `ADC_CTL` 的 pop 清掉 en；DCache 不可缓存读错位 |
| **D4** | **`adc_cnt == pops_eff + adc_level`**（守恒式，每帧严格成立） | FIFO 计数错 / pop 打空 / 写入丢失 |
| **D5** | 第 1 帧起列展宽 ≥ **400 行** | 自动量程没生效 |
| **D6** | `col_col` ∈ 0..799 | 程序跑飞 |

**D4 值得单独说**：一开始写成"每帧 `adc_cnt` 增量 == pop 增量"，结果第 0/1/2 帧报 FAIL
—— 但那是**采样窗口与帧边沿不对齐**造成的（差几十个），不是 bug。改成
`writes = pops_eff + level` 这个**任何时刻都严格成立的守恒式**之后，一次通过。
教训：**判据要写成不变量（invariant），不要写成近似等式**。

### 28.2 结果

```
[RECORDER] status=PASS (6 判据 x 6 帧)
```

回归项从 **54 → 55**。它跑的是**烧进比特流的同一份镜像**（`project_src/boot_rec.hex`），
所以以后任何改动只要破坏"软件↔ADC/显示"的契约，这条就会红。

代价：约 5 分钟（慢在等软件横幅 121 字节 @115200）。相对它守住的三个真 bug，值得。

## 29. S1a 的补充证据：I2C 主控在**真硅**上验证通过（2026-11-17 21:50）

### 29.1 为什么补这一条

S1a 一直写着"HDMI 总线上没有 ACK"。这个描述容易被误读成"我们的 I2C 主控有问题"。
实际上整机里有**两条独立**的 I2C 总线（HDMI 一路、音频一路），而音频那一路是**有真器件**的。

VIO 实测（位流 `S6_autorange`）：

| 探针 | 读数 | 含义 |
| --- | --- | --- |
| `f_a` | **0x0009** | 音频总线上 **位 0 与位 3 对应的地址有 ACK** |
| `addr_a` | **0x38** | 最低那个 ACK 地址是 7 位 `0x38` |
| `id00_a` / `idf5_a` / `idf6_a` | 0x00 / 0x00 / 0x00 | 寄存器 0x00/0xF5/0xF6 读回了**确定值**（不是总线浮空的 0xFF） |
| `f_h` | **0x0000** | HDMI 总线：0x38~0x3F **全无 ACK** |
| `addr_h` | 0x00 | — |
| `line_health` | 0x55 | 四条线（两路 SCL/SDA）都到过高、低电平 |

### 29.2 结论怎么用

- **音频总线的 ACK + 真实寄存器读值 ⇒ I2C 主控的物理层与协议层都正确**
  （开漏驱动、START/STOP、地址+读写位、ACK 采样、字节收发全都走通了）。
- 所以 HDMI 总线上的"全无 ACK"只在两种可能里选：
  1. ADV7511 没有上电（**HPD 为低就不上电**，这是该器件的已知行为；没插显示器正是这种情况）；
  2. 板子上的 HDMI I2C 走线与我们的引脚定义不符（例如 SCL/SDA 反了 —— RTL 里其实留了
     一个 `sw[0]` 交换开关，但那是物理拨码，远程改不了）。
- 两者的判据不同，插上显示器后一次就能分开：`f_h` 从 0 变成非 0 ⇒ 是 1，问题解决；
  仍然 0 ⇒ 再拨 `SW0` 试交换。

### 29.3 这条为什么值得单独写

**"我们的东西坏了"和"对方不在"必须分开证明。** 只报"没有 ACK"，读者无法判断是我们的
bug 还是环境问题；而同一份 IP 在另一条总线上跟真器件通了，就把责任范围一刀切干净了。
这也是本次项目里反复用到的方法：**先找一个已知正确的对照，再判断可疑的那一路**。

## 30. S5 前置打通：ARM(A9) 裸机执行通路，不用编译器（2026-11-18 00:20）

### 30.1 为什么先做这一步

S5（ARM 排空 + SD/CSV）一直卡在"没有 ARM 工具链"上，向用户确认过两次没有回音。
与其继续等，先把**"ARM 到底能不能被我们驱动"**证实掉：这一步不需要编译器，
只需要 Vivado 自带的 `xsdb`。结论是**能**，而且全程有实测数据。

### 30.2 通路与实测链

工具：`D:\vivado\2025.2\Vivado\bin\xsdb.bat`（Vivado 2025.2 自带，不是 Vitis）。
脚本：`tools/ps/jtag_probe.tcl`、`tools/ps/arm_exec.tcl`。

| JTAG 目标 | IDCODE / 说明 |
| --- | --- |
| `Xilinx TUL1` | `1234-tulA`，板载 FTDI 下载线 |
| `arm_dap` | idcode `4ba00477`，irlen 4 —— ARM 调试口 |
| `xc7z020` | idcode `23727093`，irlen 6 —— FPGA |
| `APU` | 下挂 `Cortex-A9 #0`、`#1`，均为 Running |

复位后两核停在 BootROM 的等待循环：PC = `0xFFFFFF28` / `0xFFFFFF34`，
**该处指令字实测为 `0xEAFFFFFC`（`B .`，自己跳自己）**，CPSR = `0x200001DF`（ARM 态、I/F 屏蔽）。

### 30.3 三个必须知道的坑（本轮全部踩过并定位）

1. **内存访问必须选中具体的 A9 核目标。** 选 `APU*` 这个"组"目标时，`mrd` 对任何地址都
   "成功"返回 `0x00000000`（不报错）——我第一版就是这么被误导的，误以为 PS 没起来。
   判据：读 PC 所在地址 `0xFFFFFF28`，能读出 `0xEAFFFFFC` 才算通路正常。
2. **`mwr` 的值必须是 Tcl 数字字面量。** 传字符串 `"0xE3051000"` 会静默失败（`mwr` 报错被
   `catch` 吞掉），表现为"代码没写进去"而看起来像"CPU 执行失败"。所以装载后必须**回读校验代码字**。
3. **`rst -processor` 之后 DAP 会不可枚举**（`AHB AP transaction error, DAP status 0x30000021`），
   用 `rst -dap` 可恢复；`rst -por` / `rst -srst` 在本线缆上不支持（会报 "not supported for target"）。

### 30.4 实测一：手写机器码，A9 真的执行了

14 条 ARM/A32 指令（`MOVW/MOVT/STR/LDR/ADD/B`）手工编码后写到 OCM `0xFFFF4000`，
再 `rwr pc` 跳过去（`_diag/arm_exec.tcl`）：

| 检查项 | 期望 | 实测 |
| --- | --- | --- |
| 代码字回读（14 字） | 逐字一致 | **14/14 一致** |
| PC 轨迹 | `0xFFFF4000` → `0xFFFF4034`（落进 `B .`） | **一致** |
| `[0xFFFF5000]` | `0xA55A1234` | **`0xA55A1234`** |
| `[0xFFFF5004]` | `0xA55A1235`（ALU 自增） | **`0xA55A1235`** |
| `[0xFFFF6004]` | `0xA5A55A5A`（执行标记） | **`0xA5A55A5A`** |

日志：`sim/build/arm_exec.log`，判定行 `P1-ARM-EXEC-PASS` / `RESULT=PASS`。

### 30.5 实测二 + 一个关键发现：JTAG 读不到的寄存器，CPU 读得到

第二个程序让 CPU 自己读 SLCR 并把值写回 OCM 邮箱：

| 邮箱地址 | CPU 读的寄存器 | 实测值 |
| --- | --- | --- |
| `0xFFFF7000` | `0xF8007080` | **`0x30800100`** |
| `0xFFFF7004` | `0xF8000128` | **`0x01E03201`** |
| `0xFFFF7008` | 标记 `0xA5A55A5A` | **`0xA5A55A5A`** |

同样两个地址用 **xsdb 从 JTAG 读**：恒为 `0x00000000`。
即 Debug-AP 对 SLCR 这一段的**读**被挡住（恒 0），**不是寄存器真的为 0**。
—— 但**写并没有被挡住**。这一点我一开始判断错了（以为"读回 0"就等于"写也没落地"），
代价见 §30.8：从 JTAG 硬跑 `ps7_init` 的写是真的生效了，把 PLL 配到没锁上的状态。

这条后果很硬：Vivado 导出的 `ps7_init.tcl`（配置 MIO/PLL/时钟/DDR 的 1000 多条寄存器写）
**没法从 JTAG 验证着执行**——它的 PLL 锁定轮询读 `0xF800010C` 永远读到 0，
实测三次 `MASK-POLL-TIMEOUT addr=0XF800010C mask=0x1/0x2/0x4`（日志 `sim/build/ps_full.log`）。
⇒ **PS 的完整上电只能由 CPU 自己执行（也就是 FSBL 那条路）。**盲目从 JTAG 硬跑会出事 —— 见 §30.8。

### 30.6 对 S5 的意义：把"缺工具链"拆成四件事

| S5 需要的能力 | 现状 | 说明 |
| --- | --- | --- |
| ARM 执行我们写的代码 | **已打通** | 手写机器码 + xsdb 装载，本轮实测通过 |
| CPU 侧配置 SLCR/时钟 | **有权限**（CPU 读得到就写得进） | 但要把上千条 `ps7_init` 序列翻成机器码，工作量大 |
| PS ↔ PL AXI 通道 | **需要新位流** | `ps_bd/soc_ps.bit` 是 11-11 的旧 SoC（无记录仪）；当前 `S6_autorange` 里没有 PS7 |
| SD 卡写 CSV | 未开始 | SD 控制器在 MIO 上，要写 SD 协议 + FAT，手写机器码不现实 |

因此 S5 的最短可行路径（**不装工具链也能出真实数据**）：
1. 用当前 `board_top`（带记录仪）+ PS7 重建 BD 位流，PS 侧 AXI-Lite 仍挂 `0x4000_0000`；
2. ARM 侧手写"排空循环"：读记录仪 FIFO 数据寄存器 → 写 DDR；
3. 用 xsdb 把 DDR 内容读出来落成 CSV —— **把"SD 卡"换成"JTAG 导出"，数据是真的**；
4. 若要真的写 SD 卡，必须上工具链（C + FAT 驱动），届时仍需用户批准安装。

## 31. S5 的硬件保险：AXI 从端授权超时（2026-11-18 00:30）

### 31.1 触发这次改动的现场事故

想用现成的 `ps_bd/soc_ps.bit`（PS7 + 本 SoC 的 AXI-Lite 从口）先验证"A9 通过 AXI 读写 PL 侧 DRAM"，
结果 A9 一执行到访问 `0x4000_0000` 的那条指令就出事：

```
[AXI] 烧 ps_bd/soc_ps.bit: 0
[AXI] 代码回读 0 个不一致
xsdb : Cannot halt processor core, timeout        ← stop 命令卡死
   (procedure "stop" line 14)
```

**因果**：PS 发起一笔 AXI 事务，PL 侧的从端因为没真正出复位/没时钟**永远不给响应**，
这笔挂起的事务把 PS 的中央互连锁死 —— 连调试 AP 都过不去，所以**核都 halt 不住**，
只能断电重上电。（记录仪位流本身没受影响：重烧 + VIO 实测 `adc_cnt` 7.61M→7.92M 全部正常。）

### 31.2 改法：等授权/等返回都有硬超时

`board/axil_slave.sv` 原来在两个地方死等，现在都加了 `GNT_TMO`（默认 64 拍）超时：

| 状态 | 原来 | 现在 |
| --- | --- | --- |
| `S_WRQ` 等 `m_gnt` | 永远等 | 超时 → 释放 AW/W、`bresp = SLVERR(2'b10)`、进 `S_WB` |
| `S_RDQ` 等 `m_gnt` | 永远等 | 超时 → `rdata = 0`、`rresp = SLVERR`、进 `S_RB` |
| `S_RW` 等 `m_rvalid` | 永远等 | 超时 → 同上 |

**宁可让软件收到一个 SLVERR，也不能把主机总线挂死。** 这条对 PS 尤其重要：
PS 的总线挂死是不可恢复的（要断电），而软件拿到 SLVERR 还能重试/报警。

### 31.3 验证（仿真，15 项全 PASS）

`sim/tb_axil.sv` 新增三项（原来 10 项，现在 **15 项**）：

| 检查 | 结果 |
| --- | --- |
| T9 写授权永久扣住 → `bresp == SLVERR` | **PASS** |
| T9b 超时有限（实测 **66 拍**，`GNT_TMO+2`） | **PASS** |
| T9c 读授权永久扣住 → `rresp == SLVERR` | **PASS** |
| T9d 超时读数据为 0 | **PASS** |
| T10 超时之后桥自恢复（授权回来照常读写） | **PASS** |
| 原 T1~T8（字节使能/通道分离/valid 保持/延迟授权） | 全 PASS |

`sim/tb_dram_shared.sv` 侧 6/6 也复跑通过（它同时例化了本桥）。
日志：`sim/build/tb_axil.log`、`sim/build/tb_dram_shared.log`。

### 31.4 对记录仪产品位流没有影响

`axil_slave` 只在 `AXIL_EN=1` 的 PS 工程里生效；记录仪位流是 `AXIL_EN=0`，
`board_top` 里那一路端口被钉成 0（见 `board_top.sv` 的 `g_dram_single` 分支），
所以这条改动**不改变已验收的记录仪位流行为**，也不用重烧板子。

### 31.5 这条给 S5 留下的硬约束

做"PS + 记录仪"位流时，**必须先保证 PL 侧出复位、有时钟，再让 ARM 去访问**；
现在有了超时保护，即使顺序错了也只会得到一个 SLVERR，不会再把整块板子弄到要断电。

## 32. S5 的工程实现：PS + 记录仪位流、ARM 排空、CSV 导出（2026-11-18 00:40）

这一节是 S5 的正面实现：**不改动已验证的记录仪 RTL**，另起一个 PS 顶层。

### 32.1 为什么不能复用旧的 `board_top_ps`

`board_top_ps`（§7 那版）只把 **DRAM** 挂到 AXI 上（PS 靠它灌 RISC-V 镜像），
记录仪的寄存器在 CPU 私有总线上，**ARM 看不见**。要在 ARM 侧看到 FIFO，
必须让记录仪寄存器也有一条 AXI 通路。

### 32.2 新顶层 `board/board_top_ps_rec.sv`

```
PS7 M_AXI_GP0 → axi_protocol_converter(AXI3→AXI4Lite) → axi_interconnect ─┬─ M00 → s_axil      → board_top(AXIL_EN=1) → DRAM
                                                                          └─ M01 → s_axil_mmio → axil_slave → rec_mmio
```

| 取舍 | 决定 | 理由 |
| --- | --- | --- |
| CPU 是否也访问记录仪寄存器 | **不**（`EXT_MMIO=0`） | 避免"CPU 与 PS 同写一个寄存器"的仲裁问题；这一版只要 ARM 能读到 |
| ADC 数据源 | **假 DRP 方波**（0x8000±0x200） | 不占模拟引脚、不需要 XADC 原语；先验证"排空链路"，真器件接法见 `board_top_rec.sv` |
| 显示/DAC/触发/测量 | 全部不接 | 本设计只为 S5 服务，输出悬空 |

### 32.3 地址划分（PS 侧）

| 窗口 | 地址 | 大小 | 目标 |
| --- | --- | --- | --- |
| DRAM | `0x4000_0000` | 64 KB | `board_top` 的 AXI 从口 |
| 记录仪 MMIO | `0x4001_0000` | 4 KB | `rec_mmio`（寄存器索引 = `addr[7:2]`） |

构建脚本：`_diag/build_ps_bd_rec.tcl`（工程目录 `ps_bd_rec`，不动老工程 `ps_bd`）。
踩过两个 BD 坑，都写在脚本注释里：`assign_bd_address` 会给第二个从口要 512M 段直接和
DRAM 段重叠（改成手工 `create_bd_addr_seg`）；`axi_interconnect` 的 `SI/MI_PROTOCOL`
是只读的（AXI3→AXI4-Lite 必须靠前面的 `axi_protocol_converter`）。

### 32.4 ARM 侧：排空程序 + CSV 导出

工具：`tools/ps/arm_drain.tcl`（内含迷你汇编器，按需要的指令生成机器码，不再手写十六进制）。

用到的寄存器（`rec_mmio`）：

| 索引 | 偏移 | 方向 | 含义 |
| --- | --- | --- | --- |
| 35 | `0x8C` | 读 | FIFO 队头（只窥视，不弹） |
| 37 | `0x94` | 读 | FIFO 深度 |
| 38 | `0x98` | 写 | `ADC_CTL`：bit0 使能、bit2 弹出 |
| 40 | `0xA0` | 读 | 累计样本数 |

程序（ARM/A32，约 17 条）：

1. `ADC_CTL ← 1`（使能采样）；
2. 循环 256 次：读队头 → 写 `DRAM[i]` → 指针 +4 → 写 `ADC_CTL ← 5`（使能+弹出）；
3. 循环次数与标记写 OCM 邮箱。

跑完后脚本用 `mrd` 把 DRAM 读出来，按 XADC 的"结果左对齐在 `[15:4]`"换算成码值/电压，
生成 `sim/build/drain_<时间戳>.csv`。

> **说明**：这条路径用 **JTAG 导出**代替 SD 卡——数据是真的（来自 FIFO），
> 只是落盘走调试口。要真写 SD 卡，仍需 ARM 工具链（§4.3）。

### 32.5 验收判据（位流构建完成后逐条对）

| 判据 | 期望 |
| --- | --- |
| 位流构建 | impl 100%、`write_bitstream` 成功、无 DRC |
| 烧写 | `End of startup status: HIGH` |
| ARM 能读到 MMIO | 读 `0x4001_0000+0x94`（FIFO 深度）非 0 且在 0..1024 之间 |
| 排空成功 | 邮箱标记 = `0xBEEF0005`、循环次数 = 256 |

| 数据量 | CSV 256 行 |

### 32.6 离线自检：没有 ARM 工具链也能核对机器码

手写/自动生成的机器码最容易错在**编码**，而不是逻辑。为此加了两个小工具：

| 工具 | 作用 |
| --- | --- |
| `tools/ps/arm_drain.tcl` 的 `DRAIN_DUMP_ONLY=1` | 只把生成的机器码打印成 `WORD|i|hex`，不碰硬件 |
| [`tools/ps/arm_a32_disasm.py`](../tools/ps/arm_a32_disasm.py) | 最小 ARM/A32 反汇编器：解码 MOVW/MOVT/MOV/LDR/STR/ADD/CMP/B 并**核对分支目标** |

**第一次跑就抓到一个真 bug**：`mov r7, #256` —— `MOV imm8` 只能装 0..255，
`256 & 0xFF = 0`，于是 `R7 = 0`，循环 `CMP R8,R7` **永远不相等**（会一直排空到 32 位回绕）。
反汇编输出 `mov r7, #0x00`，一眼看出来；改成 `movw r7, #0x0100` 后判据全 PASS：

```
11 0xFFFFA02C  L0: ldr r4, [r9, #0x94]     ; 等 FIFO 深度
13 0xFFFFA034      beq 0xFFFFA02C          ; [OK] 回跳到 11
20 0xFFFFA050      bne 0xFFFFA02C          ; [OK] 回跳到 11
25 0xFFFFA064  L1: b 0xFFFFA064            ; 自旋
[ARM-DISASM] status=PASS
```

这条经验值得记住：**没有工具链不等于没法验证机器码**，反汇编 + 分支目标核对就能挡掉
大多数低级错误；真正剩下的（时序、总线行为）才需要上板。

### 32.7 上板第一击：JTAG 烧 `.bit` **不会**配置 PS（2026-11-18 01:05）

烧 `board_top_ps_rec_S5.bit` 后用 `arm_drain` 一跑，ARM 立刻卡死：

| 现象 | 输出 |
| --- | --- |
| 写 OCM 代码 | `Cannot write memory if not stopped ... Cannot halt processor core, timeout` |
| `rrd pc`（还能读） | **`0xFFFFA044`**，四次采样完全不变 → 核卡在一条指令上 |
| `0xFFFFA044` 是哪条 | 正是排空程序的 `str r0, [r9, #0x98]`（写记录仪 MMIO） |

**根因**：JTAG 烧 `.bit` 只配 **PL**，不配 **PS**。Zynq 上电后 SLCR 里这三个总开关是关的：

| 寄存器 | 上电值 | 含义 |
| --- | --- | --- |
| `0xF8000900` `LVL_SHFTR_EN` | 0 | **PS→PL 电平位移器全关**（不开，PS-PL 信号根本不通） |
| `0xF8000128` `FPGA0_CLK_CTRL` | CLKACT=0 | **FCLK0 没使能**（PL 侧没有时钟） |
| `0xF8000240` `RST_FPGA_CTRL` | — | PL 各 FCLK 域复位没释放 |

没有时钟 ⇒ AXI 从端永远不会回响应 ⇒ PS 的主机端口一直等 ⇒ 中央互连被这笔事务锁死
⇒ 连调试器都 halt 不进核。**我加的 64 拍超时在从端内部，管不到"从端根本没时钟"这种情况。**

**修法（已实装）**：`tools/ps/arm_drain.tcl` 的程序现在**自带前 15 条 SLCR 初始化**：

```
解锁 SLCR → LVL_SHFTR_EN=0xF → FCLK0=0x00700F01 → RST_FPGA=0 → 锁回 SLCR
→ 自检 FPGA0_CLK_CTRL[0]：若为 0 就直接写失败标记 0xDEAD0001 并自旋（**绝不碰 AXI**）
→ 才进入排空循环
```

反汇编核对：61 条指令，`beq` 出口在第 55 条（失败路径），循环回跳落在第 40 条
（`ldr r4,[r9,#0x94]` 等 FIFO），分支目标全部 `[OK]`。

**另一个现场结论**：这种"互连锁死"**只有 POR 能解**——重新烧 PL 位流不行（实测 PC 依旧冻结在
`0xFFFFA044`），因为挂在 PS 互连内部的那笔事务不会因为 PL 变了而消失。

## 33. S7 双核解耦对比实验：PS 排空吞吐 vs PL 采样率（2026-11-18 01:20）

### 33.1 实验设计

S7 要回答的是一个量化问题：**PS（ARM）侧的排空工作，会不会拖慢 PL 侧的 200 kHz 采样？**

做法（全部在一次运行里自测，不依赖外部计时器）：

1. ARM 程序在排空**前**读一次 `adc_cnt`（`rec_mmio` idx40），存邮箱[2]；
2. 排空 `N` 个样本到 PL 侧 DRAM；
3. 排空**后**再读一次 `adc_cnt`，存邮箱[3]；
4. `Δadc_cnt` = 排空期间 PL 侧新产生的样本数 —— 这个数**与排空数之比**就是"PS 吞吐 / 采样率"，
   与时钟频率假设无关（不受"CPU 到底跑多少 MHz"影响）；
5. 再把 DRAM 内容导成 CSV，检查波形**游程**（假 DRP 的方波半周期恒为 128 样本）——
   游程一旦不是 128 的整数倍，就说明**丢样本或重复样本**。

### 33.2 三轮实测（N=2048）

| 轮次 | 排空数 | 标记 | 期间 Δ`adc_cnt` | 游程（段长） | 结论 |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮（FIFO 满） | 2048 | `BEEF0005` | 1024 | 128×8, **18**, 128×7, 110 | 有 1 处断点 |
| 第 2 轮（未修屏障） | 2048 | `BEEF0005` | 1024 | 18, 128×7, **215**, 128×7, 23 | **出现 215 > 128** |
| 第 3 轮（加 DSB 后） | 2048 | `BEEF0005` | 1024 | 105+23, 128×7, **16+112**, 128×7 | 断点成对（和=128），**无 >128** |

**第 2 轮的 215 是一个真 bug 的指纹**：A9 的 `STR` 是 posting 的（走写缓冲），
`pop` 之后紧跟着的 `peek` 有可能**又读到旧队头** → 同一个样本被排空两次 → 同一电平持续
215 个样本。修法：`pop` 之后加 **`DSB SY`**（`0xF57FF04F`），强制等写完成。第 3 轮
再没有出现 >128 的段，说明这个屏障是必需的，不是保险。

### 33.3 解耦结论（可直接引用）

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| 排空 2048 个样本期间，PL 侧新产生 | **1024 个** | 比值 2048:1024 = **2.0** |
| 折算排空吞吐 | **≈400 kSa/s** | 时长由 1024×5 µs = 5.12 ms 换算 |
| PS 侧相对采样率的余量 | **≈2×** | 即 PS 侧能"边清空积压、边跟上新数据" |
| 排空期间采样率是否变化 | **未变化**（Δ 与时间严格成 200 kHz 关系） | PL 侧独立时钟域，未受 PS 影响 |
| 数据完整性 | 2048 样本、高低各 1024 | 断点仅出现在"积压尾部/新数据头部"交界 |

**为什么交界处必然有一个断点**：FIFO 满时 `xadc_sampler` 是"**丢新样本**"
（`do_wr = (st==S_CAP) && !full`），所以积压里最后一个是"满之前的样本"，
新数据的第一个是"腾出空间之后的样本"，中间被丢掉的那些造成了相位跳变 —— 这是**可解释的**，
不是排空逻辑出错。若要拿到完全干净的 2048 连读，需要先排空积压再开始计数（下一步可做）。

### 33.4 这条实验对产品意味着什么

- **双核解耦成立**：PS 侧再怎么忙（这里是最坏的"边清积压边跟新数据"），
  PL 侧的采样节奏、HDMI 时序都不受影响（§32.8 的 `adc_cnt` 与 §31 的帧参数都没变）。
- **采集端不需要 PS 参与**：ARM 只是"消费者"，掉线/卡死最多让 FIFO 满并丢新样本，
  不会破坏已经采到的数据（FIFO 内容保持连续）。
- **吞吐余量 2×**：真要接 SD 卡时，卡写性能只要 ≥200 kSa/s 的等效带宽（每样本 2 字节 → 400 kB/s）就够。

### 33.5 补一次"干净连读"：把积压先排空再计数（2026-11-18 01:23）

§33.2 的三个断点都出在"积压尾部/新数据头部"。为拿到完全连续的波形，程序改成
**先排空历史积压（不计数）→ 再开始计 N 个样本**，并且加了 DAP 自恢复
（`rst -dap`，否则 `AHB AP transaction error ... 0x30000021` 会把 APU 藏起来）。

结果（`sim/build/drain_20261118_012357.csv`，N=2048）：

| 指标 | 实测 |
| --- | --- |
| 游程 | `46` + **128 × 15** + `82` = 2048 |
| 中间 15 段 | **全部恰好 128 样本** → `RUNLEN-PASS`（无丢失、无重复） |
| 期间 Δ`adc_cnt` | **2047**（= 排空 2048，差 1 是边界效应） |
| 折算 | 排空 2048 花了 2048×5 µs = **10.24 ms** → **严格 200 kSa/s** |

**两种工况都测到了，正好互补**：

| 工况 | 现象 | 结论 |
| --- | --- | --- |
| FIFO 满（有积压） | 排空 2048 期间 PL 只新增 1024 | PS 侧吞吐 **≈2×** 采样率，有余量 |
| FIFO 空（跟上节奏后） | 排空 2048 期间 PL 新增 2047 | PS 侧**稳定跟住 200 kSa/s**，且数据完全连续 |

CSV 片段：`0..45` 全是 2080，`46..173` 全是 2016，之后每 128 个样本翻一次，
最后 `1966..2047`（82 个）全 2080 —— 边界干净，没有半截相位。

## 34. 没有显示器，也能看到"画面上真是什么"：ILA 抓 HDMI 数据线（2026-11-18 02:10）

### 35.1 AD11 外部通道：读数恒 0 = "缺那根线"的指纹

> ❌ **本条结论已于 2026-11-19 00:10 作废**：真因是 XADC 序列器配错（`INIT_41` 的 SEQ=0011 是**单通道模式**），VAUX 通道从来没被转换过，与接线无关。见 **§48**。


把 XADC 采样通道从片内温度切回 **AD11（A18/A19）**（VIO `int_ch=0`），实测：

| 探针 | 值 | 说明 |
| --- | --- | --- |
| `adc_last` | **`0x0000`** | 悬空引脚读到 0 |
| `meas_min/mean/max` | **0 / 0 / 0** | 窗口内全是 0 |
| `adc_cnt` | 81 727 169 → 82 027 967 | 采样仍在跑（≈200 kHz） |

**这不是 bug，而是 S2 卡点的直接证据**：AD11 上什么都没有（那根 DAC→分压→AD11 的线没接），
所以读到 0；接上线之后这里就会跟着 DAC 码值变化。

### 35.2 触发率复测（当前位流 `S6_ila2`）

用墙钟长窗口（3 点、间隔 3 s）：

| 指标 | 实测 |
| --- | --- |
| 触发增量 | 20 736 次 |
| 墙钟跨度 | 6.714 s |
| 折算 | **≈3088 次/秒**；扣掉每次 VIO 读取约 300 ms 的固定开销后 **≈3130 次/秒** |
| 结论 | 与 `HOLDOFF=64 → 200k/64 = 3125 次/秒` **一致**（原结论成立） |

### 35.3 顺手记一个方法学坑：不能用 `adc_cnt` 当"转换次数"的时基

同一段数据若改用 `adc_cnt` 当时间基准，会得到"每 **62.9** 个样本触发一次"，
看起来比 64 快 1.8%。**这是假象**：`xadc_sampler` 里

```systemverilog
if (do_wr) sample_cnt <= sample_cnt + 1;   // 只有真正写进 FIFO 才 +1
```

FIFO 满时丢样本**不计数**，所以 `adc_cnt` 是"入队数"而不是"转换数"，
做分母会把速率算高。**测速率用墙钟，或另开一个"转换计数"寄存器。**

## 38. S5 的 SD 卡写入：打通了什么、卡在哪（2026-11-18）

### 38.1 先纠正一个错误判断

之前写"本机没有 ARM 交叉工具链"，**这是错的**。机器上有：
`E:\renases_e2s\toolchains\gcc_arm\13.2.rel1\bin\arm-none-eabi-gcc.exe`（Arm GNU Toolchain 13.2.1）。
`sw/build_ps_app.ps1` 一直引用它，只是没有加进 PATH，所以 `where arm-none-eabi-gcc` 查不到。

新的构建脚本：`sw/build_ps_sd.ps1`（编译 Xilinx xsdps 驱动 + 自制移植层 + 应用，
链接脚本 `sw/ps/link_ps_sd.ld`，需要 `-lgcc`，因为要用到 `__aeabi_uidiv`）。

### 38.2 已打通的四条链路（都实测过）

| 链路 | 做法 | 证据 |
|---|---|---|
| C 编译 | ARM gcc 13.2.1 + `-nostdlib` | `sd_probe.elf` 13 KB text / 18 KB bss |
| JTAG 运行 | `xsdb rst -processor` → `dow -force` → `con` | 程序在 A9 上跑到 idle |
| 程序日志回读 | 把 `xil_printf` 同步写进 OCM，用 `mrd` 读 | 逐字节正确的文本（`_diag/ps_log_dump.tcl`） |
| PS 软复位 | SLCR `PSS_RST_CTRL(0xF8000200)=1` | 能把卡死的 `CMD_INHIBIT` 清掉 |

### 38.3 为什么用"内存日志"而不是串口

**ps7_init 里的 UART1 波特率是错的。** 它按 UART 时钟 86.4 MHz 算
（`BAUDDIV=6, BAUDGEN=124` → 115200），但实测 UART 时钟是 **IO PLL/16 = 62.5 MHz**，
所以实际波特率只有 83.3 kHz，PC 按 115200 读全是乱码（第一轮实测收到 697 字节乱码）。

正确值：`BAUDGEN = 89`（62.5e6/(6×90) = 115740，误差 0.5%），改完串口就能读。
但在排查阶段串口还不可靠，所以程序把日志写进 OCM：
`0x2_4000` = 长度，`0x2_4004` 起 = 文本（`link_ps_sd.ld` 定义）。

### 38.4 三个真 bug（都已修，值得记）

1. **`0xE0100032` 不能用 32 位访问**：ESTS 是 16 位寄存器，地址不在 4 字节边界上，
   Cortex-A9 直接报对齐异常：`DFSR=0x00000801, DFAR=0xE0100032`，程序"凭空断掉"。
2. **裸机没有异常向量表**：原来 0x0 处直接是 `_start`，任何异常都会跳到 0x10
   执行普通指令，表现是随机死机。现在 `sw/ps/start_ps_sd.S` 有完整向量表，
   异常会被接住并写进日志（`*** CPU FAULT type=3 DFSR=... DFAR=... ***`），
   第 1 条就是这样抓到的。
3. **`Xil_WaitForEvent` 不能用 PMU 周期计数器**：实测 `PMCCNTR` 不涨，
   于是所有"等某位清零"的循环永不超时，表现为"卡死在 SD 初始化里"。
   改成纯轮询计数后行为可预期。
4. **内存日志不能放在 `.bss` 里**：早期把进度标记写在 `0x2F00`，正好压在
   `XSdPs` 实例上，把驱动状态踩坏，又是一轮"随机卡死"。

### 38.5 SD 控制器：卡在哪

| 观察 | 数值 |
|---|---|
| SDHCI 版本 / 能力 | `VER=0x8901 CAPS=0x69EC0080` |
| 卡在位（PRES bit16/17/18） | **1 / 1 / 1 → 卡是插着的** |
| SLCR `SDIO_CLK_CTRL(0xF8000150)` | `0x00001001`（CLKACT0=1, SRCSEL=IO PLL, DIV=16） |
| APER 门控 `SDI0_CPU_1XCLKACT` | 1 |
| 写 `CLK_CTRL = 0x4E07` | 读回一致，内部时钟 `stable=1` |
| **发 CMD0 之后** | **`NSTS=0x0000`、`ESTS=0x0000`，既不完成也不报错** |

Xilinx 官方 `xsdps` 驱动与手写 `sd_raw.c`（`sw/ps/sd_raw.c`，PIO、不用 ADMA）
得到完全一致的结果。命令状态机不推进，最合理的解释是**卡侧时钟没有真正跑起来**
（SDHCI 的 "internal clock stable" 位在这颗控制器上可能是恒定 1）。

### 38.6 备用通道（SPI 模式 + MIO GPIO）也没走通

SD 卡支持 SPI 模式，而 SD0 的四根线都在 MIO 上，于是尝试把 MIO40..45 改成 GPIO
位翻转（`sw/ps/sd_spi.c`）：CLK=MIO40、MOSI=MIO41、MISO=MIO42、CS=MIO45。

结果：把 MIO_PIN_40 的低 6 位从 `0x00` 扫到 `0x3F`，**没有任何一个值**能让
"写 1 读回 1、写 0 读回 0"；`DATA_RO_1` 里 MIO40..45 始终读 0（而 MIO32..39 读 1）。
即 GPIO 输出这条路过不去（DIRM/OEN/MIO_MST_TRI1 都按手册置过）。

### 38.7 结论与下一步

**SD 卡写入尚未完成，不宣称成功。** 目前证据把问题收敛到"PS 的 MIO/SD 引脚通路"
这一层，而不是软件。可行的下一步（按成本排序）：

1. **换一张卡 / 确认卡槽方向**：卡在位信号是 1，但没排除触点问题；
2. **示波器量卡座 CLK 脚**（J15 第 5 脚）：识别阶段应有 ~400 kHz 方波。
   有波形 = 控制器没问题，问题在卡或触点；没波形 = MIO/时钟通路问题；
3. **上电复位（拔 DC）后再试**：我做过多次 PS 软复位，可能残留半初始化状态；
4. 若确认是 MIO 通路问题，SD 写入只能换方案（例如 PL 侧 SPI 主机 + 飞线，
   或 PS 以太网/串口导出替代）。

### 38.9 补充实测（同日）：串口通了，SD 控制器仍不动

**（1）串口波特率的真实值：BDIV=124 -> 62500 baud**

用"信标 + 扫波特率"的办法（`sw/ps/uart_beacon.c` + `_diag/scan_baud2.ps1`），
在 24 个候选里只有 **62500** 能读出 `UART-BEACON`。由此反推：

```
baud = clk / (CD x (BDIV+1)) = clk / (6 x 125) = 62500  =>  UART 时钟 = 46.875 MHz
```

即 IO PLL = 750 MHz（46.875 x 16）。所以要 115200：`BDIV = 46.875e6/(6x115200) - 1 = 67`。
改成 **BAUDGEN=67** 后，PC 在 115200 下读到的日志**逐字符正确**（实测 1883 字节全文本，
`sim/build/sd/uart_check3.log`）。**PS UART1 串口从此可用。**

**（2）SDHCI 的"状态位门控"假设被排除**

SDHCI 规范里 NSTS/ESTS 的每一位都受 Status Enable 门控，所以"命令完成却不置位"
本来是个合理怀疑。实测把 `0x34=0xFFFF / 0x36=0xFFFF` 写进去（读回 `0x07FF / 0x33FF`，
即已生效）后，**CMD0 仍然是 NSTS=0、ESTS=0**。排除。

**（3）6 种 SLCR SDIO 时钟编码全部无效**

| SLCR `SDIO_CLK_CTRL` 值 | 含义 | CMD0 结果 |
|---|---|---|
| `0x00001001` | CLKACT0，SRCSEL=IO PLL，DIV=16 | NSTS=0 |
| `0x00001003` | 再置 CLKACT1 | NSTS=0 |
| `0x00001011` | SRCSEL=ARM PLL | NSTS=0 |
| `0x00001021` | SRCSEL=DDR PLL | NSTS=0 |
| `0x00000101` | DIV=1（最快） | NSTS=0 |
| `0x00001201` | DIV=18（约 55 MHz） | NSTS=0 |

每种编码下 `CLK_CTRL` 都能写到 `0x4E07`、`stable=1`，但命令状态机始终不推进。
结合"MIO40..45 当 GPIO 也驱动不了"，指向 PS 与 SD 卡座之间的引脚/时钟通路，
而不是驱动软件。

**（4）现在的判据清单（谁来一眼定性）**

| 测点 | 期望 | 含义 |
|---|---|---|
| 卡座 J15 第 5 脚（CLK） | 识别阶段 ~300 kHz 方波 | 有波形 = 控制器/引脚正常，问题在卡或触点 |
| 卡座 J15 第 3 脚（CMD） | 命令期间有短脉冲 | 有 = 命令真的发出去了 |
| 供电脚（VDD） | 3.3 V | 卡得有电 |
**（5）操作注意：跑完 PS 实验后 PL 会掉配置**

本轮多次做 PS 软复位（`PSS_RST_CTRL`）之后，读 VIO 时 Vivado 报
`Device xc7z020 is not programmed (DONE status = 0)` —— PL 的配置没了。
所以**每次跑完 PS 侧实验，都要重新 `fpga -f _baseline_v9/board_top_rec_S6_ila2.bit`**，
再读 VIO 确认。`_diag/restore_s6.tcl` 就是干这个的（xsdb 里用
`targets -set -filter {name =~ "*xc7z020*"}` 再 `fpga -f`，注意 xsdb 没有 `get_hw_devices`）。
本轮已按此恢复并复测：`adc_cnt` 6,296,849 -> 6,505,047、`col_col=799`、
`d_wb_pc` 1032->1020、`m_frame_clk=663168`、`m_frame_lines=628`。

### 38.10 关键发现：MIO_PIN 的"功能选择"在 [7:5]，不在低位

把 MIO40..45 当 GPIO 一直失败，根因是**改错了位**。

办法：让 Vivado 生成一份"把 MIO40..45 配成 GPIO"的 ps7_init
（`_diag/gen_ps7_gpio.tcl`），看它到底写什么：

| 用途 | Vivado 写的 `MIO_PIN_4x` 值 | 差别 |
|---|---|---|
| SD0（CLK/CMD/D0..D3） | `0x00000780` | `[7:5] = 4` |
| **GPIO** | **`0x00000700`** | **`[7:5] = 0`** |

两者只差 `[7:5]` 三位 —— 也就是说 **功能选择就是 [7:5]**（3 bit），
而 `[8]=1`（slew fast）、`[11:9]=3`（上拉关闭）这些是电气属性。
之前把低 6 位从 `0x00` 扫到 `0x3F` 全部失败，就是因为一直在改电气属性位。

改成 `0x0700` 之后，`MIO40` 立刻能当 GPIO 输出用：
写 1 读回 1、写 0 读回 0（`CLK-follow=1`）。**这条现在可以放心用了。**

### 38.11 SPI 模式进卡：GPIO 通了，但卡不响应

用 `0x0700` 把四根线做成 SPI（CLK=MIO40, MOSI=MIO41, MISO=MIO42, CS=MIO45），
时钟约 100 kHz，CS 高打 80 个时钟再发 CMD0（带 0x95 CRC），重试 10 次：
**R1 恒为 0xFF（MISO 一直是高，卡没有任何响应）**。

最可能的原因：**SD 卡上电默认在 SD 模式，之前那些 SDHCI 尝试已经把它留在 SD 模式里了；
按规范，卡一旦进了 SD 模式，只有重新上电才能进 SPI 模式**（CMD0 拉低 CS 的方式必须在
上电初始阶段用）。

所以下一步需要一次**真正的断电重启**（拔 DC 再插），并让卡保持插着；
重启后**第一件事就跑 `sd_spi`**（而不是先跑 SDHCI 的程序），这样卡的第一条命令
就是"CS 低 + CMD0"，有机会直接进 SPI 模式。

> 顺带说明：即便 SPI 模式通了，SPI 写块速度也只有 100 kHz~几 MHz 量级，
> 对"2048 样本 CSV"这种小文件够用；真要 200 kSa/s 连续记录还是得靠 SDHCI。

### 38.12 三条软件路径全部"卡不响应"，且卡检测脚说"没卡"

在 GPIO 可用（`0x0700`）之后，SD 访问有了第三条独立路径。三条路径的结果：

| 路径 | 实现 | 结果 |
|---|---|---|
| SDHCI（4-bit SD 模式） | `sw/ps/sd_raw.c` / Xilinx xsdps | CMD0 后 `NSTS=0 ESTS=0`，命令不推进 |
| SPI 模式（GPIO 位翻转） | `sw/ps/sd_spi.c` | `CMD0 -> R1=0xFF`（MISO 恒高），10 次重试 |
| **SD 模式 1-bit（GPIO 位翻转）** | **`sw/ps/sd_bit.c`** | **CMD0 无响应，CMD8 `waitbits=0xFFFFFFFF`（CMD 线全程为高）** |

第三条最说明问题：SD 模式下主机发完 CMD8 就会释放 CMD 线，卡若在，1~8 个字节内
必然把 CMD 拉低给出起始位。实测**32 个采样位全是 1**，等于"线上没有任何设备在说话"。

再用卡检测脚交叉验证（`sw/ps/sd_cd.c`，EES331 把 SD0 的 CD 接在 MIO0）：

```
DATA_RO_0 = 0x523FFE01   MIO0(CD) = 1     <- 1 = 没有卡（插入时该脚接地）
MIO40..45 = 1 1 1 1 1 1                   <- 卡座六根线都被外部上拉拉高
```

结论：**卡槽里大概率没有卡**（或卡没插到位/触点不通）。
这也顺带解释了 SDHCI 为什么"只发命令不完成"——不少 SDHCI 在 `Card Inserted = 0`
时本来就不执行命令。

### 39.4 顺带挖出两个 ARM 裸机陷阱（都值得记）

**（1）非对齐访问会直接把 CPU 干掉**

现象：格式化一开始就 `*** CPU FAULT type=3 DFSR=0x00000801 DFAR=0x000027C7 PC=0x... ***`，
DFAR 是个**奇数**地址。

根因两段：
- `wr16()/wr32()` 写的是逐字节，但 `-O2` 下 gcc 把它们**合并成一条 `str`/`strh`**；
- FAT32 引导扇区里到处是奇地址字段（`bs[11]`、`bs[17]`、`bs[67]`…），合并后就是非对齐字访问。

而 **Cortex-A9 在这块板的内存模型下对非对齐访问一律报对齐异常**（即使 `SCTLR.A=0`）。
两个修法一起上：
- 编译加 **`-mno-unaligned-access`**（让 gcc 永远不合并成字访问）；
- `wr16/wr32` 内部改用 `volatile u8 *`，禁止优化器合并。

**（2）异常处理器必须报 PC**

上一轮的向量表只报了 `type/DFSR/DFAR`，靠 DFAR 在 `.text` 区里飘根本定位不到。
这轮把**异常返回地址**也传进 `port_fault`：

```
*** CPU FAULT type=3 DFSR=0x00000801 DFAR=0x000027C7 PC=0x00000FC4 ***
```
再用 `arm-none-eabi-objdump -d --start-address=0xF84` 一看就知道是
`str r1, [r3, #-509]`（`bs+3`）——两分钟定位，之前靠猜花了半小时。

### 40.2 假卡是怎么造的（这才是这轮的关键）

在 OCM `0x1_0000` 摆 64 KB 当"卡"，用同一套 `sd_bus` 回调接上去。假卡做到：

| 能力 | 为什么必须有 |
|---|---|
| 按规范回 48 bit 响应（R1 内容可注入） | 才能触发 `-1/-2` 分支 |
| 读时先发若干 `0xFF` 再发 `0xFE` | 令牌搜索循环才真的被执行（不是一次就中） |
| **自己重算 CRC16** 并与主机发来的比对 | 主机 CRC 错就回 `0x0B` 令牌 —— 这是**独立算法**校验，不是自己校验自己 |
| 写成功后拉忙 24 位再释放 | 忙等循环才真的被执行 |
| 能注入：无响应 / R1 错 / 无令牌 / 读 CRC 错 / **CRC 故意算错** / 越界 / 无数据响应 / 永远忙 | 每条失败返回码都要被真的触发一次，否则"错误处理"就是死代码 |

假卡还把"当前命令、LBA、收了多少字节、CRC 对不对"记成计数器，最后打印出来当证据。

### 40.5 这轮抓出的 3 个 bug（2 个是产品代码里的）

**（1）`sd_write_block()` 的忙等超时会误报成功** ← 产品 bug

现在超限返回 `SDW_EBUSY(-8)`，并且 T4 用"永远忙"注入证明了这条分支真的能走到。

**（2）R1 错误位掩码漏了一位** ← 产品 bug

`sd_read_block()` 返回 0（当成成功）。现在用 `0xFFF98000`（bit31..19 + bit16 + bit15）。

**（3）假卡自己的差一错误** ← 测试代码 bug（但正是它证明了测试有效）

`fc_tx()` 里 `if (pending <= 515) return;` 导致第 515 个字节（CRC 低字节）收完就返回、
**永远走不到 CRC 校验**。第一次跑的结果是 `blocks accepted=0` + 11 项 FAIL ——
测试立刻把这问题指出来了，改成 `< 515` 后全绿。

> 这条值得记：假卡如果写得太"宽容"，测试就会全绿而毫无价值。
> 第一次跑 11 项 FAIL 恰恰说明这些断言不是摆设。

## 41. 真卡几何（64 MB）在 PC 上验过了，并加了第三条独立证据（2026-11-18）

### 41.1 补的是一个真实缺口

板上只能跑"小几何"：128 扇区、`reserved=2`、1 份 FAT 只有 1 个扇区 —— 因为 OCM 只有 192 KB。
真卡用的是 **64 MB 几何**：`reserved=32`、每份 FAT **1024 个扇区**、**130016 个簇**。
这两条在 `fat32.c` 里是**同一个函数的两组参数**，但大几何从来没被执行过一次。

## 42. 把"产品路径"本身变成可执行的，并抓出证据导出的一个真 bug（2026-11-18）

### 42.1 起因：`sd_fat_sd.c` 的流程一行都跑不到

`sd_fat_sd.c`（真卡产品路径）原来把"CSV → 格式化 → 写 → 回读比对"整段写在 `main()` 里，
而 `main()` 里有 OCM 地址、记录仪 MMIO、卡初始化 —— 于是没卡就**一行都执行不到**。
这跟 `sd_wr.c` 当初"只编译没执行"是同一个毛病。

修法：把这段纯逻辑抽到 **`sw/ps/sd_record.c`**（`sd_record_to_card()`），
它只依赖 `sd_bus` 和调用者给的缓冲，不碰任何硬件。于是：

| 位置 | 谁调它 | 状态 |
|---|---|---|
| 板上真卡 | `sd_fat_sd.c`（初始化 + 抓样本 + 调它） | 编译通过，等卡 |
| PC 假卡 | `tools/ps/host/fat32_host_test.c`（64 MB 内存卡） | ✅ **真跑，27/27 项通过** |

### 42.2 PC 上跑产品路径的结果（1000 个样本 / 64 MB 卷）

```

  fat32: wrote 9603 bytes, 19 clusters from 3
```

然后两条独立复核（都不用我写的代码）：

|---|---|

而是在 C 里 `blk[k] != csv[off]` **逐字节比了 9603 次，diff=0**。

### 42.3 测试自己抓出的 bug：证据 dump 写死了"前两簇"

上一轮定的证据扇区列表是写死的 7 个：`{0, 1, 6, 32, 1056, 1057, 1058}`。
它对 899 字节（2 簇）的文件是对的，但产品路径的文件是 9603 字节（19 簇）。结果：

```
got     : 9603 bytes, djb2=0xE8FF49E0
expected: 9603 bytes, djb2=0x545706DB
FAIL: content mismatch
  first diff at 1024: got 0x00 exp 0x38
```

第 1024 字节就露馅了 —— 因为只有前 2 个数据扇区被 dump 出来，后面 17 个读回来是 0。
**这个 bug 在没卡的时候就被抓到了**，否则插卡那天会白折腾一轮。

修法（`sw/ps/sd_dump.c` + PC 侧同一套规则）：先读引导扇区拿几何，再读根目录项拿
文件长度和首簇，然后
- 固定 5 个：引导、FSInfo、备份引导、FAT 第一扇区、根目录簇；
- 数据扇区：`ceil(len/512)` 个，从首簇对应的 LBA 起连续取。

现在 dump 是 24 个扇区、12488 字节，复核 PASS。

### 42.4 这条链路的已知上限（如实写）

| 限制 | 数值 | 影响 |
|---|---|---|
| 证据缓冲区 | 16 KB → 最多 **31** 个扇区 | 文件 > 约 13 KB 就放不下，程序会打 `FAIL_too_many` 而不是偷偷截断 |
| FAT 只 dump 第一扇区 | 128 个簇表项 | 文件 > 125 簇（约 64 KB）时，规范复核沿簇链会提前遇到 EOC。当前 1024 样本 ≈ 20 簇，够用 |
| 单文件 | 只认根目录里的第一个目录项 | 目前只写一个文件，够用 |

### 42.5 板上四个程序的栈顶都核对过

链接脚本把 0x2_0000 之后留给 SD/证据缓冲，所以 `.bss`+栈 必须停在它下面：

## 43. 把"最像没插卡"的三个隐患先修掉（2026-11-18）

板子还是那个 DAP 粘滞状态，所以这轮继续在软件侧找"插卡那天最可能白折腾一轮"的地方。
按"出现了会分不清原因"排序，前三名：

### 43.1 CRC7 从没和外部标准对过（第一名）

**为什么危险**：SD 卡只在 **CMD0 / CMD8** 阶段真的检查命令帧的 CRC7。
CRC7 算错 → CMD0 不会把卡复位到 idle、CMD8 被拒 → 现象和"**没插卡**"一模一样：
`waitbits=0xffffffff`、`RESULT FAIL_card_init step=1`。到时候根本分不清是卡的问题、接触的问题，还是 CRC 的问题。

**做法**：把 CRC 从 `sd_bit_bus.c` / `sd_wr.c` 里抽成 `sw/ps/sd_crc.c` + `sd_crc.h`
（只依赖 `xil_types.h`，因此**能被 PC 测试编译**），顺便消掉了原来 crc16 在两处各写一份的重复。
然后拿 SD 规范里**公开的命令帧**当标准答案：

| 检查 | 标准值 | 来源 |
|---|---|---|
| `sd_crc7(40 00 00 00 00)` | **0x4A**（帧尾 0x95） | SD 规范 CMD0 帧 `40 00 00 00 00 95` |
| `sd_crc7(48 00 00 01 AA)` | **0x43**（帧尾 0x87） | SD 规范 CMD8 帧 `48 00 00 01 AA 87` |
| `sd_crc7(77 00 00 00 00)` | **0x32**（帧尾 0x65） | CMD55 帧 |
| `sd_crc7(69 40 FF 80 00)` | **0x0B** | ACMD41 |
| `sd_crc16("123456789")` | **0x31C3** | XMODEM 标准检查值 |
| `sd_crc16(512 个 0x00)` | **0x0000** | 初值 0 |

六项全过（`tools/ps/host/fat32_host_test.c` 的 `t_crc()`，输出里是十进制：74/67/50/11/12739/0）。

> 交叉确认：我另外用 Python 按多项式 `x^7+x^3+1` 独立算了一遍，得到的帧尾也是 0x95 / 0x87，
> 和规范里公开的帧一致 —— 也就是说"标准答案"本身有两个来源。

### 43.2 响应窗口原来只给 32 个时钟（第二名）

SD 规范里命令响应的 **NCR 最长 8 个字节 = 64 个时钟**，而 `wait_start()` 原来只扫 **32** 个。
一张"稍微慢一点"的卡会被误判成无响应 —— 又是那个"看起来像没插卡"的现象。

改法：
- 窗口 32 → **64** 个时钟；
- 新增 `sd_bit_waitcount()`，把这次响应前**实际打掉多少个时钟**记下来并打印（`ncr=`）。

插卡那天如果看到 `ncr=60` 之类的大数，就知道是"卡慢但在"；如果 `ncr=64` 且 `waitbits=0xffffffff`，
才是真的没卡。这比一个"TIMEOUT"有用得多。

### 43.3 提速失败原来会直接崩掉整轮（第三名）

识别阶段必须 100~400 kHz，但格式化 64 MB 要写一千多个块；所以识别完要提速（`half=300 → 40`）。
位翻转的时钟是靠忙等循环"凑"出来的，卡能跑多快事先谁也不知道 ——
原来提速后一旦读不出来，整轮就失败，而且日志里看不出"是提速的问题"。

改成 `sd_bit_speed_probe(SD_HALF_FAST, blk)`：

```
speed: half 40 failed (rc=-4), fall back to 300      → 继续，只是慢
speed: half 300 failed (rc=-4)                       → 真的坏了
```

返回 1=高速可用 / 0=已退回慢速 / -1=两种速度都不行。慢速能读就说明卡没问题，只是慢；
12 倍慢也比"整轮失败、重来一次"划算。

### 43.4 这一轮的数字

| 项 | 结果 |
|---|---|
| 主机侧检查 | **33/33 通过**（新增 6 项 CRC 已知答案） |
| 板上程序 | 5 个全部编译通过（`sd_wr_test` / `sd_bit` / `sd_fat_sd` / `sd_fat_sd_syn` / `sd_dump`） |
| `_stack_top` | `0x8390 / 0x6208 / 0x89C8 / 0x88C8 / 0x62E8`，全部 < 0x2_0000 |

### 43.5 边界（还是没变）

位翻转时序仍未在真引脚上成功过一次；板子仍需断电重上。这一轮**没有动硬件**。

## 44. 位级仿真：把位翻转驱动接上一个"会应答的卡"，抓出 1 个致命 bug（2026-11-18）

### 44.1 为什么做这件事

`sw/ps/sd_bit_bus.c` 是整条 SD 通路里**唯一从没和任何"会应答的东西"说过话**的一层。
它只在真板上对着**空卡槽**跑过，结果永远是"CMD8 超时"。所以帧格式、位序、CRC7、
CMD 线换向、48 位响应解析、数据阶段 —— 全都只是"看着对"。

板子又一直不可用（DAP 粘滞），于是换了个办法：在 PC 上拦掉 GPIO 寄存器
（`tools/ps/host/sim/xil_io.h` 把 `Xil_In32/Xil_Out32` 重定向到模拟器），接一个
**按位应答的 SD 卡模型**，然后原封不动地跑真代码：

```
sd_bit_init() → sd_bit_powerup() → sd_bit_card_init()
  → sd_read_block() / sd_write_block()      (sd_wr.c)
  → sd_record_to_card()                     (sd_record.c，产品路径)
  → fat32_format() / fat32_write_file()      (fat32.c)
```

卡模型按 SD 物理层规范（1-bit）实现：命令 48 位、**自己重算 CRC7**、R1/R3/R6/R7=48 位、
R2=136 位、CMD0 无响应、CMD17 发 2×0xFF + 0xFE + 512 + CRC16、CMD24 收数据并**重算 CRC16**、
数据响应令牌 0x05 + 忙 16 个时钟。总线空闲（全 1）时**只在看到起始位 0 才开始收命令**，
和真卡一样。

```powershell
powershell -NoProfile -File tools\ps\host\build_sim.ps1
```

### 44.2 抓到的 bug：每个响应都左移了一位（致命）

第一次跑，卡"应答了"，但内容全是废的：

```
[2] CMD8 -> ok resp=0x000000d5 (期望 &0xFFF=0x1AA)
[3] ACMD41 -> OCR=0xe07fc000      (应该是 0xc0ff8000)
[5] CMD3 -> RCA=0x891a            (应该是 0x1234)
[6] CMD7 -> R1=0x80000000         (R1 里凭空多出 bit31"错误位")
```

规律很清楚：**每个值都是正确值右移一位**（0x1AA→0xD5、0xC0FF8000→0xE07FC000、0x1234→0x891A）。
根因在 `rd48()`：

```c
for (i = 0; i < 6; i++) { (void)rx_bit(); }   // ← 错：只跳过 6 位
```

48 位响应是 `0(起始) | 0(传输位) | cmd[5:0] | 内容[31:0] | crc7[6:0] | 1(结束)`，
起始位之后要跳 **7 位**（传输位 + 6 位命令号），而代码只跳了 6 位 —— 于是"内容"从
**传输位**开始读，整体左移一位。

真卡上的后果：RCA 是错的 → CMD7 选不中卡；R1 里多出 0x80000000 → `sd_read_block()`
直接当成"R1 报错"返回 `-2`。现象是"卡明明有应答，但之后全都失败"，
比"没响应"难查得多。

**这一条要是等插卡才发现，大概率会怀疑卡、怀疑接线、怀疑时序，唯独不会怀疑一位偏移。**

### 44.3 修完之后的完整结果（21/21）

```
  [ok] sd_bit_init = 0            (CLK 自检：写 1 读 1)
[2] CMD8 -> ok resp=0x000001aa
[3] ACMD41 -> OCR=0xc0ff8000 after 1 tries
[5] CMD3 -> RCA=0x1234
[6] CMD7 -> R1=0x00000000
```

## 45. 板子救回来了半小时：`rst -dap` 能清 DAP 粘滞错误（2026-11-18）

### 45.1 发现：不用断电也能救

§40.9 / §43.5 一直说"板子卡在 DAP 粘滞状态、只能拔电"。这一轮试出了一个办法：

```
1  DAP (APB AP transaction error, DAP status 0x30000021)
2  xc7z020

→  1* APU
```

`not supported`）。清掉之后 A9 目标立刻回来，接着跑 `sd_bit.elf` **成功**
（就是那种"跑完打日志"的成功）。

### 45.2 但它只能救一次

`Memory write error at 0x0. AP transaction timeout`；此后状态变成
**`0xF0000021`（A9 目标自己在报 APB 错误）**，`rst -dap` / `rst -system` /
`rst -processor` / `stop` 全部无效：

```
apb_ok (initial)                = 0
apb_ok after rst -dap           = 0
apb_ok after rst -system        = 0
apb_ok after rst -processor     = 0
apb_ok after stop+rst           = 0
```

（`_diag/_dap_probe.tcl` 就是这段"逐个组合试、用一次 OCM 读判断通没通"的脚本。）

### 45.3 一条重要旁证：JTAG 和 PL 是好的

同一个会话里 `fpga -f _baseline_v9/board_top_ps_rec_S5.bit` **成功了**
（PCAP 不经过 PS 的调试 APB）。所以：

| 通道 | 状态 |
|---|---|
| JTAG 扫描链 / PL 配置 | ✅ 正常 |
| PS 的调试 APB（dow / mrd / rst -processor） | ❌ 卡在 AP 错误 |

也就是说问题只在 PS 侧，**拔电重上是最干净的解法**（这次是真的拔电，不是软件复位）。

### 45.4 顺手改了运行脚本的行为（避免再把自己搞死）

`_diag/ps_run_sd.tcl` 原来每次都先做 **PSS 软复位**（`SLCR 0xF8000200 = 1`，
当年为了清 SDHCI 的 `CMD_INHIBIT`）。但：

- 位翻转那套程序**完全不用 SDHCI**，这个复位没有意义；
- 而这个 PS 一旦被 PSS 软复位，调试 APB 就很容易变成 `AP transaction timeout`。

所以现在改成：

| 改动 | 效果 |
|---|---|
| PSS 软复位改成**默认关闭**，要清 SDHCI 时显式 `$env:PS_SOFTRESET='1'` | 位翻转程序不再无谓复位 |
| 开跑前先检查 A9 在不在，不在就自动 `rst -dap`（最多 3 次） | 能自愈的情况自动恢复 |
| `dow` 失败自动重试 3 次（每次先 `rst -dap` + `rst -processor`） | 偶发错误不白跑 |
| 日志解码按 §40.9 的教训用**十进制**（`mrd -value` 返回十进制） | 不再解出乱码 |

### 45.5 这一轮唯一的新硬件证据

`sd_bit.elf` 在救回来的板子上跑了一次（**插卡前**的基线）：

```
gpio: MIO=0x0700 CLK-follow=1 DATA_RO=0xffff
=== SD Mode (1-bit, bit-banged over MIO) ===
half=300 (~333 kHz)
[1] CMD0 sent (no response expected)
[2] CMD8 -> TIMEOUT resp=0x00000000 idle=1 waitbits=0xffffffff ncr=64
RESULT FAIL_card_init step=1 waitbits=0xffffffff
```

`ncr=64` 是上一轮新加的诊断：**在规范允许的完整窗口（64 个时钟）内，CMD 线一直是高**，
所以"没卡"这个判断现在是有窗口覆盖的，不是"扫了 32 位就下结论"。

### 45.6 另一个小改进：把"选哪些扇区"抽成共享函数

`sd_dump.c` 里"从 BPB + 目录项算出要 dump 哪些扇区"这段逻辑原来是第二份实现

主机侧检查因此从 33 项涨到 **37 项，全通过**。

真引脚上一次都没成功过（没卡）；调试 APB 现在卡在 `0xF0000021`，**必须拔电重上**。
板子恢复后第一件事仍然是：插卡 → 跑 `sd_bit` → 跑到 `sd_fat_sd_syn` → `sd_fat_sd` → `sd_dump`。

## 47. 手册复核：XADC 的三处引出 + DAC 极性订正（2026-11-18 21:40）

### 47.1 起因

S2 卡在"AD11 读数恒 0"。用户指出手册第 39 页的 XADC 模块表只列了 J12/J21
（AD10/AD2），与本项目一直用的 AD11(A18/A19) 对不上。于是把
`参考文献EES331_UserManual_v1.0_1220.pdf` 读完，结论如下（页码 = PDF 页）。

### 47.2 板上 XADC 引出**三处**，不矛盾

| 手册 | 连接器 | 引脚标号 | FPGA 脚 | 通道 | DRP |
|---|---|---|---|---|---|
| §16（第 20/21 页）| J5-9 / J5-10 | `IO_L12P(xadc11P)` / `IO_L12N(xadc11N)` | **A18 / A19** | AD11 | 0x1B |
| §16（同上）| J5-13 / J5-14 | `IO_L10P(xadc6P)` / `IO_L10N(xadc6N)` | V13 / W13 | AD6 | 0x16 |
| §27（第 39 页）| J12-1 / J12-2 | `AD10P_35` / `AD10N_35` | **B16 / B17** | AD10 | 0x1A |
| §27（同上）| J21-1 / J21-2 | `AD2P_35` / `AD2N_35` | **C15 / B15** | AD2 | 0x12 |

§27 表下原文：**"XADC 接口在扩展 IO-J5 和底板扩展 IO-FX8 上也有引出，均可正常使用。"**

所以 J5 与 J12/J21 是**两组不同接口、不同通道**。本项目文档写 J5-9/10 = A18/A19
**是对的**（中途我一度误判成"没有依据"，已撤回，见 §47.7）。
手册第 39 页那张表里第 4 行写成 `AD10P_35 | B17`，按差分对推断应为 `AD10N`。

另：§16 原文"除了电源和 GND 外，每个 IO 都串联一个 200R 的电阻起到保护作用"。
200 Ω 只抬源阻抗，不影响直流电平（XADC 输入高阻）；分压 330∥100 = 77 Ω，
加 200 Ω 后 277 Ω，远低于 10 kΩ，可用。

### 47.3 DAC 极性：全项目写反了

§17（第 21 页）原文：

```
DAC_VREF = -5V*4.7K/(4.7K+1.2k)=3.98V
```

是**负参考**（−3.98 V）。原理图：`IOUT1(11)→LM324 反相端(2)`、
`IOUT2(12)→同相端(3)` 并 0 Ω 到地、`RFB(9)→输出`，输出接到 **J2-1（丝印 `VOUT_0832`）**。

负参考送进反相运放 = **两次反相抵消**，输出与码值**同向**：

| 码 | 输出 |
|---|---|
| 0x00 | 0 V |
| 0x80 | ≈1.99 V |
| 0xFF | **+3.98 V** |

以前按"反相"写（`dac_code` 复位 0xFF 当成 0 V），是只看了运放拓扑、漏了 VREF 的负号。
两处影响：
1. `adctest` 的扫频方向与期望值**全反**（已改成 0x00→0xFF 升序，并加期望 mV 列）；
2. 复位值 0xFF 实际是**满量程** 3.98 V。经 1:4.3 分压后是 0.926 V，仍在 XADC 的
   0~1 V 之内，所以位流不为此重建；但**绝不允许去掉分压直接接**（会打 XADC）。

### 47.4 为什么仍然不用 AD6

AD6 = V13/W13 在 Vivado 里只接受 LVCMOS18，而 bank 35 在板上是 3.3 V，
place 阶段直接 `[DRC BIVC-1] Conflicting Vcc voltages in bank 35`。AD11/AD10/AD2 无此问题。

### 47.5 为此做的位流：`board_top_rec_S2_3ch`

| 项 | 值 |
|---|---|
| 模拟输入 | AD11 + AD10 + AD2 **三路全接**进 XADC 原语 |
| `INIT_42` | 0x0840 → **0x0C04**（VAUX11+VAUX10+VAUX2；同时去掉一直悬空、白扫的 VAUX6）|
| VIO `probe_out3` | 新增 2 位 `ch_sel`：**0=AD11(J5-9/10) / 1=AD10(J12) / 2=AD2(J21)** |
| XDC | 新增 `B16/B17/C15/B15`，**且必须显式写 `IOSTANDARD LVCMOS33`** |

## 48. S2 的真根因：XADC 辅助通道从来就没被转换过（2026-11-19 00:10）

### 48.1 一句话

`INIT_41 = 0x3100` 的 SEQ 字段是 **0011 = 单通道模式**，不是「连续序列」。
于是 ADC 一直在转 Config1 里那个固定通道（= 片内温度），**16 个 VAUX 结果寄存器
从来没被更新过** —— 读 `DADDR=0x1B/0x1A/0x12` 永远返回 0。

这跟「引脚上没有信号」长得**一模一样**。从 11-16 起本项目的结论
「AD11 恒 0 = 缺那根线的指纹」（§35.1）就是建立在这个误判上的，**全部作废**。

### 48.2 正确的寄存器分工（UG480 表 4-1/4-2）

| 寄存器 | 作用 | 旧值 | 新值 |
|---|---|---|---|
| 41h[15:12] | SEQ：0=默认 1=单次 **2=连续序列** 3=单通道 | ❌ 3（单通道） | **2** |
| 48h | **片内**通道：bit8=温度 9=VCCINT 10=VCCAUX 14=VCCBRAM 0=校准 | ❌ 0 | 0x0100（温度）|
| 49h | **VAUX 通道**：bit n = VAUXn（**只有这里能使能**） | ❌ 0 | 0x0C04（VAUX11/10/2）|
| 42h | Config2（DCLK 分频等），**与通道选择无关** | ❌ 当成序列寄存器 | 0x0400（DCLK/4）|

交叉核对来源：UG480 表 4-1/4-2 + betrusted-soc `hal_xadc.rs`
（`XadcSeq1Mask::Vaux11 = 0x0800`、`Vaux10 = 0x0400`、`Vaux2 = 0x0004`）。

序列长度 4 → 每通道刷新 ≈ 250 kSa/s，高于 200 kHz 轮询。

### 48.3 改完第一次读到真值（位流 `board_top_rec_S2_seq`）

| 通道 | 接线 | `adc_last` | 12 位码 | 换算 mV | 判定 |
|---|---|---|---|---|---|
| AD11 | J5-9/10（**没接**）| 0x0000 | 0 | 0 | 表上确实没信号 |
| AD10 | J12 | **0x395D** | 917 | **223** | **SIGNAL** |
| AD2 | J21 | **0x4026** | 1026 | **250** | **SIGNAL** |
| 片内温度 | — | 0xA13A | 2579 | 44.1 °C | 正常 |

这是本项目**第一次**从外部模拟引脚读回非零值，且两个通道读数不同
（223 vs 250 mV），排除了「两条线短在一起」。

### 48.4 还没解释的：绝对幅度只有预期的 1/4

`dac_code = 0xFF` 时，若 DAC 满量程 3.98 V、分压 1:4.3，AD10 应读到 **926 mV**，
实测 223 mV（≈ 1/4.2）。两个可能：
1. ~~板上 VREF 电位器被调小~~ —— **这条已排除**：手册第 22 页「参考电压生成图」显示 VREF 是
   **固定分压**（−5V —[R231 1.2K 1%]— DAC_VREF —[R229 4.7K 1%]— GND，另有 R49 标 `0/NC`
   是"可选短接到 +5V"的装配位），**板上没有可调电位器**。
   ★ 由此还有一条分支必须排除：若 R49 装了 0 Ω，VREF ≈ **+5 V**，DAC 输出就变成
   **0 ~ −3.98 V（负压）**，经分压后是负电压送进 XADC（单极性模式会钳到 0）。
   所以测量时务必确认 J2-1 的**极性**（红笔接 J2-1、黑笔接地；若显示负值就是这一支）；
2. 分压电阻实际不是 100/330（或串了两组）。

**判据**：让 DAC 自己扫一遍（三角波），读数必须**跟着动**且线性 —— 这不需要
知道绝对满量程，也不需要万用表。为此把三角波使能从 `ch_sel==3` 改成
`trig_selftest`（它只接触发单元，与 ADC/DAC 无关），这样三个口都能在斜坡下观察。

### 48.5 流程教训

一条「看起来自洽」的解释（读数 0 = 没接线）会把 bug 藏很久：它让所有后续动作
（量针脚、调 P/N、怀疑供电）都建立在错误前提上。以后凡是「某路读数恒 0」，
**先证明那一路确实被转换过**（切到已知有源的通道 / 打开序列器），再谈接线。

### 48.6 三角波验证：DAC 的码值**没有**体现在引脚电压上（2026-11-19 00:55）

为了把「绝对幅度只有 1/4」这件事查清楚，把三角波使能从 `ch_sel==3` 改到
`trig_selftest`（`probe_out2`，只接触发单元），做成位流 `board_top_rec_S2_ramp2`，
于是三个口都能在斜坡下逐个观察。实测：

| 检查 | 结果 |
|---|---|
| `trig_selftest` 写入是否生效 | ✅ `trig_cnt` 1 秒内 25016 → 28318（+3302 ≈ 3125/s），VIO 写入确实有效 |
| AD10（J12）斜坡下的 min/max | 933 / 942（**spread 9 码 ≈ 2.2 mV**）|
| AD2（J21）斜坡下的 min/max | 1040 / 1051（**spread 11 码 ≈ 2.7 mV**）|
| AD11（J5-9/10，未接线） | 0 / 0 |

结论：DAC 码值每 2 ms 变一次、全摆幅 1 秒，**读数却基本不动**。
所以 J12/J21 上那 222/250 mV **不是 DAC 输出经分压来的**，更像悬空引脚的固定偏置。

⇒ 目前能确认的只有一步：**XADC 的辅助通道确实在转换了**（这是今天最大的进展，
之前它们根本没被转换过）。而「DAC → 分压 → 引脚」这一段仍未验证。

### 48.7 下一步的判定顺序（不需要串口）

| # | 观察 | 判据 |
|---|---|---|
| 1 | 斜坡模式下用万用表量 **J2-1**（`VOUT_0832`）| 读数应在 0~4 V 之间**缓慢摆动**（三角波 1 s 周期）。稳在某个值 → DAC 没收到数据 |
| 2 | 量分压节点（330/100 交点）| 应同步摆动，幅度约为 J2-1 的 1/4.3 |
| 3 | 量 **U24-19（ILE/BYTE2）** | 应为 3.3 V。板上若有 DIP/跳线选择 DAC 数据源，先确认它接的是 FPGA |
| 4 | 量 U24-13/14（D7/D6）| 斜坡下应看到电平变化（或万用表读数不稳）|

第 1 步最关键：**它把「DAC 有没有在动」和「线通不通」彻底分开**。

### 48.8 把「FPGA 侧到底有没有在动」也变成证据（2026-11-19 01:45）

为了不让「DAC 不跟随」只剩推测，把 VIO 的 `in19` 从 `dac_code`（MMIO 寄存器，
永远 0xFF）改成 **`dac_byte`（真正送到 DAC 引脚的那个字节）**，做成位流
`board_top_rec_S2_dacbyte`（WNS **+0.653** / WHS **+0.015**）。

三角波打开后连采 12 次：

```
samples: 255 255 167 167 167 86 86 86 167 167 167 89
dac_byte|min=86|max=255|spread=169|verdict=DAC_BYTE_RAMPING
```

（同一值连续出现 3 次是 VIO 探针读值有缓存，不是不变化；看 spread 即可。）

⇒ **FPGA 侧确定在扫**（86 ~ 255，Δ169 码）。同一时刻 AD10/AD2 的读数只动 2~3 mV。

这一条把责任彻底分开：**问题在板级**，不在 RTL。
剩下三种可能，按可能性排序：

| # | 可能 | 现场判据 |
|---|---|---|
| A | DAC 芯片没收到数据（U24-19 不是 ILE / 数据线没通 / 板上真有跳线）| 斜坡下量 U24-13/14（D7/D6）是否在跳；量 U24-19 是否 3.3 V |
| B | DAC 有输出但被分压拉垮（430 Ω / 9.3 mA 对 LM324 太重）| 斜坡下量 J2-1：空载摆 0~4 V、接上分压后塌在某个值 → 换 3.3k+10k |
| C | 分压中点没真接到 ADC 脚 | 量插进板子的那个针脚，应与分压中点同电压 |

### 48.9 顺带订正一条来源可疑的注释

`board/dac0832.sv` 原来写「若 DAC 输出恒为 0，先把 **DIP** 的这根改 0」——
复核手册 §17 原理图：CS#/WR1#/WR2#/XFER# 全部直连 FPGA，**手册里没有 DAC 相关的
DIP 开关或跳线**。这句是从别的板子带过来的说法，已改成「先量 U24-19 电平、
再量 D7/D6 在斜坡下是否跳变」。
