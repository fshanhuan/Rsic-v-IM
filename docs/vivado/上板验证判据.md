## 0. 前提：烧进去的程序是什么

`prog.hex`（14 条指令，就是仿真里的 `prog`）。**PC → 指令 → 预期写回值**：

| # | PC | 编码 | 反汇编 | 写回寄存器 | 预期 `probe4` 值 |
| --- | --- | --- | --- | --- | --- |
| 1 | `0x00` | `000010b7` | `lui x1, 0x1` | x1 | `0x00001000` |
| 2 | `0x04` | `00500113` | `addi x2, x0, 5` | x2 | `0x00000005` |
| 3 | `0x08` | `00700193` | `addi x3, x0, 7` | x3 | `0x00000007` |
| 4 | `0x0C` | `00310233` | `add x4, x2, x3` | x4 | `0x0000000C` (12) |
| 5 | `0x10` | `023102b3` | **`mul x5, x2, x3`** | x5 | `0x00000023` (35) |
| 6 | `0x14` | `0040a023` | `sw x4, 0(x1)` | x0 (`ena=0`) | `0x00001000`（这里显示的是**地址**） |
| 7 | `0x18` | `0000a303` | **`lw x6, 0(x1)`** | x6 | `0x0000000C` |
| 8 | `0x1C` | `002303b3` | `add x7, x6, x2` | x7 | `0x00000011` (17) |
| 9 | `0x20` | `00310463` | **`beq x2, x3, +8`**（5≠7，**不该跳**） | x8 (`ena=0`) | `0x00000000` |
| 10 | `0x24` | `00310433` | `add x8, x2, x3` | x8 | `0x0000000C` |
| 11 | `0x28` | `0080006f` | **`jal x0, +8`**（跳过 `0x2C`） | x0 | `0x0000002C` |
| 12 | `0x2C` | `7ff00493` | `addi x9, x0, 0x7ff` | — | **永不执行**（被 jal 跳过） |
| 13 | `0x30` | `03f06513` | `ori x10, x0, 0x3f` | x10 | `0x0000003F` (63) |
| 14 | `0x34` | `00000073` | **`ecall`** | — | `probe12` 出脉冲 |

### ★ 一个必须先知道的事实：程序不会"跑完停下"，它会**永远重跑**

`ecall` 触发异常后，`dnpc = mtvec`，而 `mtvec` 复位值是 **0**（`CSR.RESET_VAL=0`）。
所以 CPU 跳回 `PC=0x00`，把上面 14 条**从头再执行一遍**，无限循环，一圈约 **70~80 拍 ≈ 1.5µs**。

> ⚠️ **上面这句话在 v9 B9 修复之前是"设计意图"，不是"板上事实"。**
> 实测（ILA 逐拍数据）当时 PC **根本没有跳回 0**，而是一路顺序爬行、每绕 IROM 一圈
> （16KB，`pc[13:2]` 掩码使得取指内容仍然正确）才又撞上一次 `ecall`，
> 所以现象是"程序看着在跑、数据也算得对，但控制流完全错了"。
> 已修（`rtl/IFU.sv` 去掉重定向分支的 `& ready`），详见
> [`ecall重定向故障_根因与修复.md`](ecall重定向故障_根因与修复.md)。

这对验证是**好事**：

* ILA 触发条件一定会命中，不需要"抢一次性事件"；
* 2048 点深度 ÷ 50MHz = **40.96µs ≈ 25 圈**，一次抓取就能看到重复的整圈模式。
* 而且"同一个写回序列反复出现"本身就是**重定向生效的旁证** ——
  若序列单调向前、从不回头，就是 B9 那个故障。

## 2. ① 心跳灯 LED0（V4）怎么读

`debug_dead` 的定义（`board/board_top_ila.sv` 末尾）：

```systemverilog
assign debug_dead = |{debug_wb_have_inst, debug_wb_ena,
                      debug_wb_pc, debug_wb_reg, debug_wb_value,
                      debug_icache_hit_cnt,  debug_icache_miss_cnt,
                      debug_dcache_hit_cnt,  debug_dcache_miss_cnt,
                      debug_mcause, debug_mepc, debug_mtval,
                      debug_trap_take,
                      debug_dnpc_flag, debug_ready, debug_ifu_pc};   // ← v9 B9 新增
```

即 **16 个调试量的"或"**（v9 B9 之前是 13 个），接 LED0。

* **LED 极性**：EES-331 手册 §20 的原理图是 `FPGA 引脚 → 560R → LED → GND`，
  所以是**高电平点亮**（`debug_dead=1` → 亮）。
* **计数器复位**：`ICache`/`DCache` 的 `hit_cnt`/`miss_cnt` 都在 `reset` 时清 0
  （`rtl/ICache.sv:149`、`rtl/DCache.sv:235`）。

于是：

| 操作 | 预期 | 含义 |
| --- | --- | --- |
| 按下 S1（L18）不放 | **灭** | 复位有效，计数器被清 0 |
| 松开 S1 | **常亮** | 时钟锁定 + **至少退休了一条指令**（写回值/计数器非 0） |
| 松开后仍灭 | ✗ 故障 | 见 §8 |
| 按复位时灯不灭 | ✗ 故障 | 按键/引脚不对（应为 L18，低有效） |

> ⚠️ 灯是**粘滞**的：一旦亮过，即使 CPU 之后卡死也仍然亮（计数器不回零）。
> 所以"想知道它此刻还在不在跑"，必须**按一下 S1**：应该灭→再亮。
> 这是这块板上唯一不需要 PC 的动态判据。

## 3. ②③ ILA 怎么抓

1. `Open Hardware Manager` → `Open Target` → `Auto Connect`
   （EES-331 用板载下载器；找不到就按手册 §6 把 SW8 拨成"板载调试器"，并检查 JP6/JP7）。
2. `Program Device` → 选 `board_top_gui.bit`。烧完 `hw_ila_1` 应自动出现（没有就 `Refresh Device`）。
   探针文件是同目录的 `board_top_gui.ltx`，一般自动带上。
3. 打开 `hw_ila_1` 波形窗口。

**探针 ↔ 信号**（`.ltx` 里存的就是这些真名，波形窗口直接显示，不需要换算）：

| 探针 | 信号名 | 位宽 |
| --- | --- | --- |
| probe0 | `debug_wb_have_inst` | 1 |
| probe1 | `debug_wb_pc` | 32 |
| probe2 | `debug_wb_ena` | 1 |
| probe3 | `debug_wb_reg` | 5 |
| probe4 | `debug_wb_value` | 32 |
| probe5 | `debug_icache_hit_cnt` | 32 |
| probe6 | `debug_icache_miss_cnt` | 32 |
| probe7 | `debug_dcache_hit_cnt` | 32 |
| probe8 | `debug_dcache_miss_cnt` | 32 |
| probe9 | `debug_mcause` | 32 |
| probe10 | `debug_mepc` | 32 |
| probe11 | `debug_mtval` | 32（v9 B9 已补 `assign mtval_out`，现在有真值） |
| probe12 | `debug_trap_take` | 1 |
| **probe13** | `debug_dnpc_flag` | 1（重定向请求，**v9 B9 新增**） |
| **probe14** | `debug_ready` | 1（IFU 的 `ready`，**v9 B9 新增**） |
| **probe15** | `debug_ifu_pc` | 32（取指级 PC，**v9 B9 新增**） |

> **probe13/14/15 是上板定位 `ecall` 重定向失败时加的诊断探针**，
> 用法见 [`ecall重定向故障_根因与修复.md`](ecall重定向故障_根因与修复.md) §8：
> **`probe13`（请求有没有发）× `probe14`（那一拍 ready 是不是 0）**
> 就能分辨"请求没发"和"请求被背压吃掉"。

### 3.1 第一次抓：**先不设触发**（确认采样时钟活着）

`Trigger Setup` 面板空着就等于"立即触发"（全局触发 = 1）。直接点工具栏的
**▶ Run trigger**，一秒内就该抓满 2048 点。这一步本身就是最有力的诊断：

| 现象 | 结论 |
| --- | --- |
| 抓满 2048 点，`debug_wb_pc` / 计数器是**非 0 的跳变值** | ✅ 采样时钟（50MHz）活着 + CPU 在跑 → 进 §3.2 设真触发 |
| 抓满 2048 点，但**全是 0** | 时钟活着，但 CPU 被按在复位态 → 查按键 **L18** / `reset_sync` |
| 一直停在 `Waiting for Trigger` / `Arming`，数据回不来 | ✗ **采样时钟没跑** → MMCM 没锁（`CLKFBIN`）或 M19 没时钟 |

> ⚠️ 刚打开 ILA 时图里 Value 列显示的 `00000000` 是**占位值**
> （此时 `Window sample 0 of 2048`、Status = `Idle`），
> 在真正抓过一次之前**不能**当作"CPU 没跑"的证据。
>
> 配合板上 **LED0**：按住 S1 灭、松开常亮 = 时钟 + 复位 + CPU 这条链是通的。
> 这是不用电脑、10 秒就能做完的第一步。

### 3.2 最省事的触发条件

| 目的 | 条件 |
| --- | --- |
| 抓一整圈 | `probe1 == 0x00000000`（Basic，`==`） |
| **一次就验证 ALU+乘法器** | `probe1 == 0x00000010` |
| **一次就验证存/取通路** | `probe1 == 0x00000018` |
| **一次就验证分支不误跳** | `probe1 == 0x00000020`（若抓到 `0x2C` 说明 beq 误跳） |
| 抓异常现场 | **不要用 `probe12` 上升沿**（对本程序永远不命中，见 §5.1）；直接看 `probe9`/`probe10` 的恒定值 |
| **验证 `ecall` 重定向（v9 B9 新增，最重要的一条）** | `probe15 == 0x00000000`（Basic，`==`）—— 抓得到 = PC 真的回到了 `mtvec` |
| **诊断"重定向请求有没有发"** | `probe13 == 1`（抓所有重定向），配合看 `probe14` |

**在 GUI 里怎么设**（`Trigger Setup - hw_ila_1` 面板）：

1. 点绿色 **+** → 弹出探针列表 → 选 `debug_wb_pc[31:0]` → OK；
2. 接着在 **+** 右边的下拉里给 `debug_wb_value` 也加进**观察窗口**（不是触发条件）；
3. 在触发行填 `Operator = ==`、`Radix = H`、`Value = 00000010`；
4. 把捕获模式设成 **ALWAYS**、`Trigger position in window` 放中间
   （这样触发点前后各留一半窗口，一眼能看到整圈写回序列）；
5. 点 **▶ Run trigger**。

因为程序无限循环，设好条件后 1~2µs 内必然命中，不需要按复位配合。

## 4. ③ 五个"单点决定性"检查

抓到波形后，按顺序看这五个地方，每个都能单独定位一大块功能：

| # | 触发条件 | 期望 | 证明/证伪了什么 |
| --- | --- | --- | --- |
| 1 | `probe1==0x10` | `probe4==0x00000023` | **乘法器（MDU）+ ALU** 正确。5×7=35，不是 12（加法）也不是别的 |
| 2 | `probe1==0x18` | `probe4==0x0000000C` | **store→load 往返正确**：`0x14` 的 sw 把 12 写进 DRAM 0x1000，`0x18` 的 lw 读回 12 |
| 3 | `probe1==0x20` 出现且 **`0x2C` 不出现** | `probe3==x8`、`probe2==0` | **beq 正确判定"不跳"**（5≠7）。若抓不到 `0x20` 却抓到 `0x2C`，就是分支误跳 |
| 4 | `probe1==0x30` 出现 | `probe4==0x0000003F` | **jal 跳转正确**：`0x2C` 被跳过，`x9` 永远是 0。若 `probe1` 出现 `0x2C`（且 `probe4==0x000007FF`），jal 没生效 |
| **5** | **`probe15 == 0x00000000`**（`ecall` 之后） | **能抓到，且抓到后 `probe15` 从 0 重新往上走** | **`ecall` 的重定向正确** —— PC 真的跳到了 `mtvec`。**前四条全过也可能栽在这一条**（v9 B9 的真实教训） |

> 补充：`probe0`（`have_inst`）与 `probe2`（`ena`）不等价。
> `sw`/`beq` 是 `have_inst=1` 但 `ena=0`（不写寄存器），这是**正常**的，别当成故障。
> `jal x0` 是 `ena=1` 但 `probe3=0`（写 x0 等于没写），也正常。
>
> ⚠️ **第 5 条是本清单最重要的补丁**：第 1~4 条全部通过、程序仍然有 bug，
> 就发生在这里 —— 详见 §7.1。

## 5. 异常现场（probe9 / probe10 / probe12）

> ⚠️ **`probe12` 对本程序永远是 0，不要拿它当触发条件 —— 见 §5.1。**

| 观察 | 期望 | 含义 |
| --- | --- | --- |
| `probe9 (mcause)` 恒定值 | `== 0x0000000B` | 11 = M 模式 `ecall`，**正确** |
| `probe10 (mepc)` 恒定值 | `== 0x00000034` | 异常 PC 正好是 `ecall` 那条 |
| `probe11 (mtval)` 恒定值 | 应为 0。v9 B9 已补 `assign mtval_out`，但**同步异常检测本身还没修好**（`trap_take` 抬不起来），所以仍然不要拿它下结论，见 §7 |

### 5.1 `probe12`（`debug_trap_take`）为什么恒为 0 —— 触发条件口径修正

**现象**：2026-10-16 00:12 与 2026-10-15 20:54 两次上板抓取，`probe12` 在 2048 拍里**全是 0**。

**这不是故障，是判据把触发对象写错了**：

* `trap_take` 是 Control 的「**同步**异常（非法指令 / 地址非对齐）确认接收」单拍脉冲，
  `rtl/CSR.sv` 用它写 `mcause` / `mtval`（所以它抬不起来时 `mtval` 也就没内容，见 §7）；
* `ecall` 走的是**另一条路**：`ecall_flag` —— `rtl/CSR.sv` 的 `trap_commit`、`mepc_wen`、
  `mcause_reg` 三处都并列带上了它，**本来就不会拉 `trap_take`**；
* `prog.hex` 里只有一条 `ecall`、没有任何同步异常 ⇒ **`probe12` 恒 0 是预期结果**。

**所以**：想观察 `ecall` 现场，**不要**用「`probe12` 上升沿」当触发条件（永远不命中）。改用：

* 触发 `probe15 == 0x00000000`（PC 回到 `mtvec`）—— 这也是 §4 第 5 条；
* 或者干脆不触发：`probe9` / `probe10` 这两个量**任何一次抓取里都在**，直接读恒定值即可。

> 同步异常（非法指令 / 非对齐访存）到底能不能触发，要用 `sim/tb_exc.sv` 单独验
> （现状：`trap_take` 抬不起来，是**独立于本判据的既有缺口**，见 §7）。

**如果 `probe9` 不是 `0x0B`，就是设计出了问题**，对照下表（`rtl/para.sv`/`rtl/CSR.sv` 口径）：

| mcause | 含义 | 板上的可能成因 |
| --- | --- | --- |
| `0x02` | 非法指令 | IROM 初值没进去（BRAM 全 0），或取指数据被 `NOP` 灌死 |
| `0x04`/`0x06` | 取指/访存地址非对齐 | 地址计算错 |
| `0x0B` | `ecall` | ✅ 期望值 |
| `0x8000_000x` | 中断 | 本设计无中断源，出现即异常 |

## 6. 计数器（probe5~8）怎么读：它们是**拍数**，不是次数

`rtl/ICache.sv:167` 的计数条件是 `if (fetch_align)`，即**每个"取指结果有效"的时钟拍加 1**，
不是"每条指令加 1"。仿真里 14 条指令就得到 `ICache hit=50 / miss=15`、`DCache hit=3 / miss=1`
（当前 RTL，含 H1；H1 之前是 `ICache 48/16`），就是因为停顿期间同一个已命中的地址会被反复计数。

所以：

* ❌ **不要**期望板上抓到这几个数。那是"从复位起第一遍"的数值，
  而且仿真测试台还 force 了一个 `WBU.stall`（`tb_iverilog.sv:601`），拍数不必逐拍对齐。
* ✅ 只做**趋势判断**：

| 观察 | 正常 | 异常 |
| --- | --- | --- |
| `probe5/6/7/8` 是否非 0 且在增长 | 是 | 全 0 = 取指/访存通路完全没动 |
| 隔一段时间再抓一次，`probe6`（I-Cache miss） | 基本**冻住**（第一遍之后就命中了） | 与 `probe5` 同速增长 = **Cache 没起作用** |
| `probe7 : probe8`（D-Cache 命中:缺失） | 远大于 1；**miss 每圈也在涨是正常的**（仿真首遍 3:1） | 读数≈1:1 时**先读 §6.1** —— 板上现况就是这样，已定性为"每圈多一次无用 DRAM 读"，**不是 Cache 失效** |

### 6.1 板上 `probe7 : probe8` = 1:1 的定性

**现况**（2026-10-16 00:12 抓取）：`dcache_hit : dcache_miss = 14848907 : 14848905`（≈1:1），
两者**每圈各 +1**；而 2026-10-15 20:54 那次是 `3927546 : 1`（miss 全程冻住）。
**两次抓取的数据都是对的**：`lw x6` 都读回 `0x0000000C`，`sw` 也都把 12 写进了 `dram[0x1000]`。

**根因**（已用"板等价"长跑仿真复现，配方与数据见 `E:\FPGA\v9_vivado_ila\_diag\README.md`）：
H1（`rtl/EXU.sv` 的 `up_stall` 门控）修好官方差分之后，LSU 交给 DCache 的 `sw → lw`
**不再背靠背**；而 `rtl/DCache.sv` 的 `cache_rd_req` 用 `line_resident` 判"该行是否驻留"，
`line_resident` 里含 `resp_valid_r`（比 `cpu_en` **晚 2 拍**）⇒ 一条请求的**第一拍必然读到"不驻留"**，
于是**每圈多发一次 DRAM 读、多记一次 miss**。

**量级与影响**：

* 数据通路**正确**（`lw` 读回 `0x0C`；`sw` 的写直达也没受影响）；
* **不花时间**：把驻留判定换成不等 `resp_valid_r` 的版本后，读请求 0.99/圈 → **0.01/圈**、
  miss 0.988/圈 → **0**，而**一圈仍然是 45.56 拍**（仿真实测，完全不变）；
* 一圈从旧 bit 的 43.6 拍变成 45.5 拍，是 **H1 的额外停顿**（`IFU_stall` 37.4% → 43.5%）造成的，
  **与 D-Cache 无关**。

**结论**：这一条**不作为"D-Cache 失效"的判据**。若答辩/评审需要看到"远大于 1"的读数，
用 `_diag\run_long.bat` 的 `fix2` 变体做对照演示即可 —— **交付 RTL 不改**（数据正确、时序无差，
改动收益只是省掉每圈一次无用 BRAM 读）。

## 7.1 `ecall` 之后 PC 去哪了 —— 一个**曾经真实存在**的故障（✅ 已修，v9 B9）

这一节是本清单**最重要的一次更新**，因为在你最初的判据里它是**盲区**。

**旧版判据只检查到"`ecall` 被译码、`mepc/mcause` 写对了"，就判定功能正常。
但没有人检查过 `ecall` 之后 PC 有没有跳到 `mtvec` —— 而它并没有跳。**

板上 ILA 原始证据（2048 拍 ×2）：

| 检查项 | 结果 |
| --- | --- |
| `probe1`（`debug_wb_pc`）是否出现过 `0x00000000` | **从未出现** |
| `probe10`（`mepc`）的不同取值 | `0xDEA78034` → `0xDEA7C034`，**正好差 `0x4000` = 一圈 16KB** |
| `probe9`（`mcause`） | 恒 `0x0B`（`ecall` 确实被识别并登记了） |

`mepc` 每绕 IROM 一圈才变一次 ⇒ **PC 每绕一圈就回到 `0x34` 再执行一次 `ecall`，
然后继续顺序爬行**，如此无限循环。

**根因**：`rtl/IFU.sv` 用 `dnpc_flag & ready` 门控真实重定向，而 `ecall`/`mret`/`fence.i`
的 `dnpc_flag` **只有一拍宽**（IDU 在 `flush=dnpc_flag` 那一拍就把译码级灌成 NOP），
撞上取指 hold 拍（`ready=0`）就**永久丢失** —— 实测 `0x34` 的 `ecall` **正好**命中。
**已修成 `else if (dnpc_flag)`。**

**新增的判据（请加进你的检查表）：**

| 检查 | 预期 | 判据 |
| --- | --- | --- |
| 触发 `probe15 == 0x00000000`（或 `probe1 == 0x00000000`） | **能抓到** | `ecall` 后 PC 确实回到 `mtvec`。**抓不到 = 重定向失效** |
| 触发 `probe13 == 1`（任意重定向），看 `probe14` | `probe13=1` 时 PC 下一拍就是目标 | `probe13=1` 且 `probe14=0` 且 `probe15` 没变 = 被背压吃掉 |
| `probe10`（`mepc`）在一段窗口内 | **保持不变** | 若它反复按 `+0x4000` 变化，说明程序在绕圈重跑 = 重定向失效 |

完整的定位过程、根因推导与仿真复现见
[`ecall重定向故障_根因与修复.md`](ecall重定向故障_根因与修复.md)。

> **这段经历的意义**：原判据的四个"决定性单点检查"全都通过，程序却是有 bug 的。
> 教训是 —— **判据必须覆盖"控制流去了哪"，不能只覆盖"数据算得对不对"。**
