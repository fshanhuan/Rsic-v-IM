## P1-1　`run <file>`：从文件系统加载并执行 C 应用　✅

### 之前为什么失败（三个原因，逐个修掉）

| # | 原因 | 现象 |
|---|---|---|
| 1 | 应用被直接跳进 `main`（`0x5034`），`gp` 还是 **shell 的** `__global_pointer$` | 全局变量/常量读到 shell 的数据 |
| 2 | 应用的 `.rodata/.data` 链到 `0x1_0000`，但那正是 **shell 自己的 .data/.bss** | 应用写穿了 shell 的命令表 |
| 3 | `.bss` 没人清，`sp` 还是 shell 的栈 | 深调用/局部数组和 shell 栈帧重叠 |

三者任一都会让应用跑飞 → 异常 → `mtvec=0` → **从 0 重启 → 又打出 shell 横幅**。
上一轮看到的"`run hello 5034` 打出横幅"就是这个。

### 修法

1. **`sw/app/start.S`**：入口桩（放在 `.text` 最前面，= 镜像基址）
   - 把 shell 的 `gp/ra/sp` 存进应用 `.data` 的 `app_shell_ctx`；
   - `gp` = 应用的 `__global_pointer$`，`sp` = 应用私有栈顶 `__app_stack_top`；
   - 清应用自己的 `.bss`；
   - `call main` → 回来后**原样还原** shell 的 `gp/ra/sp` → `ret`。
   - `app_shell_ctx` 必须在 `.data` 而不是 `.bss`：清 `.bss` 会把它擦掉，回来就是 `gp=0`。
2. **`sw/app/link_app.ld`**：`irom 0x6000 / 40K`、`dram 0xA000 / 20K`、
   `__app_stack_top = 0xF000`，并 `ASSERT` 数据段不许越过栈底。
3. **容器格式**（`sw/mkapp.py`）：32 B 头 + 代码 + 数据
   `magic 'BAPP' | irom_base | irom_len | dram_base | dram_len | entry | sum | hdr_words`
   —— 一条 `run` 完成"装代码 + 装数据 + 跳入口"，且带**校验和**（串口丢字节当场报错）。
4. **`sw/monitor.c` `c_runf`**：认容器也认裸镜像；代码只准落在 `>= IROM_APP_MIN`
   （运行期由 `_etext` 算），数据只准落在 `0xA000~0xFFFF`；按**字**拷贝
   （IROM 窗口的写通路是整字写使能，逐字节 store 会变成读-改-写）。
5. **DRAM 三段划分**（全 128 KB 都用上）：

   | 区间 | 用途 |
   |---|---|
   | `0x0_0000 – 0x0_9FFF` | ramdisk 文件系统 40 KB（160 块 × 256 B） |
   | `0x0_A000 – 0x0_FFFF` | 应用 `.rodata/.data/.bss`（20 KB）+ 应用私有栈（4 KB） |
   | `0x1_0000 – 0x1_FFFF` | shell 自己的 `.rodata/.data/.bss/栈` |

### 板上实测（原始回显）

```

hex8, '.'=end
```

三句话各自证一件事：

- `HELLO-APP from IROM 0x6000`：`.rodata` 真的被装进 DRAM `0xA000` 且能 `lw` 读；
- `acc=15`：`.data` 读写正常，`.bss` 清零由桩完成；
- `returned to shell` + 提示符 `>`：`gp/ra/sp` 还原成功，**shell 没被应用搞坏**；
- 连续 `run` 两次结果一致（上面第二次也是 `acc=15`）。

## P1-2　文件系统空间回收　✅

`sw/monitor.c` 的 ramdisk 从"bump 分配（删了不回收）"换成**位图 + 连续分配**：

- 40 KB = 160 块 × 256 B；块 0 超级块、块 1..3 目录（32 项 × 24 B）、块 4 位图、块 5.. 数据；
- `fs_alloc(n)` 找**连续 n 块**并标记；`rm` 把 n 块清回位图 → `df` 真的变多。

板上实测（同一次上电内连续四条命令）：

```
> df
 free 152 / 160 blocks = 38 KB          ← hello_app 占 3 块
> sa big a000 1f40                       ← 8000 B = 32 块
 saved 8000 B as big
> df
 free 120 / 160 blocks = 30 KB          ← 152 - 32 = 120 ✓
> rm big
 removed
> df
 free 152 / 160 blocks = 38 KB          ← 32 块全部回收 ✓
```

## P1-3　贪吃蛇增量重绘　✅

原来每帧 `ESC[H` 后**整屏重画**：240 格 × 8 B（`ESC[<r>;<c>H` + 字符）+ 边框 ≈ **2.5 KB/帧**，
120 ms 一帧 → 需要 20 KB/s，而链路只有 11.5 KB/s ⇒ **串口被写满、终端滚个不停**（就是用户看到的现象）。

现在（`sw/snake_play.c`）：

- 边框只画一次；`scr[H][W]` 记住"屏幕上现在是什么"，每帧只对**变了的格子**发 `ESC[<r>;<c>H`；
- 一次移动通常只改 2~3 格 ≈ **30 B**；蛇死了画面不动 ⇒ **一个字节都不发**；
- 状态行单独比对，变短时用 `ESC[K` 擦尾巴。

### A/B 实测（同一块板、同 9 s 抓包窗口）

| 版本 | 9 s 内串口字节 | 单帧/单步 | 说明 |
|---|---|---|---|
| 整屏重画（`-DSNAKE_FULL_REDRAW` 强制 `scr_ok=0`） | **60 553 B** | **2 523 B/帧**（24 帧就打满链路） | 复现 P1-3 之前的行为 |
| 增量重绘（发布版） | **3 115 B** | ≈ **30 B/步**（首帧 2 667 B + 之后共 447 B） | 首帧一次性画满，之后只发改动 |

单步流量：**2 523 B → 30 B（约 84×）**；整窗口：**60 553 B → 3 115 B（约 19×）**。
`-DSNAKE_FULL_REDRAW` 这个开关保留在源码里（默认不开），是这次 A/B 的可复现手段。

复现：

```powershell
powershell -NoProfile -File _diag\board_run.ps1 -Hex sw\build\snake_play_irom.hex `
    -DramHex sw\build\snake_play_dram.hex -Repeat 2 -NoGo -ReleaseWaitMs 500 -ListenSec 9
```

## 仍然没做到的 / 已知边界

1. **容器路径没有进仿真回归**：`sa` + `run`（容器解析、校验和、数据拷贝）目前只有
   **板上实测**。原因是仿真里要把 540 B 容器逐字节喂进 `tb_monitor`，约 105 ms 仿真时间，
   iverilog 下太贵。下一步可以做 `+fs=` 预装 FS 镜像（`sw/mkfs.py`）走一次端到端。
2. **应用代码区只有 40 KB，shell 余量 780 B**：`_etext = 0x4CF4`，`IROM_APP_MIN` 一旦
   涨到 `0x6000`，`run`/`L` 会**拒绝**（不会静默踩坏 shell），届时把 `APP_EXEC` 再上移一档。
3. **`b`（重新进引导器）在应用里无效**：应用不解析串口命令，`-PreCmd b` 只有 shell 在
   运行时才管用；应用跑着的时候只能重配 FPGA 才能回到 shell（本轮 A/B 就踩过）。
4. **`run` 之后 DRAM 里的应用数据不会被回收**：下次 `run` 覆盖即可，但 `df` 不反映它。
