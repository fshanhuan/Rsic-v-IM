## 1. 一句话结论

记录仪的**数据通路已经在真板上完整跑通**：XADC 200 kHz 采样 → FIFO → RV32 列摘要 →
每帧 800 列推给显示子系统 → 60 Hz 提交翻 bank → HDMI 时序发生器输出 800×600@60、
帧参数与理论逐项一致。**唯一没验证的是"像素真的出到 HDMI 线上"**——这一步卡在
"没有 HDMI 显示器"（ADV7511 收不到 HPD 就不应答 I2C，也就不出图）。

**双核那条线也已经打通**：PS（ARM）侧通过 AXI 读记录仪 FIFO、排空 2048 个样本到 PL DRAM、
导出 CSV，实测吞吐 **≈400 kSa/s**（对 200 kHz 采样有 2× 余量），且全程不影响 PL 侧采样节奏——
**S5 的 CSV 导出与 S7 的解耦结论都已完成**；SD 卡写入的**代码侧也全部完成**，
只剩"真卡认不认这个位翻转时序"这一项实物验证（卡槽里没有卡，见 §4.3 / §11）。

## 4. 未完成项与明确卡点

### 4.1 HDMI（阻塞 S1a 的 ACK、S3/S6 的可见画面）

> **2026-11-19 22:15 更新：原来的"HPD 低"判断被证伪了半条。**
> 采集卡（UGREEN-25854）已经接上、并且**带着 HDMI 线冷上电**过一次 ——
> ADV7511 **仍然不 ACK**：`init_done=0` / `init_ack_err` 继续涨（+35/4 s）/
> `hdmi_scl=hdmi_sda=0`。所以**不是"没插显示器"**这么简单。
> 详见《方案》§52。

- **现象**：ADV7511 恒无 ACK；主控电气正常（`line_health=0x55`）、
  37 根引脚与厂商手册逐脚一致、自动配置每 200 ms 重试（`init_ack_err` 持续增长）。
- **已排除**：
  1. **不是"没有 sink"** —— 采集卡一直插着、且冷上电过一次，仍然 `BUS_HELD_LOW`；
  2. **不是主控/总线电气** —— 同一颗 I2C 主控在音频总线 ADAU1761 上正常 ACK（`f_a=0x0009`）；
  3. **不是视频时序** —— `663168` 像素/帧、`628` 行、DE `480000`、hs/ vs 低电平与理论逐项相同；
  4. **不是上拉缺失** —— 原理图 P31/P32：R110/R140 = 2.2 kΩ→1.8 V、R106/R107 = 2.2 kΩ→3.3 V，
     而且 XDC 还开了 FPGA 内部上拉。**上拉齐全却仍读 0 ⇒ 有东西在把两根线按住**。
- **结论（2026-11-20 20:0x，已实测确认）：`IIC_SCL_HDMI` 与 `IIC_SDA_HDMI` 在板上是同一个电节点。**
  判据（新位流加的两个 VIO 输出，可以**只把一根线按低**，并等 400 ms 让主控进入 200 ms
  静默期再读 21 ms 占空比窗口）：

  | 状态 | SCL | SDA |
  |---|---|---|
  | 都释放（基线）| 363275 = 34.64% | 363275 = **34.64%** |
  | **只按低 SCL** | 0 | **0**（SDA 被拖低）|
  | **只按低 SDA** | **0**（SCL 被拖低）| 0 |
  | 都释放（恢复）| 834758 = 79.61% | 834758 = 79.61% |

  RTL 里两条 oe 是分开的（逐行核对），同期音频总线 `line_health` 仍 `0x55`（ADAU1761 正常 ACK），
  所以短路只发生在 HDMI 这一对线上。**不是 ADV7511 坏了，也不是软件问题。**
  这一条同时解释了：`f_h=0x0000`、两线读数永远相等、健康总线空闲应 ≈99% 而实测只有 0.4%~80%、
  冷上电/拔插线/修探测模块/改 swap 全都无效。
- **下一步（一个 10 秒的动作）**：断电，通断档量 **HDMI 母座 15 ↔ 16 脚**（相邻脚，最常见搭桥位置）。
  通了就清锡；不通再量 U30 55↔56、FPGA AB10↔AB9。
  完整修复与复验步骤见 **`docs/记录仪_HDMI短接修复单.md`**。
- **修好以后的判据**：`scl_hi_cnt` 与 `sda_hi_cnt` **不再相等** → `f_h` 出现器件 → `init_done=1`；

## 6. 本次工程里**真正有价值**的几个发现

1. **DCache 不可缓存读的错位**（`syn/修复史_全量.md` §DCACHE-7）：用寄存侧身份判断
   "这笔读完成了"，会在 LSU 已换到下一笔时误判 → 连续读不同 MMIO 寄存器会读到上一条的值。
   `monitor` 那种**同地址轮询**把这个 bug 完全掩盖了十几年。修法一个条件；
   55 项回归全过；上板验证排空速率从 150/s 变成 200 kHz。
2. **`ADC_CTL` 的 pop 位顺手清掉了使能**：软件写 4 想"弹一个"，bit0=0 把采样器关了。
   指纹是 `adc_cnt` 死死停在 1024（= FIFO 深度）。修法：`if (!wdata[2]) adc_en <= wdata[0]`。
3. **`$readmemh` 找不到文件只给警告**：BRAM 初值全 0，上板表现是"CPU 停在 0x0"，
   和"程序写错"完全分不清。现在有三道自检（文件级 10 项 / 综合日志装载确认 / VIO 的 PC 范围）
   和 `tools/mk_boot_image.py` 的 4 项生成期自检。
4. **Vivado 会把 32 位带字节写使能的 RAM 拆成 4 位字节通道**：所以"查 BRAM 的 INIT_00
   里有没有完整的字"是错的检查方法（第一版就这么误报过 FAIL）。
5. **JTAG 烧 `.bit` 只配 PL、不配 PS**（§30.8）：PS 侧 `LVL_SHFTR_EN`/`FCLK0`/`RST_FPGA` 全是关的，
   ARM 一碰 AXI 就永久等待，把 PS 互连锁死、连核都 halt 不住，只能断电。
   现在 ARM 程序自带 SLCR 前置 + 自检位。
6. **A9 的 `STR` 是 posting 的**（§33.2）：`pop` 之后紧跟 `peek` 会重复读到同一队头，
   游程里出现 215（>128）就是它的指纹；加 `DSB SY` 才干净。
7. **AXI 从端必须有授权超时**（§31）：从端不出响应时，主机的整条互连会被一笔事务锁死。
   `axil_slave` 现在 64 拍超时回 SLVERR，仿真 15/15 覆盖。
8. **没有显示器也能证明"画面上是什么"**（§34）：像素域 ILA + 按颜色触发，
   分别抓到网格（80 像素间距）、波形亮线（**800 个亮像素占满整行**）、文本面板（`0x1880`+`0xEB80`）。

### 11.7 再补一轮（2026-11-18）：把"最像没插卡"的三个隐患先修掉

板子仍不可用，所以继续在软件侧找"插卡那天会白折腾一轮"的地方：

| 隐患 | 为什么会误导 | 修法 |
|---|---|---|
| **CRC7 从没和外部标准对过** | SD 卡只在 CMD0/CMD8 检查命令 CRC7；算错就是"CMD0 不复位、CMD8 被拒"，现象和没插卡**一模一样** | 抽成 `sw/ps/sd_crc.c`（可被 PC 编译），拿规范公开的帧当标准答案：CMD0 帧尾 **0x95**、CMD8 帧尾 **0x87**、XMODEM(`"123456789"`)=**0x31C3** |
| **响应窗口只给 32 个时钟** | 规范允许 NCR 最长 **64** 个时钟（8 字节）；慢一点的卡会被当成"没响应" | 窗口 32 → **64**，并新增 `ncr=` 打印实际等了多少个时钟 |
| **提速失败直接崩整轮** | 位翻转能跑多快事先不知道，一失败就整轮重来且看不出原因 | 新增 `sd_bit_speed_probe()`：高速读不出来自动退回慢速，只有两种速度都失败才报错 |

主机侧检查从 27 项增到 **33 项，全通过**（新增 6 项 CRC 已知答案）。
五个板上程序重新编译通过，`_stack_top` 全部在 `0x2_0000` 之下。

CRC 的标准答案有两个来源：SD 规范里公开的帧，以及我按多项式独立用 Python 算的一遍 —— 两者一致。

### 11.8 位级仿真（2026-11-18）：抓出一个会让真卡"全是废数据"的 bug

板子仍不可用，于是给 `sd_bit_bus.c`（位翻转驱动）在 PC 上接了一个**按位应答的 SD 卡模型**
（拦掉 GPIO 读写），原封不动跑真代码：识别 → 读块 → 写块 → 整卷格式化 → 1000 样本 CSV → 回读比对。

**第一次跑就抓到一个致命 bug**：`rd48()` 在起始位之后只跳过 6 位，而 48 位响应是
`0 | 0(传输位) | cmd[5:0] | 内容 | crc7 | 1`，应该跳 **7 位**。结果是**每个响应的内容都左移一位**：

| 现象 | 正确值 | 实到值 |
|---|---|---|
| CMD8 响应 | 0x000001AA | 0x000000D5 |
| ACMD41 OCR | 0xC0FF8000 | 0xE07FC000 |
| CMD3 RCA | 0x1234 | 0x891A |
| CMD7 R1 | 0x00000000 | 0x80000000（被当成"错误位"） |

真卡上会表现为"卡有应答，但 RCA 错、CMD7 选不中、读块全返回 R1 错误"——
比"没响应"难查得多。修完重跑：

| 项 | 结果 |
|---|---|
| 识别 | `RCA=0x1234`、`OCR=0xC0FF8000`、`CMD8=0x1AA`，全对 |
| 命令 / CRC7 错 | **1125** 条命令，**0** 个 CRC7 错（卡的独立实现逐帧验过） |
| 写块 / CRC16 错 | **1072** 次写块，**0** 个 CRC16 错 |
| 读块 | 45 次 |
| 产品路径 | CSV 9603 字节、djb2 `0x545706DB`、**逐字节 diff=0** |
| 主机侧断言 | **21/21 通过** |
| 独立复核 | 规范解析 + pyfatfs 都 PASS |

一键：`powershell -NoProfile -File tools\ps\host\build_sim.ps1`

仿真的边界很清楚：位序/帧格式/CRC/换向/令牌/忙等**全部真的执行了**；
没覆盖的只有"电平上升沿要等多久"（电气时序）和卡的真实初始化耗时。
所以真卡插上后，剩下的未知基本只剩时序 —— 而那已经有 `sd_bit_speed_probe()`
自动降速和 `ncr=` 诊断兜底。

### 11.9 板子抢救与运行脚本加固（2026-11-18）

**新发现**：DAP 的 `APB AP transaction error`（status `0x30000021`）可以用
`rst -dap` 清掉，**不必断电** —— 清完 A9 目标立刻回来，`sd_bit.elf` 成功跑了一次。

但只能救一次：随后再下载就变成 `0xF0000021`（A9 目标自己报 APB 错），
`rst -dap` / `-system` / `-processor` / `stop` 全无效（`_diag/_dap_probe.tcl` 逐个试过）。
旁证：同一会话里 `fpga -f` 编程 PL **成功**，所以 JTAG 和 PL 都是好的，问题只在 PS 调试 APB。

**这一轮唯一的硬件证据**（插卡前的基线，`sd_bit.elf`）：

```
gpio: MIO=0x0700 CLK-follow=1 DATA_RO=0xffff
half=300 (~333 kHz)
[2] CMD8 -> TIMEOUT idle=1 waitbits=0xffffffff ncr=64
```

`ncr=64` 说明"没卡"这个判断现在覆盖了规范允许的完整 64 时钟窗口。

**脚本加固**（`_diag/ps_run_sd.tcl`）：

| 改动 | 原因 |
|---|---|
| PSS 软复位默认关闭（`$env:PS_SOFTRESET='1'` 才做） | 位翻转不用 SDHCI；而 PSS 复位后调试 APB 极易 timeout |
| A9 不在时自动 `rst -dap`（最多 3 次） | 能自愈的自动恢复 |
| `dow` 失败自动重试 3 次 | 偶发错误不白跑 |
| 日志按十进制解码 | `mrd -value` 返回十进制（§40.9 的坑） |

**另一个改进**：把"验证要 dump 哪些扇区"抽成 `sd_record.c` 的 `sd_evid_plan()`，
板上 `sd_dump.c` 和 PC 测试**共用同一份代码**。主机侧检查从 33 项涨到 **37 项，全通过**。

### 11.10 一条命令跑完整场验证（2026-11-18）

插卡那天原本要按顺序跑 6~7 条命令、每条吐一大段日志，手机上容易看漏。
现在收成一条：

```powershell
powershell -NoProfile -File tools\ps\sd_session.ps1            # Card 模式
```

它按 `preflight → sd_bit → write → dump → verify` 走，**任何一步失败就停并说明原因**，
最后给一张 `[PASS]/[FAIL]` 表。`--samples` 从日志里自动解析，不用人工数。

三种模式都实测过（在板子不可用的情况下）：

| 模式 | 实测结果 |
|---|---|
| `-Mode Plan` | 打印 7 步计划，退出 0 |

| `-Mode Card` | 停在 preflight，明确提示需要拔电，退出 1 |
