## 1. Memory subsystem as implemented

### 1.1 DCache geometry
| Property | Value | Evidence |
|---|---|---|
| Geometry | direct-mapped, 64 lines × 32 bit (2 KiB), block = 1 word, no offset field | `para.sv:155-156`, `DCache.sv:61`, `DCache.sv:77-78` |
| Associativity | 1-way | `DCache.sv:92-93` |
| Tag/valid | per-line valid bit + tag, reset-cleared | `DCache.sv:63-64`, `DCache.sv:183-184` |
| Write policy | **write-through, no write-allocate**, plus store-hit merge into the resident line | header `DCache.sv:27`, merge `DCache.sv:249-261` |
| Dirty handling | none — no dirty bit exists; every store goes to the DRAM port the cycle after issue | `DCache.sv:164`, `DCache.sv:215` |
| Uncacheable window | `addr & ~32'h0FFF_FFFF != 0` ⇒ MMIO: never resident, never filled, never merged | `DCache.sv:37`, `DCache.sv:86-88`, `DCache.sv:242` |
| Counters | 32-bit hit/miss counters exist (observability only) | `DCache.sv:237-238` |

**Latency (cycles), load:**
* hit: resolved combinationally in the request cycle — `hit_now` (`DCache.sv:120-122`) compares the
  *current* address against the array (`DCache.sv:132`), so `hold = 0` (`DCache.sv:139`). 0 stall cycles.
* miss: `hold` is asserted for **exactly 2 cycles**. Request cycle T: `line_resident=0` ⇒ `cache_rd_req=1`,
  `mem_en` pulses once (`DCache.sv:101,106`); sync_mem returns at the T+1 edge (`sync_mem.sv:109`);
  `mem_req_r` is still 1 and `resp_for_now` is 0 in T+1 because the address comparator `addr_same_r`
  compares against the *previous* edge's `cpu_addr_r` (`DCache.sv:82`, `DCache.sv:125`), so `hold` stays 1
  in T+1; the fill happens at the T+2 edge (`DCache.sv:242-246`) and `hold` drops there.
  ⇒ +2 stall cycles, plus 1 register slice to get from the bus phase to writeback.
* store: never stalls (`hold` is gated by `~cpu_wen`, `DCache.sv:139`).

**Read latency accounting is correct.** The RTL keeps the read window and the fill window strictly
apart: `mem_en` is a one-shot (`DCache.sv:101-106,211-212`), and the "compare against the issuing
request" test uses the *registered* index/tag (`DCache.sv:125`) precisely because `cpu_addr_r` lags
`cpu_addr` by one edge. The LSU side honours it: `rdata_reg2 <= rdata` is unconditional
(`LSU.sv:278`) and samples the raw bus word on the fill cycle — the invariant is documented at
`LSU.sv:223-224` and the DCache side at `DCache.sv:113-119`. §DCACHE-1 in `syn/修复史_全量.md`
records that the previous version resolved `hold` from `cache_rd_req` and released the pipeline one
cycle early.

### 1.2 Bus / handshake
* `perip_ren = dcache_mem_en` and `perip_wen = store_req_r(mm_wen)` — a **single-cycle read request**
  and a **single-cycle write pulse**; sync_mem has no `ready` (`myCPU.sv:724-728,737`,
  `sync_mem.sv:14-15`).
* The write pulse is generated by a 3-state FSM (`WR_IDLE/WR_ISSUE/WR_WAIT`, `DCache.sv:142-144`,
  `DCache.sv:216-221`). The RTL comment (`DCache.sv:24-25`) records the bug history: an edge detector
  failed because `cpu_en` is a *level* held by the LSU register, so a store immediately after a load
  was never written. `store2_wdata/mask/index/offset/hit` are captured only at `store_fire`
  (`DCache.sv:226-232`) so a parked request cannot be re-issued with new payload.
* Read mask is forced to `2'b10` for the whole read window (`DCache.sv:176-177`); the board BRAM
  ignores the read mask (`sync_mem.sv:109`), so this only matters for the course SoC model.

### 1.3 LSU's extra stages — functionally necessary or delay?
The LSU is a 3-deep register slice (`LSU.sv:9-13`, one `always_ff` at `LSU.sv:225-309`):

| Stage | Contains | Necessary? |
|---|---|---|
| M1 | EXU payload (`LSU.sv:294-307`), byte-lane decode uses `[1:0]` (`LSU.sv:340,347`) | **Yes** — breaks EXU→address/payload |
| M2 | the *bus issue* cycle: `addr/wen/wdata/mask` are driven combinationally from M2 (`LSU.sv:168-171`) | **Yes** — but note the DCache re-registers the address again (`DCache.sv:203`) before driving the BRAM |
| M3 | capture `rdata` (`LSU.sv:278`) + `rd_value/rd/funct3/wb_sel` (`LSU.sv:268-277`) | **Needed only for the miss case** (`sync_mem` 1-cycle read latency). On a hit the data is available at M2 (`DCache.sv:132`) and M3 is pure staging |

Cost of the slice: ≈124 payload bits × 3 stages ≈ **372 FF**, of which the M3 slice alone is ≈127 FF
and is 100 % dead for every ALU/jump/CSR instruction (it carries `Ex_result_fwd_reg`/`rd_value` for the
forwarding network only, `LSU.sv:200,218`). Note the duplicated address alias:
`Ex_result_addr_reg`/`Ex_result_fwd_reg` are two 32-bit registers holding the same value
(`LSU.sv:97-98,231-232,284-285,299-300`), i.e. ~64 FF/stage-unit of pure duplication, on top of the
`(* max_fanout = 32/16/8 *)` attributes that instruct synthesis to replicate them further.

### 1.4 Store buffer
**None.** The store is a level→pulse adapter only; there is no queue, no commit buffer, no
retry path. Writes complete in the issue cycle (`DCache.sv:164`, `sync_mem.sv:110-126`). Search for
any FIFO/queue in `rtl/` returns nothing. Consequence: the moment the DRAM port can backpressure
(or the store must wait for a line fill), the whole pipeline must freeze behind it; today the
penalty is hidden only because `sync_mem` never refuses a write.

### 1.5 Exact timing
**Load-use stall = 1 cycle.** `Data_hazard.sv:116-123` stalls on `exu_load_use | mem_load_use |
pipe_load_use` (i.e. the load sitting in EX / M1 / M2). `load_use_stall` joins `IFU_stall`
(`Control.sv:297`) and `EXU_inst_clear` (`Control.sv:291-293`), so the consumer is re-issued;
by then the load is in M3 and is forwarded by `MEM2_Ex_result = LSU_forward_val_wb`
(`myCPU.sv:376`,`Data_hazard.sv:80`). The reason EX/M1/M2 cannot forward is explicit: on a load
`Ex_result` is the *address*, and only M3's `rdata_reg2` is data (`LSU.sv:59,216-218`,
`Data_hazard.sv:61-65`).

**Store timing:** store accepted in EX at cycle T; M1 at T+1; M2 at T+2 drives `wen`,
`addr`=`{M2[31:18],2'b00,M2[15:0]}` (`LSU.sv:168`), `wdata`, `mask`; DCache sees `cpu_en&cpu_wen`
in T+2, latches `store2_*` at the T+3 edge and raises `mem_wen` in T+3 (`DCache.sv:160,215,226-232`);
the BRAM accepts the write at the T+4 edge (`sync_mem.sv:105-126`). **Zero stall cycles.**

**Full round trip:** `jal x1, L; L: lw x2, 0(x1)` — data in `rdata_reg2` 1 cycle after the DCache
fill, i.e. **5 cycles** EX→writeback (`EX_result`→M1→M2→bus/M3-reg→WBU→RF).

## 2. MDU as implemented

### 2.1 Algorithm
* Multiply: **three parallel 32×32 array multipliers**, all live every cycle
  (`MDU_pipelined.sv:62-77`), result selected by `op_sel`, registered 1 cycle after EXU latches
  the operands (`MDU_pipelined.sv:126-131`).
* Divide: **radix-2 shift/subtract, restoring-remainder form with the remainder held in a
  *forward-shifted* form** (`shifted = {r_rem[30:0], r_a[31]}`, `rem_nxt = shifted ≥ r_div ?
  shifted - r_div : shifted`, `q_nxt = {r_q[30:0], not_neg}`), `MDU_pipelined.sv:98-103,148-159`.
  Fixed 32 iterations (`div_cnt == DIV_BITS-1`, `MDU_pipelined.sv:152`), no leading-zero skip,
  no early exit, no separate div/rem datapath. Signed ops are done by `abs32` in / sign fix-up out
  (`MDU_pipelined.sv:56-58,139-147,163-166`).
* Left-shift of `r_a` (`MDU_pipelined.sv:151`) is **redundant**: the bit consumed each iteration is
  `r_a[31]`, and `shifted` already takes it from the fixed `r_a`. One 32-bit shifter per cycle does
  nothing.

### 2.2 Cycles per operation (derived from the handshake, `EXU.sv:160-243`)
* **Multiply = 3 cycles occupied in EX ⇒ 2 added stall cycles.**
  T: `mdu_start` pulses (`EXU.sv:178`), operands are the *registered* `add1_reg/add2_reg`
  (`EXU.sv:398-404`). T+1: `mul_res_reg`/`mul_stb` set, `mdu_res_vld` set at the edge (`EXU.sv:231-234`),
  `mdu_stall` deasserts (`EXU.sv:181`). The result reaches the LSU at the T+3 edge.
  `syn/上板改造说明.md:155` claims "multiplication 1 beat, stall=0"; that holds only for the MDU's
  own `busy` output (`MDU_pipelined.sv:201`) — `EXU.mdu_stall` is `alu_opcode_reg[4] & ~mdu_res_vld`
  (`EXU.sv:181`), so the *pipeline* is frozen for 2 cycles per multiply.
* **Divide = 34 cycles from EX entry to release** (T … T+33 frozen; 34 stall cycles): cycle T is the
  launch, T+1 … T+32 are the 32 iterations, T+33 is the `div_hold` result window
  (`MDU_pipelined.sv:152-155,198-202`). The `div_hold` cycle is avoidable (see §4).
* Division of an unsigned op costs exactly the same as signed (abs/sign-fix is free combinational).

### 2.3 Does it stall the whole pipeline? Yes — completely.
`mdu_busy = mdu_stall` (`EXU.sv:183`) is wired to `Control.IFU_stall` (`Control.sv:297`, freezing
PC and ID), to `LSU.lsu_freeze` (`LSU.sv:152`, freezing all three LSU stages and `ready_last`), and to
the EXU's own `valid_next`/data registers (`EXU.sv:195-206,259`). WBU has no stall port at all
(`WBU.sv:163` returns `ready=1'b1`). So one `div` freezes fetch, decode, execute, memory and writeback
for 34 cycles; a loop body containing one `div` runs at ~34 cycles/iteration.

### 2.4 DSP48 inference
`util_post_route.rpt:118-122` — 12 × `DSP48E1`. The synthesis DSP report
(`v9_ila/v9_ila.runs/synth_1/runme.log`, DSP table) attributes **all 12 to `MDU_pipelined`**:
four groups of `A*B (18×18)` + `(PCIN>>17)+A*B` chained pairs ⇒ **4 DSPs per 32×32 signed/unsigned
multiplier, ×3 multipliers = 12**. So no, 3-4 DSPs is not what happens: the design pays 3× the
minimum because `prod_ss`/`prod_su`/`prod_uu` (`MDU_pipelined.sv:63-65`) are all synthesised, and
`prod_su` additionally widens one operand (`$signed({1'b0,d2})` = 33 bits, `MDU_pipelined.sv:64`),
which is why the report shows 18×18 and mixed 18/16 patterns rather than a clean 17×17 split.
DSP usage is 5.45 % of the device and there is no DSP sharing or time-multiplexing anywhere else in
the core.

### 2.5 Could the divider be much cheaper?
Cheaper in *logic*, not in *latency*: it is already only 407 LC / 81 CARRY4 / 235 FF
(`syn/synth_report.md:39`), i.e. it is not the area problem. The real cost is the **32-cycle
blocking latency**. Radix-4 halves iterations to 16; radix-8 gets ~11 iterations for one 32-bit
adder (3d = 2d+d) plus a 4-way q-digit mux; the classic trick for the case `r_div` has many leading
zeros is to normalise/skip — not applicable to a wall-clock-time divider without leading-zero
count. A dedicated `clz`-based skip for the common `dividend < divisor` (quotient 0, remainder =
dividend) case would return in a few cycles, but needs care with signed/div-zero semantics.

### 2.6 Does the unused combinational `MDU.sv` reveal a better structure?
**No — it is strictly worse, and it is not on the compile list.** `rtl/MDU.sv` is a single-cycle
combinational unit: the same three 32×32 multipliers (`MDU.sv:36-38`) **plus** a fully unrolled
32-stage restoring divider written as an `always_comb` for-loop (`MDU.sv:55-67`). Measured:
**2150 LC / 419 CARRY4 / 12 DSP / 0 FF** vs the pipelined **407 LC / 81 CARRY4 / 12 DSP / 235 FF**
(`syn/synth_report.md:38-39`, `syn/上板改造说明.md`). Keeping it compilable is what forces the file to
live in `rtl/` (`MDU_pipelined.sv:1-10`), which is a maintenance hazard, not a resource one.
Two details in it are worth stealing, though: it computes the final remainder through a fixed
`rem` accumulator instead of the shifting `r_a` (`MDU.sv:59-66`), and it derives the result directly
from the combinational divider outputs (relevant to §4).

## 3. Concrete inefficiencies (file:line, quantified)

1. **The DCache data array is not a RAM in hardware — it is 2048 flops + muxes.**
   Synthesis: `WARNING: [Synth 8-4767] Trying to implement RAM 'data_reg' in registers ... [DCache.sv:252]`
   with reason *"RAM has multiple writes via different ports in same process"*
   (`v9_ila/v9_ila.runs/synth_1/runme.log:125-129`). Root cause is the same array written from two
   places in one `always_ff`: the fill path `data[cpu_index_r] <= mem_rdata` (`DCache.sv:245`) and the
   merge path `data[store2_index][...] <= store2_wdata[...]` (`DCache.sv:249-261`). Cost: **2048 FF**
   (13.9 % of the design's 14 765 FF) plus the 64:1 byte-lane read mux and the 8-byte-lane write
   enable network — roughly **1.5–2.5 k LUT** of the 12 006 LUT-as-logic. The ICache has the same
   three arrays but a single write site (`ICache.sv:140-148`) and its `data`/`tag` *did* infer as
   RAM64X1S (`distributed RAM table`, same log) — that is the proof of what the DCache is missing.
   The **tag array did infer** (`DCache.sv:244` is the only tag write; RAM64X1D × 24 in the same
   report), so this is a targeted, local defect rather than a broken cache.

2. **The register file is flip-flops, not LUTRAM.** `rtl/RegisterFile.sv:23-38` — one array, two
   combinational read ports, one synchronous write port, and a **full-array reset loop**
   (`RegisterFile.sv:27-29`). A reset that clears every entry cannot be mapped to distributed RAM
   (no reset on the LUT-RAM primitive), and indeed the vendor distributed-RAM report lists only
   ICache `data`/`tag` and DCache `tag` — the register file is absent, i.e. it stayed registers.
   Cost: **1024 FF** + the two independent 32:1 read muxes (≈600–1100 LUT) + one write-side decoder.

3. **Redundant buffering: LSU M1/M2/M3 + DCache request register + WBU = four registers in series.**
   `LSU.sv:225-309` (3 stages, ≈372 FF), `DCache.sv:68-73,203-208` (`cpu_addr_r`, `cpu_index_r`,
   `cpu_tag_r`, `cpu_en_r`, `resp_valid_r`, `cpu_wen_r` — another ~75 FF) and `WBU.sv:59-88` (≈135 FF)
   add another ~210 FF. Total memory-side register tax ≈ **3.8 k FF** (DCache arrays 3584 + ICache
   3136 + LSU 372 + WBU 135 + control ≈ 7.6 k in the core, of the 14 765 reported).

4. **LSU holds two 32-bit registers with identical content, twice over, and asks for replication.**
   `LSU.sv:97-98` (`Ex_result_addr_reg` fanout 32, `Ex_result_fwd_reg` fanout 16) and `LSU.sv:118-119`
   (`Ex_result_addr_reg_pipe` fanout 8, `Ex_result_fwd_reg_pipe`). Both aliases are written from the
   same source at the same edge (`LSU.sv:231-232,284-285,299-300`). ≈64 FF/stage-unit duplicated,
   plus whatever the `max_fanout` attributes physically replicate.

5. **The M1-rung load-decode/selector path is dead logic.** `rdata_ex` (byte lane `LSU.sv:339-347`,
   sext instances `LSU.sv:366-400`) feeds only `LSU_Rdata` (`LSU.sv:176`), which is connected only to
   `Control.MEM_Rdata` (`myCPU.sv:379`) — a port `Control.sv` never reads (the forwarding network
   uses `MEM2_Ex_result` only for load data, `Control.sv:314-321`). Synthesis confirms the trimming:
   `WARNING: [Synth 8-3936] ... 'rdata_byte_sel_reg' ... trimmed from '32' to '8' bits [LSU.sv:341]`
   (and `rdata_byte_sel2_reg`, `LSU.sv:352`). 4 `sext` instances + 2 byte/half-lane muxes are
   duplicated again in `WBU.sv:103-150` for the same value. Cost: ~200–400 LUT of duplicated
   decode/extension.

6. **No store buffer / no write-combining.** `DCache.sv:160-164,215` — one bus write per store, no
   queue. Zero cost today (BRAM never backpressures), but it makes the design unable to tolerate a
   wait-stated bus and forces full-pipeline freezes if one is ever introduced (`LSU.sv:152`).

7. **DCache holds a 32-bit `store2` payload and a 3-state FSM to emit a 1-cycle pulse.**
   `DCache.sv:142-158,226-232`. It works, but 40 FF + an FSM for what is, absent backpressure, a
   simple "write once when the request first appears" (`DCache.sv:24-25` documents why edge detection
   failed: `cpu_en` is a level, not a pulse).

8. **MDU: 3 multipliers where 1 suffices.** `MDU_pipelined.sv:62-65`. The synthesis DSP table lists
   twelve 18×18 / 16×16 `DSP48E1` slices, all in `MDU_pipelined` — **8 redundant DSPs** (3.6 % of the
   220 available) and their associated C/D/PCIN routing. `prod_su`'s 33-bit operand is a second,
   independent waste (`MDU_pipelined.sv:64`).

9. **Divide stalls the entire core for 34 cycles and its last 2 cycles are pure overhead.**
   `MDU_pipelined.sv:152-155` (the iteration that retires the last quotient bit also raises
   `div_hold`; the quotient is not visible until the following cycle via `r_q`) plus the extra EX
   cycle to latch `mdu_res_reg` (`EXU.sv:231-234`). A loop of 100 divisions loses ~3 400 cycles; the
   `r_a <= {r_a[30:0],1'b0}` shift (`MDU_pipelined.sv:151`) is dead as well.

## 4. Optimization opportunities, ranked

Estimates are order-of-magnitude from the two Vivado reports plus per-bit accounting; "risk" =
chance of a functional regression in a design whose difftest harness is not available here
(`syn/上板改造说明.md` "still not done: real difftest").

Edit `MDU_pipelined.sv:62-77` only. | **−8 DSP48E1**, −100…−250 LUT (12→4 DSPs, back to 1.8 % of device) | 0 | Low — pure arithmetic identity, 4968-vector harness already exists (`experimental/MDU_tb.sv`) | 2 |

| **P8** | **Carry the selected load word across M2→M3 instead of the raw bus word** (`LSU.sv:278`): register `cpu_rdata` already byte-selected. Only shrinks the M3 fan-in path; the M3→WBU offset/`funct3` re-selection stays. | ~0 | 0 | Low | 2 |

| **X3** | **Split-multiply into a 2-stage pipeline (no stall at all).** The multiply's 2-cycle stall is an artefact of `mdu_res_vld` (`EXU.sv:181,231-234`), not of the multiplier (operands live in `add1_reg`/`add2_reg`, `EXU.sv:398-404`, so the array input is already a flop-to-flop path). **Explicitly not worth doing**
* **Shrinking the 64-line direct-mapped DCache to 32/16 lines for hit rate.** Hit rate is a
  workload property, not an area property, and the array is already only 2 KiB; the area problem is
  the *implementation* (P1), not the geometry.
* **Forcing the DCache arrays into Block RAM.** A 64×32 array in a RAMB36 (or 2× RAMB18) wastes
  27.5 % → 29 % BRAM for a build whose BRAM budget is already the tightest resource in this design;
  LUTRAM (P1) is strictly better at this size.
* **`MDU.sv` (combinational) as a basis for anything.** 2150 LC / 419 CARRY4 vs 407 / 81. Its only
  value is as the historical argument for the pipelined version. Do not re-enable it; if anything,
  move it out of `rtl/` and add a stub so `cdp-tests`'s `rtl/*.sv` wildcard still resolves
  (`MDU_pipelined.sv:1-10`).
* **The 2-cycle DCache miss penalty as such.** Each of the two cycles removes a real timing hazard
  (the synchroniser `cpu_index_r/cpu_tag_r` vs `cpu_addr_r` alignment, `DCache.sv:82,124-125`).
  Folding them would re-create the §DCACHE-1 off-by-one; the miss *rate* is the lever, not the
  miss latency.
* **`LSU.sv:168`'s odd-looking `2'b00` insert at bits [17:16].** It is deliberate and equivalent for
  the current 64 KiB map (`LSU.sv:164-167`); touch it only with the memory map, never as a cleanup.
* **Replacing the WBU stage with direct writeback.** It is the only stage that closes the register
  file write and the debug probes are specified off it (`myCPU.sv:264-268,746-748`); the 135 FF is
  cheap insurance.

## 5. Gap vs mainstream RISC-V cores

| Aspect | This core (v9) | Rocket | BOOM | CVA6/Ariane | SweRV EH1 | VexRiscv | PicoRV32 |
|---|---|---|---|---|---|---|---|
| Cache hierarchy | L1I + L1D only, both direct-mapped, 64×1-word lines, no L2 | configurable L1I/L1D (typically ≥4 KiB) with L2 in `tilelink` | L1I/L1D with MSHRs, non-blocking, plus L2 | L1I 16 KiB + L1D 32 KiB, WB L1D, WT L2 | I-cache/DCCM configurable; no L1D cache in the base config | optional I/D caches, configurable | **none** (flat memory interface) |
| L1D write policy | write-through, hit-line merge, no write-allocate (`DCache.sv:27,249-261`) | WT or WB, configurable | WB | WB with dirty bits | WT to the bus, DCCM for scratch | WT or WB, configurable | n/a |
| Store buffer | **absent** (`DCache.sv:160-164`) | store buffer + MSHRs | store queue + MSHRs | write buffer before the L2 | yes — store buffer between LSU and the bus | optional write-back buffer | no |
| LSU pipelining | 3 register slices (`LSU.sv:225-309`), 1-cycle load-use stall, no MSHR, 1 outstanding miss | pipelined, multiple outstanding | out-of-order, deep | pipelined, 1+ outstanding | 2-stage LSU, in-order | configurable (1–2 stages) | memory interface stalls per access |
| MDU | iterative radix-2 divider, 34-cycle blocking; 3 parallel 32×32 multipliers (12 DSP) | pipelined/iterative `MulDiv` with DSP mapping | pipelined multiplier + radix-4 divider | `multiplier` (DSP or LUT) + `divider` (radix-2/4, `serdiv`) | 1-cycle 32×32 multiply, iterative divide | `MulPlugin` (pipelined, optional DSP) / `MulDivPlugin` | PCPI coprocessor (`PCPI_MUL`/`PCPI_DIV`), external |
| Separate div/rem | no — one datapath, result muxed (`MDU_pipelined.sv:171-192`) | shared | shared | shared (`serdiv`) | shared | shared | external |
| M-extension FPGA cost | **12 DSP48E1 + ~407 LC + 235 FF** (measured, `synth_report.md:39`) | 3–4 DSP48 per 32×32 multiplier + control | 6–12 DSPs + divider logic | 4–8 DSPs (LUT fallback exists) | 1-cycle multiplier only (LUT/DSP) | MulPlugin ≈ a few hundred LUTs / 4 DSPs; MulDivPlugin adds ~500 LUTs | external PCPI core |

Reference points (general, not measured here): a single unsigned 32×32 multiplier maps to
**4 DSP48E1** on 7-series; RV32M on a compact core is normally **600–2000 LUT + 3–8 DSP48** with
multi-cycle divide, and a 64-bit radix-2 iterative divider is ~400–800 LUT — i.e. this core's
divider is in the normal band, but its multiplier block is **3× the DSP cost** of the compact
consensus (P4) and it pays ~3 k extra LUT/FF for a DCache array that mainstream designs put in a
RAM (P1). See [VexRiscv MulPlugin](https://caeis.etech.fh-augsburg.de/beckmanf/de1_murax_franz.git/plain/VexRiscv/src/main/scala/vexriscv/plugin/MulPlugin.scala),
[VexRiscv MulSimplePlugin](https://caeis.etech.fh-augsburg.de/beckmanf/de1_murax_franz.git/tree/VexRiscv/src/main/scala/vexriscv/plugin/MulSimplePlugin.scala),
and [SweRV EH1 core analysis](https://repository.tugraz.at/publications/marc21/hdgg0-e7k63/files/83404.pdf).

**Summary of the gap:** the two structural deficits versus mainstream are (a) a mis-mapped L1D data
array that costs ~2 k FF and ~2 k LUT for what should be ~100 LUTRAM, and (b) a blocking 34-cycle
integer divide that freezes all six stages instead of scoreboarding the single dependent consumer.
The multiplier's 3× DSP usage is a smaller, purely mechanical defect. None of the three is on the
critical path (WNS +3.445 ns, `timing_post_route.rpt:149`), so all of them are area/throughput
optimisations, not timing ones.
